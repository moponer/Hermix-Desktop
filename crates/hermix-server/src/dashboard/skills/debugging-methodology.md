# 系统化调试

方法论：先建立可证伪的假设，再用最小成本验证。绝不靠猜改代码。

## 工具接线

1. **复现证据优先**：`terminal` 跑最小复现命令（一条命令、一个测试函数），
   `read_file` 读报错文件对应行。复现不了的先要环境信息（版本/OS/完整报错），
   不开工。
2. **隔离用低成本手段**：`search_files` 定位报错字符串与调用点（先于通读）；
   大文件走 offset/limit 分段；> 1500 行的排查走 `delegate_task`（Explore
   角色），task 里写清"找 X 的调用链与可疑分支，返回行号与结论"。
3. **验证修复**：修完必跑最小验证（对应用例 `cargo test -p <crate> --lib` /
   `node_modules/.bin/tsc --noEmit`），失败不得报完成。

## 四阶段纪律

1. **复现**：稳定复现步骤 + 复现条件（输入/环境/配置）。复现不了不修——
   可能是偶发或环境问题，先加日志蹲点。
2. **隔离**：二分法缩小范围（注释一半/切分支/二分提交历史），一次只验证
   **一个**假设。
3. **分析**：预期 vs 实际行为的差异就是根因线索；读日志还原时序，读代码找
   逻辑漏洞。
4. **修复**：最小修复 + 补防回归测试 + 主动告诉用户"怎么验证修好了"。

## 高频故障模式（先查这些）

- 竞态与时序：异步回调、缓存不一致
- 环境：编码/换行符（CRLF）、路径大小写、依赖版本漂移
- 边界：空值、超长输入、时区

## 反例（不要这样做）

- ❌ 一次甩给用户一堆排查步骤——一次只让用户做一件事
- ❌ 编造报错含义或 API 行为——不确定就说不确定
- ❌ 顺手重构无关代码——保持 diff 聚焦
- ❌ 盲目重试同一命令——连续两次失败就换假设

## 输出契约

调试报告四节：复现步骤 → 隔离结果（文件:行号）→ 根因（预期 vs 实际 vs 原因）
→ 修复方案 + 防复发建议。遵循系统提示 REPORT_SECTIONING 分节规则。

## 集成

- `tdd-practice`：先用失败测试锁定 bug（RED），再修（GREEN）
- `code-review`：修完进审查
- 参考：《调试九法》（Agans）
