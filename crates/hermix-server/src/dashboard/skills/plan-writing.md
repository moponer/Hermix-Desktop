# 撰写实施计划

## 工具接线

1. 计划落地用 `todo` 工具建任务组（首次 `create` 带 `group_title`，后续同
   组复用 `group_id`），每步一个可独立检查的任务；同一回复内的 create 归入
   同一计划，不逐步开新计划。
2. 需要摸现状再排计划时，`delegate_task`（Explore 角色）返回现状结论，
   禁止在计划里写"待确认"了事——确认完再出计划。
3. 计划变更（用户改需求/执行中发现偏差）用 `update` 改状态，不重建计划组。

## 六要素与质量判据

1. **目标**：一句话、可衡量。"优化性能"不合格，"首屏 LCP 从 4s 降到 2s 内"
   合格。
2. **范围**：明确包含什么、**不**包含什么——防蔓延。
3. **步骤**：可分配、可验证的粒度。判据：每步完成后能回答"怎么确认这步
   做完了"。动词模糊（"处理一下"）不合格。
4. **依赖**：前置条件与执行顺序，标出关键路径。缺依赖的排期是假的。
5. **风险**：前置识别 + 各配一个预案。比事后救火便宜。
6. **验收标准**：整体验收怎么测，写明命令或判据。

## 反例（不要这样做）

- ❌ 步骤写成"研究/调研/优化"——不可验证
- ❌ 只列步骤不写验收——计划完成后无判据，全靠感觉
- ❌ 计划一次堆满 30 步——先给里程碑，里程碑下再拆
- ❌ 把计划当枷锁——执行中发现偏差立即更新计划，不硬走

## 输出契约

计划以六要素分节呈现（遵循系统提示 REPORT_SECTIONING），同时 `todo` 建
任务组供用户看进度。宣布步骤≠执行：计划确认后立即开工第一步，不留
"接下来我会…"式的空回合（系统提示 PLAN_BEFORE_EXECUTE 规则）。

## 集成

- `architecture-design`：架构决策是计划的输入
- 参考：《金字塔原理》（明托）、Personal Kanban
