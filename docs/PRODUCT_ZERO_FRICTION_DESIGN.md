# Hermix Desktop 「对话即操作」产品简化设计方案

> 副标题：把「配置 / 安装 / 删除 / 审批 / 更新」五类用户手动操作尽可能归零，让桌面端只通过对话完成工作
> 状态：分析 + 头脑风暴稿（不开发）
> 日期：2026-07-24

---

## 0. TL;DR（给产品方先看这段）

**一句话目标**：Hermix 是个 Windows 桌面 AI 助手，用户打开它只为一件事——**把活交给对话**。但今天它里面塞了太多"只有懂行的人才配用"的手动操作：填 API Key、改 `config.yaml`、手丢 `SKILL.md`、每次危险操作点审批、手动清理缓存……这些不是功能，是**通往价值的收费站**。

**核心策略 = 3 个归零 + 3 个自动 + 1 个护栏**：

| 维度 | 今天 | 目标态 |
|---|---|---|
| **启动配置** | 不填 Provider+Key+默认模型就进不了对话 | 零配置开箱，对话里一句话补完 |
| **能力安装** | 手动丢文件 / 填 stdio 命令 | 自动发现 + 一句话"给我装 XX" |
| **清理删除** | 手动删会话/清缓存/卸技能 | 系统自治（归档+配额），用户无感 |
| **审批打断** | 每次高危弹窗 + 倒计时 | 信任分级，只在"延迟成本 > 打扰成本"时打断 |
| **更新运维** | 手动重装 + sidecar 崩了手动重启 | 后台静默更新 + watchdog 自愈 |
| **引导** | 空状态丢几个 chip，无向导 | 自学习式：进来就能问，能力随用随现 |

**最大摩擦源（子 agent 确认）**：首次启动必须先过"Provider + API Key + 默认模型"三道门槛；叠加每次危险工具调用的审批弹窗持续打断。两者共同构成"开箱即用"的最大障碍。本方案把这两点列为最高优先级（见 §4.1、§4.5）。

**铁律**：对话简化 ≠ 移除控制权。永远保留"逃生舱"——一个低频但存在的硬开关，保证极客用户仍能完全掌控。这是对抗式审查（§6）的结论。

## 1. 问题定义：当前用户摩擦地图

基于代码探索（medium 彻底度），当前所有"用户必须手动操作"的入口分 5 类：

### 1.1 配置类（手动改选项 / 手改文件）
- **模型 + Provider + API Key**（`SettingsView.tsx` 模型 tab）：要从 16+ 内置 provider 里选、粘贴 Key、点"获取模型"，或手填自定义 provider。**不设默认模型连对话都进不去**（有 mismatch banner）。首次最重。
- **画像 Persona**（`PersonaView`）：手动填，简单。
- **后端 / Python 运行时**（`BackendTab` + `PythonRuntimePanel`）：需手动开 TickLoop；Python 须用户自装或手填 override 路径。中等。
- **高级参数**（`AdvancedTab` 6 个数值：压缩/子 agent）：保存后需重启。简单但打断。
- **手改 `config.yaml`**（`hermix-config/src/config.rs`）：`tools` 白名单、`terminal.backend`(docker/ssh/modal/容器)、`proxy`、`approval`、`skills` 启停、`mcp_servers`、`compaction` 阈值、`smart_model_routing`、`permission_profile` 等只能改 yaml。专家级、繁琐。

### 1.2 安装 / 接入类
- **技能 Skills**（`PluginsView.tsx` 技能 tab）：**无应用内安装按钮**；官方市场 18 个 seed 只读展示（开关禁用、"待实装"）。装技能 = 手动把 `SKILL.md` 丢进 `~/.hermix/skills/<category>/<name>/`（见 `hermix-skills/src/store.rs`）。繁琐。
- **MCP 服务器**（`ConnectorsTab`）：手动填 stdio(`command`/`args`) 或 http(`url`)+环境变量，依赖 `npx/uvx`；可"恢复官方示例"5 个。中等~繁琐。
- **插件 / 工具集**：同文件另两 tab，**后端自动发现，开关即启用**。简单（已是好样板）。
- **专家 Experts**（`AgentsView.tsx`）：手动建表单 或 "AI 生成"向导；内置专家 `data/builtinExperts.ts` 只读可选。中等。

### 1.3 删除 / 清理类
- **删除会话**（`Sidebar.tsx` → `window.confirm` 不可撤销）：简单。
- **解散群聊 / 卸载技能 / 删 MCP / 删专家**：物理删文件或确认框。中等、多数不可撤销。
- **删除记忆**：经 `memory` 工具对话触发，无独立面板。中等。
- **清理缓存 / 本地数据**：仅 `hermix-tools` 的 `storage_analyzer` 工具，**无统一清理 UI**。繁琐。

### 1.4 运维类
- **更新升级**：无自动更新 UI（`release/` 手动重装）。繁琐。
- **配置迁移**（`migration.rs`）：启动探测旧 `~/.hermes`，弹"是否导入"对话框，或设环境变量。中等。
- **修复 / 重装依赖**：`cargo`/`build-tauri.bat`，无自愈。繁琐。
- **首次启动引导 onboarding**：**基本无正式向导**，仅 `ChatView` 空状态让用户从 composer chips 选专家/workspace。用户不知从何下手。复杂。
- **Sidecar 崩溃**：文档 P0-4 指无 watchdog，崩溃需手动重启应用。

### 1.5 审批 / 权限类
- **工具调用审批**（`InlineApprovalCard.tsx` + `PendingApprovalToast.tsx`）：每次高危操作（terminal/write_file/patch/storage_clean/cua/browser 等）弹"允许/拒绝"并**带倒计时**（超时自动取消/拒绝）。频繁打断。繁琐。
- **权限档案 / 免审批**：`permission_profile` 与 `ApprovalConfig` 持久化到 yaml；要常驻"Always Allow"需手改 yaml。中等~繁琐。

**量化摩擦**：
- 进入第一次有效对话前，平均要跨 **3 个设置页 + 粘贴 1 个密钥**；
- 一个典型工作流（写代码→跑命令→改文件）会触发 **3~8 次审批弹窗**；
- 想扩展能力（装技能/连 MCP）要 **离开对话去翻插件页 + 手改文件系统**。

## 2. 业界思想调研（提炼可借鉴的点）

### 2.1 约定优于配置 / 固执己见软件（Convention over Configuration）
- 来源：Ruby on Rails（DHH, 2004）、Spring Boot、Maven。核心——**系统内置合理默认，只有当默认不满足时才手动覆盖**。"好的约定让你忘记配置的存在。"
- 反面教材：Salesforce 式的"无限可配置"最终变成实施噩梦；Shopify 式"固执己见"直接铺好 happy path，85% 工作流开箱即用，只剩 15% 需要定制。
- **借鉴**：把所有 `config.yaml` 字段先给"经过实战的默认值"，仅暴露少量"真需要个性化"的旋钮；且旋钮也用对话调，不暴露文件。

### 2.2 渐进式披露 + 自学习式 onboarding
- 数据：线性产品 tour 完成率 **53%**，上下文触发的渐进式披露 **75%**（+30% 付费转化，Userpilot 2025）。人工作记忆一次约 **4 项**。
- 三层模型：L1 首会话只给"单一引导动作"；L2 首周随探索浮现次要功能；L3 首月给幂用户高级能力。
- **Onboarding 不是教程，是守护者**（commonux.org）：产品自己会教自己，不打断、不讲座。空状态即软起点。
- **借鉴**：Day1 只给对话；Week1 浮现"你可以让我连飞书/装技能"；Month1 浮现高级参数。

### 2.3 对话替代表单（FreedomTrack 案例）
- 把多步表单换成 AI 对话：自然语言解析去除摩擦（"我月入 12 万" → 自动建记录）；概念在上下文里教（"宽基指数通常 2% 分红"）；流程随用户走（开口先说负债就从负债开始）；**可跳过且已建记录保留**；收集到的数据反而更丰富。
- 关键前提：**清晰的数据模型映射到工具定义**——对话采集什么，由后端 tool schema 决定。
- **借鉴**：首次引导、配置修改、技能安装，全部用"对话 + tool 写回"实现，而不是表单/设置页。

### 2.4 Chat-first 架构（Hermes desktop 文章）
- Desktop-client-first 的理由：数据隐私（流可控在本地）、系统集成（通知/快捷键/托盘/本地文件）、专注克制（Simple-first）。
- 架构取舍：会话状态管理成核心；**复杂功能"按需加载"**（技能/渠道/任务管理懒加载，只有点导航才加载）；管理页与聊天主界面实时同步状态。
- **借鉴**：保留"按需加载"工程优势，但把"管理页"从用户视线里移走——它仍存在，只是默认折叠，由对话触发。

### 2.5 AI-Native Desktop 四 Shift（LinkedIn 设计领导视角）
1. **Intent Over Clicks**——你说目标，系统跑流程。
2. **Proactive Over Reactive**——软件预判需求，在摩擦发生前止住。
3. **Unified Flow Over Silos**——agent 连通日历/文档/消息整套工具。
4. **Interactions Over Interfaces**——可信对话取代死板界面。
- 构建块：跨应用 agent（细粒度权限）、情境感知（大上下文+本地数据）、**人类级可解释性 + 撤销**、**设计良好的打断**（仅当"延迟成本 > 打扰成本"时升级）。
- **借鉴**：§4.5 审批重设计、§4.7 主动式 agent 直接来自这里。

### 2.6 工作台"收件箱"隐喻 + 后台/主动式 agent（XClaw / Ona）
- XClaw：多并行 agent 同窗；用"收件箱"组织任务（可标记/归档/稍后），而非聊天列表。
- Ona 重构：对话即工作区，界面安静，上下文共享，agent 像"和你并肩在战壕里"；减少噪点；支持后台并行 agent。
- **借鉴**：会话不强制删，改为"归档=收件箱"；长任务后台跑，完成用系统通知提醒。

### 2.7 小结：可落地设计原则清单
> 零配置启动 · 对话即唯一入口 · 能力自动发现 · 清理自治 · 审批是护栏不是路障 · 渐进式自学习 · 可解释+可撤销 · 主动替代被动 · 失败自愈

## 3. 设计原则（从本项目第一性约束推导）

不是"别人这么做所以我做"，而是从 Hermix 的物理/架构约束推出：

| 约束（物理/架构事实） | 推导出的原则 |
|---|---|
| 桌面端、数据流主要在本地、用户打开只为"把活交给对话" | **对话是唯一入口**：任何操作都该能从一句话开始 |
| 能力（技能/MCP/工具集）由后端自动发现已可行（插件页已是好样板） | **自动发现 > 手动安装**：装东西不该是用户的活 |
| 首次无内置模型、必须外部 API → 这是真实门槛 | **默认即可用**：给 fallback 链 + 受限模式，绝不挡在对话前 |
| 审批是安全护栏，但每次弹窗打断 flow | **护栏不是路障**：按信任分级，只在高成本延迟时打断 |
| 本地有文件系统/缓存会无限增长 | **清理自治**：LRU+配额，用户无感 |
| 桌面有系统通知/托盘/快捷键 | **主动替代被动**：完成提醒、主动提议 |
| 任何自动操作都可能错 | **永远可解释 + 可撤销**：每次执行给一句理由 + 一个 undo |

**核心信念（来自 Opinionated Software）**：把"重复且可预测的选择"变成隐式默认，只暴露"真正需要个性化"的部分。Hermix 应铺好 85% 用户的 happy path。

## 4. 方案设计（分模块，详尽）

### 4.1 零配置启动（消灭第一个摩擦源，最高优先级）
**今天**：`SettingsView` 模型 tab 强制选 provider + 贴 key + 选默认模型，否则 mismatch banner 挡门。
**目标**：打开即进对话。

- **默认模型 fallback 链**：启动时按"本地可用性"探测，排序候选（如：环境变量里已有的 key > 上次用过的 > 内置免费/试用端点 > 本地轻量模型）。自动选第一个可用作默认，**不弹 banner**。
- **受限模式（关键逃生）**：若完全无任何可用模型，仍可进对话，但 agent 回复"我目前没有可用的模型，你贴一个 Key 我就满血；或者先用本地轻量模式试试"。**绝不白屏/挡门**。
- **对话式首次引导**（取代表单）：进来后 agent 用自然语言问——"想用哪个模型？我有 Claude / GPT / 本地 Ollama，你贴个 key 就行，或者先试用本地模式"。用户回一句，agent 调 `set_provider` tool 写回，**不跳设置页**。
- **Key 存密钥库**：贴的 key 进系统凭据库（Windows Credential Manager / keyring），不落明文 yaml。
- **度量目标**：首启动 → 首次有效对话 **< 30 秒**（理想），最差 < 3 分钟。

### 4.2 配置归零（消灭手改 yaml）
**今天**：`config.yaml` 里 `tools` 白名单、`terminal.backend`、`proxy`、`approval`、`skills`、`mcp_servers`、`compaction`、`smart_model_routing`、`permission_profile` 只能手改文件。
**目标**：所有字段有"实战默认"，且**对话可调**。

- 给每个 yaml 字段一个 safe default（如 `terminal.backend` 默认 `local`，`compaction` 默认中档，`smart_model_routing` 默认开）。
- 用户想改 → 对话："把 terminal 后端换成 docker 容器 X" → agent 调 `update_config` tool 改对应字段并热加载（**免重启**，借鉴 AdvancedTab 现在要重启的痛点）。
- **设置页大幅瘦身**：只保留"视觉偏好"（主题/字号）等纯前端项；其余全部对话化。设置页从"必需"降级为"高级逃生舱"。
- **逃生舱**：仍保留"导出/编辑原始 config"入口给极客，但默认隐藏。

### 4.3 安装 / 接入自动化（消灭手动丢文件）
**今天**：装技能=手丢 `SKILL.md`；连 MCP=手填 stdio/http；专家=手建表单。
**目标**：自动发现 + 一句话。

- **技能 Marketplace 对话化**：把只读的 18 个 seed 变成可一键启用；用户说"给我装个 XX 技能" → agent 调 `install_skill` tool 从内置/可信源拉取，**不再手丢文件**。
- **能力自动推荐（Proactive）**：agent 读对话上下文，预判你需要的能力并轻提示——"你似乎在做 PDF 处理，要我装个 pdf 技能吗？"（借鉴 §2.5 主动式）。用户点一下或回"好"即装。
- **MCP 对话式接入**："连一下我的飞书" → agent 引导填 token（存密钥库），调 `add_mcp_server` tool 写回。**把 `npx/uvx` 命令细节藏起来**。
- **专家从"手建"到"说一句就能造"**：内置专家默认全开可选；新建专家用"AI 生成"向导（已有）进一步对话化，去掉空白表单。
- **插件/工具集**：已是自动发现+开关的好样板，保留 toggle 但**默认全启**，减少决策。

### 4.4 删除 / 清理自治（消灭手动清理）
**今天**：手动删会话、清缓存（无 UI）、卸技能（物理删）。
**目标**：系统自治，用户无感。

- **缓存/本地数据自治**：后端按 LRU + 配额自动回收（借鉴 `storage_analyzer` 的能力，但做成定时静默任务，不暴露 UI）。用户永远不必"清理缓存"。
- **会话不强制删，改为归档（收件箱隐喻）**：参考 XClaw/Ona。旧会话自动归档而非删除；用户想找时"在收件箱里"。误归档可恢复。
- **卸载对话化**："移除飞书连接" → agent 调 `remove_mcp_server`，带一句极简确认（非恐怖确认框），并保留"随时重连"能力。
- **记忆对话式管理**：延续现有 `memory` 工具，不单独面板。

### 4.5 审批护栏重设计（消灭持续打断）
**今天**：`InlineApprovalCard` 每次高危弹窗 + 倒计时，疲劳。
**目标**：信任分级，只在"延迟成本 > 打扰成本"时打断。

- **三级信任模型**：
  - L0 陌生/高危且不可逆（如 `rm -rf`、对外发邮件）→ **问**，给一句解释 + 倒计时（保留现有护栏）。
  - L1 已授权类别（用户曾说"这类都允许"）→ **静默执行 + 对话里记一笔**（"已帮你跑完命令"），不打断。
  - L2 低危本地操作（读文件、本地搜索）→ **默认执行**，连记录都极简。
- **自然语言设免批**："以后这类文件操作都直接做" → agent 调 `set_permission_profile` 写回（取代手改 yaml 的 Always Allow）。
- **每次执行给可解释性 + 撤销**：高危操作前一句理由（"我要删 /tmp 下 3 个缓存文件，因为…"），执行后给 undo 入口（借鉴 §2.5 构建块）。
- **设计良好的打断**：仅当"延迟成本 > 打扰成本"升级打断；批量操作合并为一次确认（"接下来 5 步我都要改文件，允许吗？"）。

### 4.6 更新 / 运维自愈（消灭手动重装）
**今天**：无自动更新、sidecar 崩了手动重启、迁移要对话框、依赖无自愈。
**目标**：后台静默 + 自愈。

- **自动更新**：后台检测 + 静默下载，完成给**可选重启提示**（不打断当前长任务）。
- **Sidecar watchdog**：检测 sidecar 崩溃自动重启（补 P0-4），用户无感。
- **配置迁移无声化**：探测到旧 `~/.hermes` 自动后台导入，仅首次给一行"已从旧版导入"，不弹三选一对话框。
- **依赖自修复**：启动自检，缺失依赖自动拉取/修复。

### 4.7 主动式 / 后台 agent（从被动到主动）
**今天**：对话是纯被动问答。
**目标**：Intent Over Clicks + Proactive Over Reactive。

- **完成提醒**：长任务后台跑完用系统通知（已有桌面集成能力）提醒，不占对话。
- **主动提议**：基于本地数据/历史，"你上周的报表还没整理，要我帮你吗？"——参照 §2.5。
- **收件箱式任务管理**：并行任务进"收件箱"，可标记/归档/稍后，而非散落聊天列表（XClaw/Ona）。

### 4.8 Onboarding 重设计（自学习，不教学）
**今天**：空状态丢几个 chip，无向导，用户迷茫。
**目标**：进来就能问，能力随用随现。

- **空状态即入口**：保留 composer chips，但 chips 是"示例问题"而非"设置导航"（"帮我写周报""整理这个文件夹"）。
- **首动作即价值**：进来就能问一个问题并得到答案（哪怕受限模式也先给结果）。
- **渐进式披露三层**（§2.2 数据支撑）：
  - Day1：只给对话。
  - Week1：浮现"你可以让我连飞书 / 装技能"（随对话上下文）。
  - Month1：浮现高级参数（压缩/子 agent 档位），且仅对高频用户。
- **可跳过 + 状态保留**：任何引导中途退出，已采集信息不丢（§2.3）。

## 6. 对抗式审查（This breaks when…）

> 每个方案必须回答"在什么场景下会崩"。不能枚举失败模式的方案 = 不完整。

**6.1 零配置但用户要强隐私**
- 崩法：默认 fallback 选了"云模型"，用户其实要全本地。
- 缓解：受限模式 + 首次对话明确问"云还是本地"，默认走本地优先；隐私相关默认保守。

**6.2 自动安装技能 → 供应链/安全风险**
- 崩法：自动推荐装了恶意技能。
- 缓解：技能仅来自**可信源白名单**；自动推荐只"提议"不"自作主张装"；装前给来源+权限清单。

**6.3 审批降级 → 误删/误执行高危**
- 崩法：L1 免批后被 agent 误执行 `rm -rf`。
- 缓解：不可逆操作**永远**在 L0（必问）；免批只覆盖"可逆/低危"类别；所有执行留 undo。

**6.4 对话式配置 → 表达不清 / agent 误解**
- 崩法：用户说"把后端改成那个" agent 改错字段。
- 缓解：改前回显"我将把 terminal.backend 改为 docker，对吗？"；保留逃生舱可手改；变更可撤销。

**6.5 自治清理 → 误删用户想要的数据**
- 崩法：LRU 把用户还要的会话/文件回收了。
- 缓解：只回收明确"缓存/临时"类；用户数据（会话/记忆/文件）只归档不删；配额阈值保守 + 可回收站。

**6.6 主动式 agent → 打扰过度（反噬）**
- 崩法：每天弹 10 条"要我帮你吗"变成骚扰。
- 缓解：主动提议有频控 + 可一键"别主动了"；默认低频；基于强信号才提议。

**6.7 自动更新 → 破坏进行中的长任务**
- 崩法：后台更新强制重启，丢了用户跑了一半的 agent 任务。
- 缓解：更新只"下载"，重启**等用户空闲/显式确认**；长任务运行时推迟重启。

**总原则（逃生舱）**：对话简化是默认层；**永远保留一个低频硬开关/原始 config 入口**，让极客用户仍能完全掌控。简化 ≠ 剥夺控制权。

## 7. 阶段路线（不开发，只规划；每阶段可独立交付）

- **Phase 0 — 摩擦度量**：埋点（首启动到首对话时长、设置页打开率、审批弹窗日均次数、技能安装流失）。没有度量就没有收敛。
- **Phase 1 — 零配置启动 + 对话式 onboarding（最高 ROI）**：解决 §1 最大摩擦源。开箱即进对话 + 受限模式 + 对话引导补 key。
- **Phase 2 — 审批护栏重设计**：三级信任 + 合并确认 + undo。直接砍掉持续打断。
- **Phase 3 — 安装/接入对话化 + 自动发现**：技能 Marketplace 一键、MCP 对话接入、专家对话造、能力自动推荐。
- **Phase 4 — 清理/运维自治 + 主动式 agent**：LRU 自治、归档收件箱、自动更新、watchdog、主动提议、系统通知。

> 依赖关系：Phase 1 独立价值最大；Phase 2 独立；Phase 3/4 可并行推进。

## 9. 结论

Hermix 的定位本来就应该是"**对话即操作系统**"——用户只管说要什么，配置/安装/删除/审批/更新这些"计算机的脏活"由系统在自己看不见的地方做完。业界共识很清晰：**约定优于配置、对话替代表单、渐进式自学习、护栏而非路障、可解释且可撤销、主动而非被动**。把这些思想映射到本项目已存在的工程资产（自动发现的插件页、对话触发的 memory 工具、桌面通知集成）上，大部分改造是"把已有的能力从设置页搬进对话"，而非从零造。

最高杠杆的两刀：**零配置启动**（砍掉进门收费站）和**审批护栏重设计**（砍掉持续打断）。先把这两刀做了，开箱体验会质的飞跃；其余按 Phase 3/4 渐次归零。

**一句话收尾**：让用户忘记"配置"这个词的存在——这就是成功。
