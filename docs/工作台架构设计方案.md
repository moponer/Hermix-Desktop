# 工作台（Workspace）架构设计方案

> 版本：v0.3（实施回写） · 日期：2026-08-27 · 状态：M0–M6 已实施（§13.1 落地对照）
>
> 目标：为 Hermix Desktop 增加「对话式自定义工作台」能力——用户通过对话任意调整工作台布局、展示项目、实现管理能力（人员管理、车辆管理、安全台账等），支持多工作台 Tab 隔离、LLM 自动建设、数据存储、条件/定时提醒、总结分析、远程部署与协作。
>
> v0.3 变更：新增 §13.1 实施落地状态（M0–M6 逐项对照，含与原方案的偏差标注）。
>
> v0.2 变更：新增 §16（超出 CRUD 的自定义代码）与 §17（二轮评审补充 12 项缺口）。
>
> 设计口径遵循 AGENTS.md：**第一性原理**、**对抗性评审**、**零上下文膨胀**、**六步决策阶梯**（YAGNI → 标准库 → 原生平台 → 现有依赖 → 单行代码 → 最小实现）。

## 1. 背景与目标

### 1.1 一句话定义

让用户用自然语言说「帮我建一个车辆管理工作台」，把数据（CSV/Excel/粘贴文本/文件）丢进对话框，LLM 自动建议管理模块与界面设计，用户确认后**自动完成建设**（建表、导入数据、生成 UI、注册数据工具、配置提醒），完成后提醒用户测试；有问题继续对话迭代。用户可创建**多个工作台**，互不影响，通过 **Tab 切换**。

### 1.2 核心诉求拆解

| 诉求 | 含义 | 架构含义 |
|---|---|---|
| 对话任意调整布局 | 布局即数据，可被 LLM 读写 | 布局用声明式 JSON，渲染器通用化 |
| 展示项目 + 管理能力 | 台账类 CRUD + 仪表盘展示 | 数据表 + 视图 + 仪表盘组件 |
| 用户自定义开发 | 前端界面 + 功能实现 | Schema 驱动为主 + 代码逃生门 |
| 多工作台互不影响 | 隔离 | 每工作台独立数据 + 独立定义 |
| 数据丢入对话框 → LLM 建议 | 自动建设 | LLM 生成管线 + 确认 + 自动执行 |
| 一次性完成不报错 | 交付质量 | Schema 校验 + 预览 + 可回滚 |
| 远程部署 / 一键使用 / 协作 | 同步 | 本地优先 + 可移植包 + 预留同步层 |
| 条件提醒 / 定时提醒 / 总结分析 | 自动化 | 确定性走 SQL+调度，语义走 LLM 定时任务 |

### 1.3 设计原则（从 AGENTS.md 推导）

1. **零上下文膨胀是核心约束**：任何可能膨胀上下文的操作（大文件解析、大表读取、多 URL 提取）必须走 sub-agent 隔离。工作台的数据摄入、LLM 分析、定时总结全部遵循。
2. **LLM 永远通过工具操作数据，不直接写 SQL**：保证数据准确性、可审计、可校验。
3. **确定性逻辑不浪费 LLM**：条件提醒、数据校验、统计聚合用 SQL + 调度器；只有语义综合（周报、异常发现、自然语言查询）才用 LLM。
4. **数据模型从第一天 sync-friendly**：行级 UUID + `updated_at` + `updated_by`，为远程协作预留。
5. **不造轮子**：复用项目已有的 rusqlite、hermix-cron、hermix-automation、hermix-tools、acui 协议；前端复用 React 19 + Tailwind 4 + 现有 SpreadsheetView。

## 2. 现状盘点（项目已有能力）

调研结论：Hermix Desktop 已具备本方案 60% 以上的基础设施，工作台是**新概念**，与现有「工作区（目录沙箱）」和「自定义应用（独立 exe）」均不同，但可大量复用。

### 2.1 可直接复用的能力

| 现有能力 | 位置 | 复用点 |
|---|---|---|
| SQLite（rusqlite 0.32 bundled） | workspace 依赖，7 个 crate 已用 | 工作台数据存储 |
| 调度器（cron + RRULE） | `hermix-cron` | 定时提醒 / 定时分析触发 |
| 自动化引擎（automations / runtime_state / runs 三表） | `hermix-automation` | 提醒规则 + LLM 定时任务载体 |
| 工具注册表 + 派发 + 审批引擎 | `hermix-tools` | 注册 `workspace_*` 数据工具族 |
| Agent Loop + sub-agent 隔离 | `hermix-agent` | LLM 生成管线、数据摄入隔离 |
| ACUI 协议（show/update/hide 卡片） | `acui/` + `hermix_core::AcuiDirective` | 提案确认卡、建设进度卡、完成提醒卡 |
| 表格组件（虚拟滚动、表头冻结、搜索、CSV 导出） | `SpreadsheetView.tsx` | 表格视图基础（需改造为 Schema 驱动） |
| 自定义应用机制（vanilla HTML/JS → 独立 exe） | `custom-apps` + hx-shell | 工作台「高级自定义」逃生门 |
| WS + HTTP 传输 | `hermix-transport` / `hermix-server` | 工作台 API + 实时通知 |

### 2.2 关键差异澄清

- **现有「工作区」(useWorkspaces)**：是目录别名，用于限制对话读写范围（沙箱边界）。**不是**本方案的工作台。
- **现有「自定义应用」(custom-apps)**：LLM 写 vanilla 网页工程 → 打包成**独立 exe**，每个 app 一个 WebView2 进程。适合独立工具类。
- **本方案「工作台」**：Schema 驱动的**进程内多模块**空间，数据在后端 SQLite，适合台账/管理类。二者互补，关系见 §12。

### 2.3 前端依赖缺口

现有前端依赖（React 19 / Tailwind 4 / lucide-react / papaparse / xlsx / react-markdown）**缺少**：图表库、表格数据层（SpreadsheetView 是自研、面向只读预览）、拖拽布局库、看板/日历组件。缺口清单见 §4.2。

## 3. 市场调研结论（开源方案）

调研了四个方向的开源生态，结论如下（详细清单见附录）。

### 3.1 低代码内部工具平台（Appsmith / ToolJet / Budibase / NocoDB / Baserow）

- **共性架构**：数据源（DB）→ 应用定义（schema/JSON）→ 通用渲染器（表格/表单/看板/日历/图表）→ 自动化（规则/定时）。
- **关键启示**：这类平台的核心不是"写代码"，而是**「Schema 即应用」**——LLM 只需产出正确的声明式定义，通用渲染器负责呈现。这正是工作台的第一路径。
- **差异**：Appsmith 偏开发者（JS 扩展）、Budibase 偏简单 CRUD、ToolJet 偏企业治理、NocoDB 偏"给数据库套表格 UI"、Baserow 偏团队协作。**没有一家**提供"对话式 LLM 从零建工作台 + 本地优先桌面端"的形态——这是 Hermix 的差异化机会。

### 3.2 LLM 生成应用（Bolt.new / Lovable / v0）

- **共性架构**（来自 Beam 对 Lovable/Bolt 的架构拆解）：`planner 拆任务 → 代码生成 agent 改文件 → 沙箱跑应用 → 错误回传 → 迭代循环 → 部署`。
- **关键启示**：
  1. **沙箱 + 预览 + 错误回传闭环**是"一次性交付不报错"的唯一可行路径——LLM 先出草案，跑起来看错误，修到能跑，再交付。
  2. 生产质量取决于**显式约束**（数据库 schema、权限边界、后台任务、回滚），不能指望模型从 prompt 推断。
  3. Bolt 默认 React + Vite + Tailwind，Lovable 默认 Supabase（数据库/鉴权/存储/边缘函数一体）。
- **对本方案的取舍**：Bolt/Lovable 是"代码生成"路线，自由但重（需沙箱、编译、部署）。工作台 90% 场景是台账 CRUD + 仪表盘，**Schema 生成路线**更轻、更稳、更易同步。代码生成作为逃生门（§12）。

### 3.3 本地优先数据 + 同步（ElectricSQL / PowerSync / Zero / Yjs / Automerge）

- **共识**：2026 年本地优先（local-first）已是主流——本地读写零延迟、离线可用、CRDT/同步引擎自动合并。
- **引擎对比**：ElectricSQL（Postgres→客户端 SQLite，shape 订阅，LWW）、PowerSync（最成熟，自定义冲突解决，SQLite 客户端）、Zero（最现代，客户端响应式缓存，IndexedDB）、Yjs/Automerge（文档型 CRDT，协作编辑器主力）。
- **关键启示**：桌面端本地 SQLite + 可选同步服务器是正解。**数据模型 sync-friendly（行级时间戳 + UUID）必须从第一天设计**，否则后期接同步引擎要重写数据层。

### 3.4 布局 / 表格 / 图表引擎

- **布局**：`react-grid-layout`（React 原生、dashboard 场景 gold standard、布局可序列化）vs `Gridstack.js`（框架无关）。**React 项目选 react-grid-layout**。
- **表格**：TanStack Table（headless、虚拟滚动、性能强）vs AG Grid（重、功能全）。轻量选 TanStack Table。
- **图表**：ECharts（功能全、按需引入、中文生态）vs Recharts（React 原生、轻量）。仪表盘/台账场景推荐 ECharts。
- **看板/日历**：无必要不引重型库——看板用 dnd-kit + 自研轻量组件；日历用原生 `<input type="date">` + 自研月视图（六步阶梯第 3 条：原生平台优先）。

## 4. 核心设计决策与技术栈

### 4.1 最高层决策：Schema 驱动为主，代码生成为逃生门

这是整个方案的**第一性决策**。工作台的建设有两条路线：

| 路线 | 原理 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **A. Schema 驱动（主路径）** | LLM 产出声明式 `WorkspaceSchema`（表结构/视图/仪表盘/提醒），通用渲染器呈现，数据走后端 SQLite | 安全（无代码执行）、快、稳、易校验、易同步、运行开销小 | 受组件目录限制，做不到"任意" | 台账/管理类（人员/车辆/安全台账）≈ 90% |
| **B. 代码生成（逃生门）** | LLM 写 vanilla HTML/JS 网页工程，跑在沙箱/独立 exe | 无限表达力 | 需沙箱/编译/迭代闭环，重，难同步 | 独立工具类（计算器/PDF 查看器/特殊交互） |

**决策：A 为主，B 为逃生门**。依据：
- 六步阶梯（YAGNI / 最小实现）：台账 CRUD + 仪表盘用 Schema 就够，不需要为 10% 的场景承担代码生成的全部复杂度。
- 对抗性评审：代码生成路线的失败面（编译错、运行时错、沙箱逃逸、数据与 UI 脱节）远大于 Schema 路线；"一次性交付不报错"只有 Schema 路线做得到。
- 现有 custom-app 机制（§12）已经覆盖了 B 路线的独立工具场景，工作台无需重复造。

### 4.2 技术栈选型

**前端（全部复用/新增于 apps/desktop-tauri）：**

| 层 | 选型 | 理由 |
|---|---|---|
| 框架 | React 19 + Tailwind 4 + Vite | 已有，不换 |
| 布局引擎 | `react-grid-layout` | React 原生、布局可序列化、dashboard 场景 gold standard（调研结论） |
| 表格数据层 | TanStack Table v8 | headless、虚拟滚动、类型安全；替代 SpreadsheetView 的只读预览定位 |
| 表格 UI | 复用/改造 SpreadsheetView 视觉 | 表头冻结、行虚拟化、搜索、CSV 导出已实现 |
| 图表 | ECharts（按需引入） | 仪表盘/台账图表类型全（折线/柱状/饼/漏斗/甘特）、中文生态 |
| 看板 | dnd-kit + 自研轻量看板 | 不引重型库（六步阶梯） |
| 日历 | 原生 `<input type="date">` + 自研月视图 | 原生平台优先 |
| 状态 | React 自带 + zustand（可选） | 工作台多 Tab 共享数据，zstore 轻量；如现有状态方案够用则不引 |
| 图标 | lucide-react | 已有 |

**后端（全部复用/新增于 crates/）：**

| 层 | 选型 | 理由 |
|---|---|---|
| 数据存储 | rusqlite 0.32（bundled） | 已是 workspace 依赖，7 个 crate 在用 |
| 调度 | `hermix-cron` + `hermix-automation` | 已有，直接复用 |
| 工具注册 | `hermix-tools` 注册表 | 已有，注册 `workspace_*` 工具族 |
| 生成管线 | `hermix-agent` agent loop + sub-agent 隔离 | 已有 |
| 提案/进度 UI | `acui` 协议 | 已有，LLM→前端卡片通道 |
| 传输 | WS + HTTP（hermix-transport / hermix-server） | 已有 |
| 同步（未来） | PowerSync / ElectricSQL / Zero / Yjs | 调研结论，见 §11 |

**新增 crate 建议**：`hermix-workspace`（工作台核心：定义模型、SQLite 存储、工具族、生成管线、提醒引擎）。保持与 `hermix-tools`、`hermix-automation` 的依赖方向：`hermix-workspace` 依赖它们，不反向。

### 4.3 新增前端依赖清单（最小集）

```
react-grid-layout   # 布局
@tanstack/react-table  # 表格数据层
echarts              # 图表（按需引入）
dnd-kit              # 看板拖拽
（可选）zustand       # 轻量共享状态
```

新增依赖控制在 5 个以内，全部有明确理由，符合六步阶梯。

## 5. 概念模型

### 5.1 工作台（Workspace）

一个工作台 = 一个独立的"数字业务空间"，包含四部分：

```
Workspace (工作台)
├── 定义 workspace.json     # 元数据 + 模块列表 + 布局 + 提醒 + 权限（纯 JSON，可版本化）
├── 数据 data.sqlite        # 每工作台独立 SQLite 库（表、行、附件引用）
├── 模块 modules            # 数据表 + 视图 + 仪表盘组件
├── 自动化 automations      # 条件提醒规则 + 定时任务 + LLM 分析任务
└── 分享 sharing            # 导出/导入包、协作配置（预留）
```

### 5.2 模块（Module）

模块是工作台内的功能单元，三种类型：

| 模块类型 | 内容 | 示例 |
|---|---|---|
| **数据表** | 字段定义（类型/必填/枚举/关系）+ 行数据 | 人员表、车辆表、安全台账表 |
| **视图** | 同一数据表的不同呈现（表格/表单/看板/日历） | 车辆列表、出车登记表单、安全事件看板 |
| **仪表盘** | 统计卡 + 图表 + 列表的组合布局 | 首页总览（车辆数、临检提醒、本月出车） |

### 5.3 定义模型（WorkspaceSchema，核心数据结构）

```jsonc
{
  "schema_version": 1,
  "name": "车辆管理工作台",
  "icon": "car",
  "modules": [
    {
      "id": "vehicles",
      "type": "table",
      "name": "车辆台账",
      "fields": [
        { "id": "plate", "name": "车牌号", "type": "text", "required": true, "unique": true },
        { "id": "model", "name": "车型", "type": "text" },
        { "id": "owner", "name": "负责人", "type": "relation", "target": "personnel" },
        { "id": "inspection_date", "name": "年检日期", "type": "date" },
        { "id": "status", "name": "状态", "type": "enum", "options": ["在用", "维修", "停用"] }
      ],
      "views": [
        { "id": "list", "type": "grid", "fields": ["plate", "model", "owner", "inspection_date", "status"] },
        { "id": "form", "type": "form", "fields": ["plate", "model", "owner", "inspection_date", "status"] },
        { "id": "board", "type": "kanban", "group_by": "status" }
      ]
    },
    {
      "id": "overview",
      "type": "dashboard",
      "name": "总览",
      "widgets": [
        { "id": "w1", "type": "stat", "title": "在用车辆", "query": "count where status=在用" },
        { "id": "w2", "type": "chart", "title": "临检提醒", "query": "count where inspection_date<=+7d" }
      ]
    }
  ],
  "layout": { "overview": [ { "i": "w1", "x": 0, "y": 0, "w": 4, "h": 2 } ] },
  "automations": [
    { "id": "a1", "kind": "condition", "name": "年检临期提醒",
      "table": "vehicles",
      "condition": "inspection_date <= date('now','+7 days') and status != '停用'",
      "message": "车辆 {plate} 年检将于 {inspection_date} 到期，请安排年检。",
      "frequency": "daily" },
    { "id": "a2", "kind": "llm_summary", "name": "每周安全周报",
      "schedule": "0 9 * * 1",
      "prompt": "汇总上周安全台账事件，输出周报。",
      "output": "notify" }
  ]
}
```

### 5.4 关键设计点

- **定义与数据分离**：`workspace.json` 描述"长什么样"，`data.sqlite` 存"有什么数据"。定义可版本化、可迁移、可导出分享；数据可独立备份。
- **布局即数据**：`layout` 是 react-grid-layout 的可序列化输出，LLM 可以读写它来实现"对话调整布局"。
- **查询即字符串**：widget 的 `query` 是受控 SQL 片段（白名单校验），由后端编译执行，不暴露任意 SQL。
- **提醒规则结构化**：`condition` 是单表 WHERE 片段（参数化 + 白名单），`message` 支持 `{field}` 变量插值。

## 6. 分层架构

```
┌────────────────────────────────────────────────────────────┐
│ 前端（apps/desktop-tauri，React 19 + Tailwind 4）           │
│  ┌──────────────────────────────────────────────────────┐  │
│  │ 工作台 Tab 容器 WorkspaceTabs（多工作台，互不影响）      │  │
│  │  ┌────────────────────────────────────────────┐      │  │
│  │  │ Schema 渲染器 WorkspaceRenderer            │      │  │
│  │  │  ├─ TableView（TanStack + 表格 UI）          │      │  │
│  │  │  ├─ FormView / KanbanView / CalendarView   │      │  │
│  │  │  ├─ DashboardWidgets（Stat/Chart/List）     │      │  │
│  │  │  └─ react-grid-layout 布局容器              │      │  │
│  │  └────────────────────────────────────────────┘      │  │
│  │  提醒中心 NotificationCenter（WS 推送 → Toast/角标）   │  │
│  └──────────────────────────────────────────────────────┘  │
├────────────────────────────────────────────────────────────┤
│ 传输层：WS（实时通知/ACUI 卡）+ HTTP REST（CRUD/查询）       │
├────────────────────────────────────────────────────────────┤
│ 后端（crates/hermix-workspace + 复用现有 crate）            │
│  ┌──────────────────────────────────────────────────────┐  │
│  │ 定义服务 WorkspaceService                            │  │
│  │  ├─ schema CRUD + 校验 + 迁移                        │  │
│  │  ├─ 数据服务 DataService（SQLite CRUD/查询/导入）      │  │
│  │  ├─ 工具注册 ToolRegistry（workspace_* 工具族）        │  │
│  │  └─ 生成管线 BuildPipeline（LLM 生成→校验→建表→建 UI） │  │
│  ├──────────────────────────────────────────────────────┤  │
│  │ 数据层：每工作台一个 SQLite 库（rusqlite）              │  │
│  ├──────────────────────────────────────────────────────┤  │
│  │ 调度层：hermix-cron + hermix-automation              │  │

│  │  └─ LLM 定时分析任务（sub-agent 隔离读数据）            │  │
│  ├──────────────────────────────────────────────────────┤  │
│  │ 同步层（预留）：导出/导入包 → 共享 → 实时同步           │  │
│  └──────────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────────┘
```

### 6.1 模块职责

| 模块 | 职责 | 关键约束 |
|---|---|---|
| `WorkspaceTabs`（前端） | 多工作台 Tab 切换、创建/删除/重命名 | 每个 Tab 独立渲染实例，数据隔离 |
| `WorkspaceRenderer`（前端） | 读 schema → 渲染视图/仪表盘；监听 WS 数据变更刷新 | 纯函数式渲染，schema 即 props |
| `WorkspaceService`（后端） | 定义 CRUD、数据 CRUD、校验、迁移 | 所有写操作过校验 + 审计 |
| `ToolRegistry`（后端） | 注册 `workspace_*` 工具给 LLM | 工具定义注入精确 schema（§9） |
| `BuildPipeline`（后端） | LLM 生成 → 校验 → 建表 → 导入 → 建 UI → 通知 | 失败可回滚（事务 + 定义快照） |
| 提醒引擎（后端） | 条件规则 tick、LLM 定时任务调度 | 确定性走 SQL，语义走 LLM（§10） |
| 同步层（预留） | 导出/导入包、协作 | 数据模型 sync-friendly（§11） |

### 6.2 数据流

- **用户操作**：前端 → HTTP REST → `WorkspaceService` → SQLite → WS 广播变更 → 前端刷新。
- **LLM 操作数据**：LLM → `workspace_*` 工具 → `ToolRegistry` 校验 → SQLite → WS 广播 → 前端刷新。
- **提醒推送**：调度器 tick → 条件命中 → WS 推通知 → 前端 `NotificationCenter` 展示。
- **对话建设**：用户丢数据 → sub-agent 解析 → LLM 生成 schema 提案 → acui 卡片 → 用户确认 → `BuildPipeline` 执行 → acui 进度卡 → 完成提醒。

## 7. LLM 对话式建设管线（核心）

### 7.1 端到端流程

```
[用户] 把数据（CSV/Excel/粘贴文本/文件）丢进对话框 + 一句话需求
   │
   ▼
[1. 数据摄入] sub-agent 隔离解析 → 抽样 → 推断字段类型（零 ctx 膨胀）
   │
   ▼
[2. 生成提案] LLM 产出 WorkspaceSchema（表/视图/仪表盘/提醒）
   │
   ▼
[3. 提案确认] acui 卡片渲染提案（可预览、可编辑）→ 用户确认/修改
   │
   ▼
[4. 自动建设] BuildPipeline：校验 schema → 建 SQLite 表 → 导入数据
   │            → 注册 workspace_* 工具 → 生成 UI → 配置提醒
   │
   ▼
[5. 完成提醒] acui 完成卡 + WS 通知："建设完成，请测试"
   │
   ▼
[6. 用户测试] 用户在工作台里增删改查、看仪表盘
   │
   ▼
[7. 迭代] 用户反馈 → LLM 增量修改 schema（新增字段/模块/提醒/布局）
```

### 7.2 数据摄入（sub-agent 隔离，防 ctx 膨胀）

- **触发**：用户在对话中丢入文件/粘贴大段数据。
- **机制**：主 agent 不直接解析大文件。派 sub-agent：
  - 读文件 → 解析（复用现有 `fileParser` / `xlsx` / `papaparse`）→ 统计行数/列数/列类型/枚举分布/空值率 → 返回**精简结论**（列名 + 推断类型 + 抽样 5 行 + 数据质量提示）。
  - 主 ctx 只拿到结论（几百 token），大文件字节不进主 ctx。
- **边界**：> 50KB / > 1500 行 / 多 sheet 一律走 sub-agent（AGENTS.md 零膨胀规则）。

### 7.3 生成提案（LLM 产出 Schema）

- **输入**：数据摄入结论 + 用户一句话需求 + 现有组件目录清单（让 LLM 知道能用什么视图/组件）。
- **输出**：严格 JSON 的 `WorkspaceSchema`（§5.3），用 JSON Schema 约束 + few-shot 示例。
- **决策点**（LLM 拍板）：
  - 哪些列是主键/唯一/必填/枚举/关系；
  - 建哪些视图（表格/表单/看板/日历）；
  - 仪表盘放哪些统计卡/图表；
  - 建议哪些提醒规则（条件 + 定时）；
  - 是否需要关系表（如人员 ↔ 车辆）。
- **护栏**：字段类型白名单、表名/字段名标识符安全（防注入）、视图引用字段必须存在。

### 7.4 提案确认（acui 卡片）

- 复用现有 `acui` 协议：`StreamEvent::Acui` 推 `show` 卡。
- 卡片内容：schema 预览（表格结构树 + 视图缩略 + 提醒规则列表）+ 「确认建设 / 修改 / 取消」按钮。
- 用户修改：可对话式改（"把年检日期改成必填"）→ LLM 增量改 schema → 重新渲染卡片。
- **确认即契约**：用户确认后，schema 快照存为定义 v1，后续建设以此为准。

### 7.5 自动建设（BuildPipeline，一次性交付的关键）

建设必须**原子、可回滚、可重试**：

```
1. 校验：schema 过 JSON Schema + 业务规则校验（字段/视图/提醒引用完整性）
2. 建表：事务内建 SQLite 表（含索引、唯一约束、外键）
3. 导入：分批导入数据（每批 500 行，进度经 acui 更新卡回传）
4. 注册工具：为该表生成 workspace_* 工具定义（注入精确 schema）
5. 生成 UI：前端收到新 schema → WorkspaceRenderer 渲染
6. 配置提醒：把 automations 写入 hermix-automation
7. 完成：acui 完成卡 + WS 通知"建设完成，请测试"
```

- **失败处理**：任一步失败 → 事务回滚 + 删除半成品 + 报错信息回传 LLM → LLM 修正后重试。**绝不留半成品工作台**。
- **幂等**：每个建设任务有 task_id，重试不重复建表/重复导入。

### 7.6 迭代（增量修改）

- 用户后续对话（"加一个司机表"、"把状态改成枚举"、"首页加个饼图"、"每周一发周报"）→ LLM 读当前 schema → 产出 **diff**（增/改/删）→ 确认 → 执行迁移。
- 迁移策略：加字段（ALTER TABLE ADD COLUMN，带默认值）、加表（新表）、改枚举（校验存量值）、删字段（标记 deprecated，不物理删，防数据丢失）。
- 布局调整："把统计卡挪到左边" → LLM 改 `layout` JSON → react-grid-layout 热更新。

## 8. 数据存储设计

### 8.1 存储布局

```
~/.hermix/workspaces/
├── <ws_id>/
│   ├── workspace.json      # 定义（schema + 布局 + 提醒 + 权限 + 元数据）
│   ├── data.sqlite         # 该工作台全部业务数据（表 + 行）
│   ├── files/              # 附件/导入文件（按引用存储）
│   └── audit.sqlite        # 变更审计日志（谁/何时/改了什么）
├── <ws_id2>/...
└── registry.sqlite         # 主注册表：工作台列表、Tab 顺序、分享配置
```

### 8.2 存储决策

| 决策点 | 结论 | 依据（第一性/六步阶梯） |
|---|---|---|
| 每工作台独立 DB 文件 | 是 | 隔离（多工作台互不影响）、备份/导出天然（拷文件）、损坏影响面小、删除即删目录 |
| 引擎 | rusqlite 0.32（bundled） | 已是 workspace 依赖，7 个 crate 在用（现有依赖优先） |
| 定义文件 | `workspace.json` 纯 JSON | 可版本化、可 diff、可导出分享、LLM 可直接读写 |
| 行主键 | UUID（非自增） | 同步友好：多端合并不冲突（§11） |
| 行时间戳 | `created_at` / `updated_at` / `updated_by` 每表必带 | sync-friendly + 审计 + 排序 |
| 附件 | 文件系统 + 元数据引用 | 大文件不进 SQLite，备份走目录 |
| 审计 | 独立 `audit.sqlite`，所有写操作记日志 | 可追溯、可回滚、满足管理台账合规 |

### 8.3 数据表约定（自动生成）

每个业务表由 BuildPipeline 按 schema 自动生成，统一附加系统列：

```sql
CREATE TABLE vehicles (
  id           TEXT PRIMARY KEY,          -- UUID
  plate        TEXT NOT NULL UNIQUE,      -- 业务字段（来自 schema）
  model        TEXT,
  owner_id     TEXT REFERENCES personnel(id),  -- 关系字段（外键）
  inspection_date DATE,
  status       TEXT CHECK(status IN ('在用','维修','停用')),
  created_at   TEXT NOT NULL DEFAULT (datetime('now')),
  updated_at   TEXT NOT NULL DEFAULT (datetime('now')),
  updated_by   TEXT                        -- 操作来源（user/llm/automation）
);
```

- 所有查询参数化（防 SQL 注入）；标识符（表名/列名）来自 schema 白名单，不经用户/LLM 拼接。
- 关系字段存外键 ID，不存名字（§9.3）。

### 8.4 备份与恢复

- 工作台级备份 = 拷 `workspace.json` + `data.sqlite` + `files/`。
- 定义版本化：每次 schema 变更存历史版本，支持回滚到旧定义（数据保留，字段标记 deprecated）。

## 9. 对话中数据准确更新（工具族）

### 9.1 核心原则

**LLM 永远通过工具操作数据，不直接写 SQL、不直接改文件。** 这是数据准确性的根本保证——工具层做 schema 校验、参数化、审计，LLM 只负责"说什么数据"，不负责"怎么写进库"。

### 9.2 workspace_* 工具族

| 工具 | 功能 | 校验 |
|---|---|---|
| `workspace_list` | 列出所有工作台 + 模块 | — |
| `workspace_table_schema` | 获取某表的精确 schema（字段/类型/枚举/关系） | — |
| `workspace_table_query` | 查询（带过滤/排序/分页/聚合） | 列名白名单、LIMIT 上限、聚合函数白名单 |
| `workspace_table_insert` | 插入一行/多行 | JSON 严格匹配 schema（必填/类型/枚举/唯一） |
| `workspace_table_update` | 按主键更新 | 同上 + 主键存在性 |
| `workspace_table_delete` | 按主键删除 | 需审批（复用审批引擎） |
| `workspace_table_count` | 计数/聚合统计 | 同上 |
| `workspace_reminder_create` | 新增提醒规则 | 条件编译为 SQL 可测试（§10） |

### 9.3 数据准确性保障机制

1. **精确 schema 注入**：每次调用数据工具，工具定义里**动态注入该表的字段 schema**（字段名、类型、枚举选项、必填、关系目标）。LLM 看到的字段名与库中一致，杜绝"字段名猜错"。
2. **JSON 严格校验**：LLM 输出经 serde 反序列化 + 业务规则校验（枚举值、类型、必填、唯一、外键存在）后才写库；校验失败返回**精确错误**（哪个字段、期望什么），LLM 据此修正重试。
3. **关系用 ID 不用名字**：`owner` 字段 LLM 先 `workspace_table_query` 查人员表拿 `id`，再写入 `owner_id`。工具描述里明确指导这一模式，避免"写名字对不上"。
4. **查询先于写**：更新/删除前，工具强制先按条件查询确认目标行（返回行预览），防误改。
5. **审计**：所有写操作记 `audit.sqlite`（操作者 user/llm/automation、时间、变更前后）。
6. **审批**：删除、批量更新等破坏性操作走现有审批引擎（approval），用户确认后执行。

### 9.4 示例（LLM 对话中更新数据）

```
用户：把京A12345 的年检日期改成 2027-03-15，状态改成"维修"

LLM 调用链：
1. workspace_table_schema(workspace="车辆管理", table="vehicles")
   → 拿到字段定义（plate, inspection_date, status, ...）
2. workspace_table_query(workspace="车辆管理", table="vehicles", filter={plate:"京A12345"})
   → 返回该行 + id（确认目标存在）
3. workspace_table_update(workspace="车辆管理", table="vehicles", id="...",
     data={inspection_date:"2027-03-15", status:"维修"})
   → 校验通过 → 写库 → WS 广播 → 前端表格实时刷新
4. LLM 总结："已更新，年检日期改为 2027-03-15，状态改为维修。"
```

用户无需关心表结构，LLM 通过工具自动完成"定位 → 校验 → 写入 → 反馈"闭环。

## 10. 提醒与定时分析（LLM vs 非 LLM 分工）

### 10.1 分工原则

**确定性条件 → SQL + 调度器（零 LLM）；语义综合 → LLM 定时任务。** 依据：确定性逻辑用 LLM 是浪费（慢、贵、不稳定）；语义判断（总结、异常、自然语言）用 SQL 做不到。

### 10.2 能力矩阵

| 能力 | 类型 | 实现 | 是否 LLM | 示例 |
|---|---|---|---|---|
| 条件提醒 | 确定性 | SQL 查询 + tick 触发 + 通知 | 否 | 车辆年检 7 天内到期 |
| 定时提醒 | 确定性 | cron 触发 + 通知 | 否 | 每周一 9 点提醒周会 |
| 数据校验 | 确定性 | SQL 约束 / 工具校验 | 否 | 重复录入、必填缺失、枚举越界 |
| 统计聚合 | 确定性 | SQL 聚合（COUNT/SUM/GROUP BY） | 否 | 本月出车次数、各状态车辆数 |
| 周报/月报生成 | 语义 | LLM 定时任务（sub-agent 读数据 → 总结） | 是 | 每周安全周报 |
| 异常发现 | 语义 | LLM 定时任务（趋势/模式分析） | 是 | 事故率异常上升 |
| 自然语言查询 | 语义 | LLM 实时（工具查询 + 总结） | 是 | "上季度安全事件趋势" |

### 10.3 条件提醒引擎（无 LLM）

```
用户对话："当车辆年检 7 天内到期时提醒我"
  → LLM 把自然语言转成结构化规则（一次性 LLM 成本）
  → 规则存 hermix-automation：
     { kind:"condition", table:"vehicles",
       condition:"inspection_date <= date('now','+7 days') and status != '停用'",
       message:"车辆 {plate} 年检将于 {inspection_date} 到期",
       frequency:"daily" }
  → 调度器每 tick 跑 SQL 查询命中行
  → 命中 → 渲染 message（{field} 变量插值）→ WS 推前端 NotificationCenter
  → 每日去重（同一条只提醒一次，直到条件不再满足）
```

- **条件可测试**：规则创建时后端编译 SQL 并**试跑一次**，返回命中预览（"当前有 3 辆车将到期"），用户确认后才启用。
- **去重**：按 `(rule_id, row_id)` 记录已提醒，条件仍满足时不重复打扰。
- **通知渠道**：桌面 Toast / 角标 / 系统通知（复用现有通知能力）。

### 10.4 LLM 定时分析任务

- 复用 `hermix-automation`（已有 automations / runtime_state / runs 三表）：
  - 定义：`{ kind:"llm_summary", schedule:"0 9 * * 1", prompt:"汇总上周安全台账事件，输出周报", scope:"safety_ledger", output:"notify" }`
  - 触发：调度器到点 → 派发 agent 任务。
  - 执行：**sub-agent 隔离**读数据（工具查询带 LIMIT/聚合，大表不进主 ctx）→ LLM 总结 → 产出（存回某表 / 生成报告 / 推送到对话）。
- **运行记录**：每次执行记 `automation_runs`，失败重试/告警。
- **产出落点**：周报可存为工作台内"报告"模块的文档，或直接推送到对话历史。

### 10.5 触发频率与成本控制

- 条件提醒：高频 tick（如每小时）但零 LLM 成本，纯 SQL。
- LLM 分析：低频（每日/每周），且可配置模型档位（低成本模型跑例行总结）。
- 防抖：LLM 任务串行执行，失败不无限重试（最多 2 次），避免 token 失控。

## 11. 远程部署与协作（提前规划设计）

### 11.1 设计原则

**本地优先（local-first）**：数据默认在本地 SQLite，读写零延迟、离线可用；同步是**可选增强**，但**数据模型从第一天 sync-friendly**，未来接同步引擎无需重写数据层。

### 11.2 三阶段演进

| 阶段 | 能力 | 实现 | 时机 |
|---|---|---|---|
| **A. 本地面向** | 工作台 = 可移植包 `.hwx`（workspace.json + data.sqlite + files/ 打包） | 导出/导入，其他用户收到包 → 一键导入使用 | 首版 |
| **B. 共享协作** | 工作台发布到共享位置（局域网/网盘/自建服务），他人只读或可编辑打开 | 行级 `updated_at` + LWW 合并；定义文件 diff 合并 | 二期 |
| **C. 实时协作** | 多人同时编辑、实时同步 | 接同步引擎（PowerSync / ElectricSQL / Zero / Yjs） | 按需 |

### 11.3 提前设计（第一天就做）

1. **数据模型 sync-friendly**：行主键 UUID、每行 `updated_at`/`updated_by`（§8.3）。这是接任何同步引擎的前提。
2. **定义文件可移植**：`workspace.json` 是纯 JSON + 版本号，可 diff、可合并、可迁移。
3. **数据层抽象**：所有数据访问走 `WorkspaceStore` trait：
   ```rust
   trait WorkspaceStore {
       fn query(&self, ws_id, table, filter) -> Result<Rows>;
       fn insert(&self, ws_id, table, rows) -> Result<()>;
       fn update(&self, ws_id, table, id, patch) -> Result<()>;
       fn delete(&self, ws_id, table, id) -> Result<()>;
   }
   // 实现：LocalSqliteStore（首版）/ SyncedStore（未来）
   ```
   前端、工具族、提醒引擎只依赖 trait，不依赖具体实现。
4. **权限模型预留**：定义里预留 `roles: { owner/editor/viewer }` 字段，首版单用户不启用，二期启用。
5. **分享包格式 `.hwx`**：zip 归档（定义 + 数据 + 文件），带 manifest（版本、作者、校验和），导入时校验。

### 11.4 同步引擎选型（调研结论，按需接入）

| 引擎 | 特点 | 适用 |
|---|---|---|
| PowerSync | 最成熟、自定义冲突解决、SQLite 客户端 | 首选（若走 Postgres 后端） |
| ElectricSQL | Postgres→SQLite、shape 订阅、LWW | 备选 |
| Zero | 最现代、客户端响应式缓存 | 轻量备选 |
| Yjs / Automerge | 文档型 CRDT | 共享视图/文档型内容 |

**推荐路径**：Phase A 用 `.hwx` 包（零服务器）；Phase C 若需要实时协作，优先评估 PowerSync（最成熟）或 Zero（最现代）。桌面端本地 SQLite + 可选同步服务器是 2026 年本地优先的标准形态。

## 12. 与现有 custom-app 方案的关系

### 12.1 定位区分

| 维度 | 工作台（Workspace） | 自定义应用（Custom App） |
|---|---|---|
| 驱动方式 | Schema 驱动（声明式） | 代码驱动（vanilla HTML/JS） |
| 运行形态 | 主程序进程内模块 | 独立 exe（每 app 一个 WebView2 进程） |
| 数据 | 后端 SQLite，结构化、可查询、可提醒 | app 自带 sql.js / Hermix.storage，隔离 |
| 适用 | 台账/管理类（人员/车辆/安全台账） | 独立工具类（计算器/PDF 查看器/特殊交互） |
| 建设方式 | 对话 → LLM 生成 schema → 自动建表建 UI | 对话 → LLM 写网页工程 → 打包 exe |
| 运行开销 | 低（单进程，无额外 WebView2） | 较高（每 app 一个 WebView2 进程） |
| 协作/同步 | 预留（§11） | 无（独立 exe，天然离线） |

### 12.2 互补关系

- **工作台**是"业务空间"，管理台账数据；**自定义应用**是"工具"，做独立功能。
- **逃生门**：工作台遇到 Schema 表达不了的需求（特殊交互、复杂可视化、自定义算法），可在模块内**嵌入自定义应用**（复用 custom-app 产物，iframe/WebView 嵌入），或把整个工作台导出为 custom-app 独立分发。
- 两者共用：LLM 生成管线、acui 协议、审批引擎、sub-agent 隔离。

## 14. 对抗性评审（失败模式）

> 按 AGENTS.md 要求，每个方案必须枚举"在什么场景下会崩"。以下为工作台方案的失败模式与对策。

### 14.1 LLM 生成质量

| 失败模式 | 场景 | 对策 |
|---|---|---|
| Schema 字段类型推断错 | 把"备注"列推断成 date | 数据摄入返回类型置信度；提案可编辑；确认前预览 |
| 关系建模错 | 该用外键却建成重复文本列 | 提案卡展示关系图；LLM 用 schema 工具自查 |
| 视图引用不存在的字段 | 看板 group_by 一个已删字段 | schema 校验（引用完整性）在建表前拦截 |
| 提醒条件写错 | `inspection_date <= +7d` 方向反了 | 规则试跑预览（"当前命中 3 条"）用户确认 |

### 14.2 数据安全与一致性

| 失败模式 | 场景 | 对策 |
|---|---|---|
| SQL 注入 | LLM/用户输入拼接进 SQL | 全参数化 + 标识符白名单（§8.3） |
| LLM 误删数据 | 更新/删除命中错误行 | 工具强制先查询预览 + 审批引擎（§9.3） |
| 数据导入中断 | 5 万行 CSV 导一半失败 | 事务分批 + 断点续导 + 失败回滚（§7.5） |
| 多工作台数据污染 | 表名/字段名跨工作台冲突 | 每工作台独立 DB 文件（§8.2） |
| 同步冲突 | 两台机器改同一行 | LWW + 行级时间戳 + UUID（§11） |

### 14.3 上下文膨胀（零膨胀原则）

| 失败模式 | 场景 | 对策 |
|---|---|---|
| LLM 读大表 | 查询返回 10 万行进 ctx | 工具查询强制 LIMIT + 聚合优先 + sub-agent 隔离 |
| 数据摄入大文件 | 50MB xlsx 解析进主 ctx | sub-agent 隔离，主 ctx 只拿结论（§7.2） |
| 定时分析读全量 | 周报读整年台账 | sub-agent + 工具 LIMIT/聚合（§10.4） |
| 提案卡过大 | 20 个模块的 schema 全渲染 | 提案卡只展示摘要 + 可展开 |

### 14.4 运行与交付

| 失败模式 | 场景 | 对策 |
|---|---|---|
| 建设半途失败 | 建表成功导入失败 | 事务回滚 + 删半成品 + 报错回传 LLM 重试（§7.5） |
| 重复建设 | 用户双击确认 | 建设任务幂等（task_id），重试不重复建表（§7.5） |
| 前端渲染崩溃 | schema 有未知组件类型 | 渲染器对未知类型降级为"未支持组件"占位，不白屏 |
| 提醒轰炸 | 条件满足一直提醒 | 按 (rule_id,row_id) 去重，每日一次（§10.3） |
| 迁移破坏数据 | 改枚举导致存量值非法 | 改枚举前校验存量，非法值标 deprecated 不物理删（§7.6） |

### 14.5 性能与成本

| 失败模式 | 场景 | 对策 |
|---|---|---|
| 表格卡顿 | 万行表格无虚拟滚动 | TanStack + 行虚拟化（复用 SpreadsheetView 经验） |
| 图表拖慢首屏 | ECharts 全量引入 | 按需引入 + 懒加载 |
| LLM token 失控 | 定时任务高频跑 | 低频调度 + 成本模型档位 + 失败限重试（§10.5） |
| 布局渲染风暴 | react-grid-layout 频繁 setState | 布局变更 debounce + 只持久化变更 |

## 16. 超出 CRUD 的自定义代码（逃生门细化）

> 用户需求超出"增删改查 + 仪表盘"时，功能代码必须现写。本方案的原则：**能力化扩展点，而非自由代码执行**——代码只能在类型化的扩展点内写，且通过统一校验的数据桥访问数据。

### 16.1 核心原则

| 原则 | 理由 |
|---|---|
| 能力化扩展点，不开放任意代码执行 | 任意代码 = 沙箱逃逸、数据破坏、权限滥用风险；能力化扩展点有明确边界，可校验、可预览、可回滚 |
| 扩展代码一律经 WorkspaceBridge 访问数据 | 与 LLM 工具族同一套校验层，扩展代码无法绕过校验、无法直连 DB |
| 代码随工作台版本化、可打包 | 纳入 `.hwx` 包，随定义一起导出/导入/协作 |
| 代码执行前用户确认 | 信任模型：用户手写 vs LLM 生成，提交前在提案卡审查 |

### 16.2 五个扩展点（写什么 + 写哪里）

| # | 扩展点 | 写什么 | 写哪里 | 运行时 | 覆盖场景 |
|---|---|---|---|---|---|
| ① | 自定义组件 | vanilla JS Web Component（Hermix.* 原语 + WorkspaceBridge） | `~/.hermix/workspaces/<ws_id>/widgets/<id>/` | 渲染器隔离容器（iframe sandbox / web component slot） | 特殊 UI：地图、向导、特殊图表、嵌入第三方 |
| ② | 自定义动作 | vanilla JS 脚本（确定性逻辑）或 agent 任务（语义逻辑） | `~/.hermix/workspaces/<ws_id>/actions/<id>/` | 后端脚本沙箱（可选）或 sub-agent | 业务逻辑：计算、校验、批量转换、调外部 API |
| ③ | 自定义 SQL 视图 | 只读 SQL（白名单校验） | `workspace.json` 的 views 定义 | 后端 SQLite（只读） | 复杂聚合、跨表 join、计算列 |
| ④ | 自定义自动化 | 步骤编排（确定性步骤 + LLM 步骤） | `hermix-automation` | 调度器 | 多步流程、条件分支、定时任务 |
| ⑤ | 嵌入独立应用 | vanilla HTML/JS 网页工程 | custom-app 机制（独立 exe 或嵌入 bundle） | 独立 exe / iframe 嵌入 | 完整独立工具 |

### 16.3 后端脚本沙箱：新增依赖决策（现状：项目无脚本运行时）

现状盘点：`Cargo.toml` 全 workspace **无** quick-js / rquickjs / boa / deno_core / rhai / mlua 等脚本引擎。因此后端"确定性业务逻辑"的实现路径按六步阶梯排序：

1. **现有依赖优先（首版不做脚本运行时）**：
   - ③ SQL 视图——复杂聚合/跨表报表用只读 SQL 表达；
   - ② agent 任务——需要"判断/总结/生成"的语义逻辑用 sub-agent + 工具表达（复用 hermix-automation）；
   - ① 前端组件——需要 UI 交互的逻辑下沉到前端 vanilla JS（复用 custom-app 已验证的 Hermix.* 模式）。
2. **最小实现（确需后端确定性脚本时才加）**：引入 `rquickjs`（成熟、可嵌入、体积小）做沙箱脚本运行时，禁 fs/process/child_process，网络需显式授权，资源限制（超时/内存/循环数），数据仅经 WorkspaceBridge，每次执行审计，破坏性操作走审批。

> 决策依据：首版 90% 的"超出 CRUD"需求（特殊 UI、语义判断、复杂报表、多步流程）用 ①③④ + agent 任务就能覆盖，不引脚本运行时；只有"必须后端跑确定性计算且 SQL 表达不了"（如复杂算法、外部 API 编排）才需要 ② 的脚本运行时——这是 YAGNI 的落点，列为 M5+ 可选增强。

### 16.4 代码怎么被写出来（LLM 生成闭环）

复用 custom-app 的 validate 经验（`crates/hermix-plugin/src/validate.rs`）：

```
1. 需求超出 Schema → LLM 按决策表（§16.5）选扩展点
2. LLM 生成代码（widget/action）到工作台目录
3. 校验 validate：禁远程 URL、禁直接 DB 访问、禁危险 API、禁未授权网络
4. 预览：隔离容器跑起来，错误回传 LLM 修复（复用 §7 迭代闭环）
5. 用户确认 → 提交（纳入 .hwx 包，随工作台版本化）
6. 运行：按钮/提醒/调度/对话触发 → 执行 → 审计
```

### 16.5 决策表：什么需求用哪个扩展点

| 需求 | 扩展点 |
|---|---|
| 特殊界面（地图/向导/特殊图表） | ① 自定义组件 |
| 计算/校验/批量转换逻辑 | ② 自定义动作（脚本，M5+）或 ③ SQL 视图 |
| 调用外部 API / 集成设备 | ② 自定义动作（脚本，需授权，M5+） |
| 语义判断（"这批数据是否异常"） | ② 自定义动作（agent 任务，现有能力） |
| 复杂聚合/跨表报表 | ③ SQL 视图 |
| 多步审批/处理流程 | ④ 自定义自动化 |
| 完整独立工具 | ⑤ 嵌入独立应用 |

### 16.6 WorkspaceBridge（扩展代码的数据桥）

自定义组件/动作通过 WorkspaceBridge 访问数据——与 LLM 工具族（§9）同一套校验层：

```js
WorkspaceBridge.query(table, { filter, sort, limit })   // 列名白名单 + 参数化
WorkspaceBridge.insert(table, rows)                     // JSON 严格校验
WorkspaceBridge.update(table, id, patch)                // 同上
WorkspaceBridge.delete(table, id)                       // 需审批
WorkspaceBridge.count(table, filter)                    // 聚合
WorkspaceBridge.notify(message)                         // 推通知
WorkspaceBridge.http({ method, url, body })             // 需显式授权 + 白名单
```

## 17. 复审补充（2026-08-26 二轮评审）

> 首版评审后补充的缺口。按"直接影响一次性交付质量 → 台账刚需 → 架构完整性"排序。

### 17.1 导入清洗与预览（脏数据处理）

用户丢的数据往往不干净（重复行、空值、格式不一、编码问题），直接建表导入会留隐患。导入流程升级为：

```
解析 → 清洗（去重/空值/类型转换/格式规范化）→ 导入预览 → 落库
```

- **清洗规则**：LLM 按数据摄入的质量提示生成清洗规则（去重键、空值策略、日期格式、枚举映射），在提案卡展示。
- **导入预览**：落库前展示"将导入 N 行、跳过 M 行异常（附异常清单）"，用户确认后才写库。
- **增量更新**：用户定期重新导入同一份数据（如每月车辆名单）→ **upsert 按唯一键**（新增 + 更新 + 标记删除），用户选策略，不整表覆盖。

### 17.2 建设后自动自测（质量闭环）

文档此前只提"完成后提醒用户测试"，缺机器自测。补充：**BuildPipeline 完成后自动跑 smoke test**：

```
建表 → 插入样例 → 查询 → 视图渲染校验 → 提醒规则试跑 → 全部通过才报"建设完成"
```

- 任一环节失败 → 自动回滚或错误回传 LLM 修复后重试。
- 这是"一次性交付不报错"的机器保障，不依赖用户手动测试兜底。

### 17.3 附件/图片管理

台账常挂图片（车辆照片、事故现场照），§8.1 的 `files/` 需补设计：

- 新增 `attachment` 字段类型：上传 → 存 `files/<row_id>/` → 元数据引用 → 图片内联预览。
- 单文件大小限制（如 20MB）、类型白名单、附件随 `.hwx` 包导出。

### 17.4 权限模型细化

§11.3 只留了 `roles: {owner/editor/viewer}`，管理台账需要更细粒度（参考 NocoDB 的 collaborative/locked views）：

- **工作台级**：owner / editor / viewer。
- **表/视图级**：锁定视图（只读）vs 可编辑视图。
- **行级（二期）**：按字段过滤（"普通员工只看本部门"）→ 预留 `row_filter` 表达式。
- 首版单用户不启用，但 `workspace.json` 预留 `permissions` 结构，避免后期改 schema。

### 17.5 导出/报表/打印

用户要"展示项目"，需工作台级导出：

- 表格/视图 → Excel（复用现有 xlsx）/ CSV。
- 仪表盘/视图 → PDF / 打印（复用 Hermix.screenshot 思路）。
- 一键导出当前工作台数据包（`.hwx`）。

### 17.6 撤销与变更历史

审计日志已记变更前后，但缺用户可用的撤销/历史：

- **变更历史视图**：按行展示"谁/何时/从 X 改到 Y"（audit.sqlite 的 diff 视图）。
- **撤销**：最近 N 步操作可回滚（按变更记录反向应用）；LLM 批量操作后尤其需要（防"LLM 改错了想反悔"）。

### 17.7 全局搜索

台账需要跨表快速检索：

- 输入关键词 → 后端跨表搜索 → 结果按表分组展示。
- 轻量实现：SQLite **FTS5** 虚拟表，导入时建全文索引，零新依赖。

### 17.8 工作台上下文注入（LLM 准确性前提）

多工作台时 LLM 必须知道"当前在哪个工作台"：

- **active workspace 注入 system prompt**（当前工作台名 + 模块列表 + 数据规模）。
- `workspace_*` 工具默认带当前工作台参数，LLM 无需每次指定。
- 切换 Tab 时上下文同步更新——这是 §9 数据准确性的前提。

### 17.9 通知深链

提醒点击后要能定位到具体位置：

- 提醒消息带深链：点击 → 打开对应工作台 → 定位到对应表/行（高亮）。
- 前端 `NotificationCenter` 支持 action 跳转。

### 17.10 规模边界与性能

- **单表规模**：SQLite 单表几十万行没问题，需自动建索引（唯一键 + 常用过滤列）。
- **分页**：服务端分页（LIMIT/OFFSET 或 keyset），前端虚拟滚动。
- **超大规模（>100 万行）**：不硬撑，提示导出/归档/分区。

### 17.11 时区与日期语义

台账是本地业务，日期语义必须明确：

- 日期字段统一**本地时区**存储；提醒的"今天/+7 天"按本地时区计算。
- 明确 `date`（日期）vs `datetime`（时间点）字段类型语义，避免 LLM 混用。

### 17.12 前端组件桥安全（补 §16）

§16 提了 iframe sandbox，补桥的安全细节：

- widget 经 iframe **postMessage 桥**：校验 message source（只收宿主 origin）、按 message id 应答。
- widget 只能访问**当前工作台**数据（WorkspaceBridge 绑定 ws_id），跨工作台访问需显式授权——防止 LLM 生成的 widget 越权读其他工作台。
