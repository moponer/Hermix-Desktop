# Decision Note: PPT / PDF 编辑 —— 用已经在磁盘上的能力，不引新依赖

Status: implemented — PPTX 有真正的就地编辑器（改文字 / 加文本框 / 增删页 / 改背景 / 写备注 / 导出）；PDF 有点选页面落位的便签批注与「点选本页文字改写」；两条路都零新依赖

## Decision

### PPTX：接上 `pptx-browser` 自带的写回器

项目早就装了 `pptx-browser@4.1.5`，它不只带渲染器（`PptxRenderer`），还带**写回器**（`PptxWriter`：改形状文字、加文本框、加图、复制/删除/重排页、改页背景、改主题色、写备注、`save()`）。之前只用了渲染面，类型声明里也只有渲染面 —— "能改 PPT"这件事在类型层面就不存在。

现在新增 `apps/viewer/src/document/PptxEditor.tsx`：左侧页导航 + 中间画布 + 右侧属性栏（形状列表 → 选中 → 改字 → 应用；新增文本框；备注；页背景；页序）。每次改动后把 writer 的产物重新灌回渲染器（`PptxRenderer.load` 可原地重载），画布与改动一致。产物走 Rust 的 `write_bytes`（`safe_output_path` 守卫），原文件永不覆盖。

### PDF：批注用注释层，文字改写用「点选」代替「手打全串」

- **便签批注**：新命令 `pdf_add_annotation`（lopdf），在前端点页面选落点（pdf.js 的 `viewport.convertToPdfPoint` 换算成 PDF 用户空间），文字原样写进页面的 `/Annots`。选批注而不是把字"烧"进页面内容流，是因为内容流里插字要自己带字体资源、标准 14 号字没有中文字形（中文渲染成空白），而批注由阅读器用自己的字体渲染，中文与 emoji 都不丢。
- **本页文字清单**：用 pdf.js 的文本层列出该页文字项，点一下就填进「原文」框。旧的文本替换要求用户手打整串原文 —— 实际没人能一字不差打完一个长句，这个功能等于没有。

## Alternatives considered

- **引入 ONLYOFFICE / Collabora 之类的完整办公套件**：能力最全（真排版、真协同），但它们是**服务端**产品：要么自建部署，要么把文档送出去 —— 与"便携、零安装、文件不出本机"的产品前提冲突，且体量是本项目的好几个数量级。
- **用 pdf.js 的 AnnotationEditor（FreeText / Ink / Highlight / Stamp）**：pdfjs-dist 6.4 自带这套编辑器与 `saveDocument()`，但它依赖 `web/pdf_viewer.mjs` 与 `pdf_viewer.css` 的整套查看器外壳，接进来等于把自绘的 PDF 视图换成 pdf.js 官方查看器（换一套视觉、换一套交互），改动面远超收益。批注走注释层已经覆盖"能写话"这一刚需。
- **给 PDF 加"画字"能力（内容流插字）**：中文需要嵌入字体，仓库里没有可嵌入的中文字体资产，标准 14 号字写中文是空白 —— 做出来也是坏的。
- **PPTX 用 pptxgenjs 之类重新生成**：那是"新建"，不是"编辑"；原文件的主题、版式、母版全部丢失，与"改完导出为新文件、原样保留"的原则冲突。
- **给 PDF / PPT 另起一套统一的编辑器框架**：四套编辑器已经各有保存/另存为/脏状态流程，再抽一层抽象的收益远小于把能力补齐。

## Consequences

- PPTX 编辑的每次改动都要做一次 zip 往返（写回 + 重新解析），大文件上有几百毫秒延迟；换来的是"改完立刻看到"。
- `pptx-browser` 的类型声明从 5 行扩到 50 行（渲染面 + 写回面），这是补上"库已经能做而项目没接"的事实，不是自造 API。
- PDF 批注是**追加**语义：每次加批注产出一份新文件，连续加多条批注需要自己依次套用产物（当前 UI 一次一条）。
- PDF 的整串精确匹配限制**已被页内改字能力取代**：整串匹配只认 `Tj` 算子、扫描件与 TJ 数组排版会报「未找到」；现在改字走**按位置定位**（点选即改 + 遮盖插入 + 真删除 + 复用文档嵌入字体写中文），见 `2026-10-21-pdf-inpage-text-editing.md`。
