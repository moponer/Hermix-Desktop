# Decision Note: 查看器的本地 MCP 端点改为默认启动

Status: implemented — 2026-10-21 落地：`McpSettings::default()` 的 `enabled` 由 `false` 改为 `true`；全新安装开箱即有端点，显式关掉的老用户保持关闭

## 事实

### 事实 1：默认关闭 = 产品的核心能力出厂即废

查看器自带 30 个 MCP 工具（`webview_*` / `browser_*` / `desktop_*` / `viewer_*`），
是「让 agent 驱动查看器」这条产品能力的唯一载体。但端点是否启动，取决于
`ViewerSettings.mcp.enabled`，而它的默认值是 `false`。

后果链条：

1. 桌面端的 `open_in_viewer`（`apps/desktop-tauri/src-tauri/src/commands.rs:1543`）
   **只拉起 exe，不起 MCP** —— 端点完全由查看器自己的设置决定；
2. 查看器设置在 `设置 → MCP 服务 → 启动查看器时拉起本地 MCP 服务`，
   是一个不起眼的复选框；
3. 用户不去翻这个开关 → 端点不存在 → agent 的 `hermix-viewer__*` 工具全部调不通。

**「能力在，但默认路径不通」** —— 与 `2026-10-21-automation-create-run-wiring-broken.md`
记的那类毛病同源：不是功能没实现，是默认路径断了，而断点没人会发现。

### 事实 2：默认关闭并没有换来实质安全边界

端点**只绑回环地址**（`apps/viewer/src-tauri/src/mcp_http.rs:47`）：

```rust
let host = if allow_remote { "0.0.0.0" } else { "127.0.0.1" };
```

`allow_remote` 默认 `false`，且打开时会在 stderr 大声告警（`mcp_http.rs:74`）。

真正要紧的那条边界是「不对外网开放」，它与「默认开还是默认关」无关。
另一方面，本地进程本来就能直接调 UIA / SendInput 驱动桌面 —— `desktop_click`、
`desktop_press_key` 这些工具做的就是这件事。**MCP 端点给本地调用方的是便利，
不是新能力。**

### 事实 3：设置文件只在用户改过设置时才落盘

`ViewerSettings::save()` 的唯一调用点是设置更新命令（`commands.rs:1223`），
启动时不写盘。所以：

- **全新安装**没有 `viewer-settings.json` → 读盘失败 → 走 `Default`；
- **显式关掉的老用户**，文件里存着 `enabled: false` → 保持关闭。

这条性质让「改默认值」有了干净的迁移语义：**只影响没表态过的安装**，
不动用户显式做过的选择（无法区分「用户主动关的」和「旧默认值写下来的 false」，
所以不猜）。

## Decision

**把 `McpSettings::default()` 的 `enabled` 改成 `true`，其余不动。**

1. 端口仍是 3911，`allow_remote` 仍是 `false` —— 安全边界（只监听回环）不动。
2. 不改「桌面端是否注册查看器 MCP」这件事：`~/.hermix/mcp_servers.json`
   的已配置列表**仍由用户在「内置目录」里点安装产生**（`dashboard/mcp.rs:134-145`
   明确记了这个决定）。端点开不开（查看器侧）≠ agent 能不能调（sidecar 侧），
   这是两个决定。
3. 不做「旧安装的 `enabled: false` 自动改成 true」的迁移 —— 见事实 3。

## Alternatives considered

- **保持默认关闭，靠文档告诉用户去开**：否决。用户要在设置里翻一个不起眼的
  复选框才能用上核心能力，而这个能力失效的表现是「agent 说工具不存在」，
  不是「有个开关没开」—— 排查成本极高。同 2026-10-06 那次 sidecar 事故同型。
- **把 `mcp_servers.json` 的播种再加回 `hermix-viewer`（sidecar 侧自动注册）**：
  否决。仓库已经明确移除过官方 server 的自动播种（`dashboard/mcp.rs:134-145`），
  当时的理由是「已配置列表 = 用户实际启用的清单，目录 = 打包进去的候选清单」。
  查看器虽然是一方组件，但「agent 能调用屏幕控制工具」是**权限授予**，
  该由用户显式做；端点监听回环则不是。这个分工不能因为「想让流程更顺」而模糊。
- **在桌面端拉起查看器时顺带起 MCP（代替改默认值）**：否决。那只覆盖「桌面端
  拉起」这一条路径；文件关联双击、用户自己启动查看器都不经过那条路径，
  而自动化任务要求查看器随时可被驱动。
- **把端点绑到随机端口 / 加握手令牌**：否决。端口是内置目录里 `install.url`
  预填的值（`http://127.0.0.1:3911/mcp`），一随机，目录条目就失去意义。
  回环 + 仅本机是这一层能给出的全部保证。

## Consequences

- **干净环境开箱可用**：装完 → 打开查看器 → 端点已在 127.0.0.1:3911 上；
  再在桌面端「内置目录」点一次「安装」（无凭据弹窗）→ agent 就有
  `hermix-viewer__*` 工具。不用去翻查看器设置里的开关。
- **端口被占不拦启动**：`mcp_http::start` 失败只打 stderr 告警，查看器照常开
  （`lib.rs:315-324`）—— 默认开着不会因为 3911 被别的进程占住就打不开应用。
- **显式关过的人不受影响**，但他们**不会**因为这次改动自动获得新能力 ——
  想用的人要么删掉 `viewer-settings.json` 里的 `enabled: false`，
  要么在设置里勾回来。这是「尊重显式选择」的代价，明确接受。
- 端点默认在跑，意味着「查看器开着 = 本机有个能驱动桌面的 HTTP 端点」。
  这是本产品把 agent 当自动化目标这件事的固有暴露面，不是本次改动引入的新风险，
  但值得写在这里：**打开查看器 = 开放本机端点**。
