# Decision Note: 输入框「增强提示词」能力

Status: implemented — 输入框新增一键增强：一句模糊需求扩写成六段结构提示词，场景规格内置在服务端模板里

## Decision

输入框工具条新增「增强」按钮（`EnhanceButton`，位于润色按钮右侧），点击一次把
当前草稿扩写成**结构化提示词**并回填输入框；再点一次还原原文。快捷键
`Ctrl+Shift+/`（润色是 `Ctrl+/`）。

产出的提示词固定六段：**角色 / 背景 / 任务 / 输入 / 约束 / 输出格式**。
服务端模板 `ENHANCE_PROMPT`
（`crates/hermix-server/src/dashboard/polish.rs`，**唯一副本**）里还带一张
**场景规格表**：周报 / 日报 / 方案 / 竞品分析 / 复盘 / 会议纪要 / 邮件 /
PPT 大纲 / 演讲稿 / SWOT / 决策分析 / 行业研究，每条给出该场景的产出结构
与语气要求。模型按草稿自动选用最贴切的一条（最多两条），用户**不需要选场景**。

技术落点沿用既有「无状态 LLM 改写」管道：`POST /api/polish/enhance` →
`agent_service.send_message` + 临时 session + `tools=[]` + 12s 超时，
与 `/api/polish/chat`、`/api/polish/automation` 同一套外壳（本次把 LLM
调用部分抽成 `run_with_prompt` 供三者共用，chat/automation 的用户消息
拼装逐字节未变）。

**与「润色」的分工**（两者并存，不互相取代）：

| | 润色（PolishButton） | 增强（EnhanceButton） |
|---|---|---|
| 性质 | 同义替换 | 扩写 + 补结构 |
| 长度 | 原文 0.7–1.3 倍 | 150–600 字的提示词 |
| 产物 | 更好读的对话文本 | 可直接投喂 AI 的提示词 |
| 格式 | 纯文本，禁 Markdown | Markdown 分段（提示词文本本身） |

## Alternatives considered

- **让用户先选场景模板**（第一版实现：菜单里列 12 个场景 + 「自动识别」）。
  否决。用户明确反对多这一步。技术上也不划算：模型从草稿认出场景的准确率
  高于用户去点下拉框；真要指定，用户在草稿里写「周报」比开菜单快。场景规格
  因此改为**内置在模板里由模型自动选用**。
- **本地模板拼接（不调 LLM）**：工作流式工具（刘哥工具箱）的路子，隐私好、
  零延迟。但它只能填空式拼装，产出的提示词是模板不是针对需求的推理结果，
  质量天花板低；且本项目的 LLM 已经在进程内，接一次调用的边际成本远低于
  维护一套本地模板引擎。否决。
- **复用 `AUTOMATION_POLISH_PROMPT`**（自动化页已有的结构化改写模板）：
  它是为自动化引擎写的——保留 `{{变量}}` 占位符、写明工具名、强调调度。
  对话输入框的增强不需要这些，且缺「背景 / 约束 / 验收」两段。否决。
- **在前端保留一份 `ENHANCE_PROMPT` 镜像**（`polish.chat.ts` /
  `polish.automation.ts` 的既有做法）：两份模板迟早漂移，而这两个旧副本
  已经漂移（前端导出从未被使用，Rust 侧注释自认是 stale read-only mirror）。
  增强模板**只存服务端一份**，前端只留请求契约。否决。
- **把增强结果直接发出去**（不进输入框）：用户失去检查/修改的机会，而
  增强结果必然掺了模型补的「[待补充]」占位。回填输入框是唯一合理形态。

## Consequences

- 增强结果**可能替用户补全事实**：模板要求缺项写「[待补充：xxx]」而不是
  编造，但模型仍可能偶发推断过度。回填输入框让用户有机会在发送前改。
- 每次增强调用的系统提示词约 1.5K 字（六段结构 + 12 条场景规格）。
  这是为「自动识别场景」付出的固定成本，相对输出 token 可忽略。
- 增强能力**绑死在当前选中模型**上：`send_message` 走默认模型，没有
  per-call 选模型的通道。想用更强的模型做增强，需要先扩 agent service。
- 失败**不降级**：增强失败时抛错并 toast，不退回「折叠空白」。润色可以
  退回空白折叠（顶多多几个空格），增强没有可退回的形态——退回原草稿等于
  「点了没反应」。两条路径的降级策略故意不同。
- 场景规格表写死在 Rust 常量里：新增场景要改 Rust + 改测试里的场景清单。
  换来的是**前后端只有一份场景知识**（前端不再有场景目录）。

## Reintroduction conditions

- 用户要「强制指定场景」（草稿措辞含糊、自动识别选错）时：恢复显式选择。
  扩展点是现成的——`ENHANCE_PROMPT` 的规格表按场景分行，加一个
  `scenario` 请求字段让模型优先某行即可。
- 需要「按场景分别用不同模型/不同温度」时：先扩 agent service 的
  per-call 模型选择能力。
