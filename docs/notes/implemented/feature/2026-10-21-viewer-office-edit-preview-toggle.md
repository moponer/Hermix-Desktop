# Decision Note: Word / Excel / PPT 的「编辑 / 预览」切换取代死掉的「文本 / 排版」

Status: implemented — 查看器重量模式下 Office 文档默认进入编辑态，工具条上一个分段开关在「编辑 / 预览」之间切换；`supportsTextView` 只对 PDF 与 HTML 成立

## Decision

「排版 / 文本」这对词对 Office 文档**没有意义**：`applyViewMode` 对 `docx` / `pptx` 原样返回，点「文本」什么都不会变 —— 一个骗人的按钮。现在：

- 共享层的 `supportsTextView` 只认 `pdf` 与 `html`（这两种的两种视图真的不同：PDF 的排版是页画布、文本是抽出的 Markdown；HTML 的排版是渲染页面、文本是源码）。桌面端预览面板与查看器同步受益。
- 查看器重量模式下，`docx` / `xlsx` / `xlsm` / `pptx` 走**「编辑 / 预览」**分段开关，**默认编辑**（Office 软件本来就是这样），工具条常驻，切换状态可见。
- 纯净模式没有编辑能力，不给这个开关，仍是只读预览。

预览区上沿（标签栏那一行）另加一个**折叠文件列表**的按钮：收起后中部列表栏整列让位，预览区占满宽度、内容居中。状态存 localStorage。

## Alternatives considered

- **给 docx / pptx 补一个真正的「文本」视图**（markitdown 抽取）：查看器没有 markitdown sidecar（`readMarkdown` 退化成读文本，二进制直接失败），要补就得再引一个 sidecar；而用户对 Word 文档要的显然是"能改"，不是"能看纯文本"。因此把这条路换成了「编辑 / 预览」。
- **保留「排版 / 文本」并给它加个提示**（点不动就说明白）：仍然是死按钮；不如让按钮只出现在它真的有意义的两种类型上。
- **编辑按钮 + 预览按钮两个平级按钮**：状态会散在两个地方，用户点完不知道自己停在哪；分段开关把状态收在一处（编辑器自己的「预览」按钮仍然存在，作为同一状态的快捷入口）。
- **折叠文件列表做成「专注模式」隐藏左右两栏**：用户明确说的是收起中间的目录浏览列表；侧栏（驱动器树）是他找文件的路，藏起来反而添乱。

## Consequences

- 查看器工具条在 Office 编辑态下也占一行（文件名交给编辑器自己的工具条，不重复显示）。
- 缩放按钮在 Office 编辑态下不显示 —— 缩放作用于只读预览，对编辑面无意义。
- 纯文本 / 代码 / PDF / 图片的预览行为不变；`supportsTextView` 的返回集合变窄，依赖它做判断的地方只有桌面端 `PreviewPanel` 与查看器 `PreviewHost` 两处。
