# Decision Note: viewer 主程序入口 + 标题栏双击 + 纯模式正文列宽

Status: implemented — 三件事一起落地：① 主程序（Hermix 桌面端）标题栏新增「文件管理器」一级入口，点击即拉起独立的 hermix-viewer；② 查看器自绘标题栏双击真的能最大化/还原；③ 查看器纯净模式下 Markdown 正文列太窄、两侧空白过大，行长上限放宽。

关联：[viewer 自绘右键菜单 + 自绘窗口标题栏](2026-10-20-viewer-context-menu-and-custom-titlebar.md)、[hermix-viewer 双模式化与全能力重构](2026-10-19-hermix-viewer-overhaul.md)

## Decision

**1. 「文件管理器」是主程序的一级入口，不是右键菜单里的二级动作。**

此前主程序能开到查看器的路径只有一条：文件树右键菜单里的「在查看器中打开」（以及全局文件搜索窗口双击）。标题栏那一排已经放着「浏览器小窗」「截图」这类**应用级动作**，查看器（独立进程、多格式预览 + 全盘搜索 + 文件操作右键菜单）却完全不在里面——用户根本不知道它存在。

做法：桌面端 `TitleBar` 右栏加一个 `FolderTree` 图标按钮 → `invoke("open_in_viewer", { path: null })`；Rust 侧 `open_in_viewer` 的路径参数改成 `Option<String>`（Tauri v2 的 `Option<T>` 参数可以整个省略，缺失即 `None`），带路径时行为不变（仍走单实例投递），不带路径时启动一个「什么都不打开」的查看器。

**2. 「无路径启动查看器」= 打开文件管理器，必须是资源管理器模式。**

查看器原本的启动模式推断是「上次显式选择优先，其次按有没有路径猜」，于是无路径启动可能落进**纯净模式**（只预览一个文件，而此时没有文件）——一个叫「文件管理器」的入口点开却是个空预览页，说不通。

改法：启动时 `paths.length === 0` 直接进重量模式（资源管理器），**不再看**上次显式选择；带路径启动才沿用旧推断（文件关联唤起 → 纯净模式「双击就看」，用户显式切过的模式优先）。

同时补上单实例投递的空载荷：第二实例无路径启动时，投递内容为空串，Rust 侧此前直接 `continue` 丢掉了——用户在主程序点了按钮，已开的窗口毫无反应。现在空载荷会：把窗口从最小化/隐藏状态拉回来并置前（`unminimize` + `show` + `set_focus`），再 emit `viewer-open-explorer`，前端据此切到重量模式。

**3. 标题栏双击最大化不能靠 DOM 的 `dblclick` 事件。**

`startDragging()` 走的是系统**模态**拖拽循环（Windows 的 Move/Sizemove 循环）：一旦启动，后续鼠标输入被系统接管，浏览器不会再派发 `dblclick`。第一版把 `toggleMaximize()` 挂在 `onDoubleClick` 上，真机双击毫无反应；第二版改成在 `pointerdown` 里按时间戳自己判双击，**时灵时不灵**——拖拽循环启动得早就把第二次按下吞了，启动得慢就赶上了（用户实测能放大，脚本实测不能）。

最终做法：自己实现这套状态机，双击与拖动**互斥**——
- 按下先不拖，记下时间与位置；
- 400ms 内的第二次按下 → 双击，切换最大化（此刻还没起拖拽，第二下不会被吞）；
- 指针移动 >4px → 判定为拖动，**立刻**起拖（无延迟，手感不变）；
- 按住不动 → 等满 220ms 再起拖（此时已排除双击）。

**4. 纯净模式的 Markdown 正文列宽由 viewer 侧覆盖，不动共享包。**

共享包给 `.preview-md-body` 的行长上限是 `68ch`——那是按桌面端「右侧窄预览栏」（常只有 400~550px）定的。viewer 的预览区是**整屏**：68ch 在 1200px 的窗口里只占三分之一宽，正文两侧各空两百多像素，像一条细带子漂在大白纸上。

改法：viewer 自己的 `styles.css` 里加一条 `.preview .preview-pane .preview-md-body { max-width: 96ch; }`（≈48 汉字/行，仍在中文长文的可读范围内）。窄栏里 96ch 大于列宽，`max-width` 自然回落到列宽，不会撑破、不会横向滚动；桌面端继续用 68ch（它的预览栏窄，放宽只会让行长失控）。共享包一行未动——它同时服务两个应用，"整屏阅读"是 viewer 独有的场景。

## Alternatives considered

1. **在侧栏/产物栏加「文件管理器」入口** ——拒绝：主程序的右栏是「预览当前会话产物」的位置，查看器是另一个独立进程的应用，放进去语义不对；标题栏右栏已经是应用级动作的所在地（浏览器小窗、截图）。
2. **让主程序内嵌查看器界面（不开独立窗口）** ——拒绝：查看器是独立进程 + 单实例 + 自绘标题栏 + 自己的 Rust 命令集，嵌进来等于重写一遍；而且用户要的是「点一下就有一个文件管理器窗口」。
3. **无路径启动时沿用上次显式选择的模式** ——拒绝：那个动作的语义是「打开文件管理器」，上次用纯净模式预览文件不该把这个入口变成空预览页。显式偏好只对「带路径启动」生效。
4. **空载荷投递时不做任何事（保持现状）** ——拒绝：用户在主程序点了按钮、这边毫无反应，是最难查的一类「点了没反应」。
5. **标题栏双击用 `onDoubleClick` + 去掉 `preventDefault()`** ——不可行：模态拖拽循环启动后浏览器不再派发 `dblclick`，与 `preventDefault()` 无关。
6. **用 400ms 定时器统一处理「拖动 or 双击」**（不靠指针移动阈值） ——拒绝：定时器到期才起拖，用户按住不动的那 220ms 里窗口不跟手；而且「按下→移动→松开」这个真实拖拽会被 220ms 的延迟吃掉手感。指针一动就起拖没有这个问题。
7. **把 68ch 直接改宽到 96ch（改共享包）** ——拒绝：共享包同时被桌面端消费，桌面端产物栏窄，放宽行长会让每行字数失控。覆盖写在 viewer 侧，作用域清楚。
8. **纯净模式用两栏排版 / 加侧边注释栏** ——拒绝（暂不做）：那是一整套阅读器布局，远超「宽度太窄」这一条诉求；先把宽度这件事做对。

## Consequences

- **桌面端多了一个 Rust 命令签名变化**：`open_in_viewer(path: String)` → `Option<String>`。既有调用方（文件树右键、文件搜索窗口双击）继续传字符串，行为不变；Tauri v2 的 `Option<T>` 参数缺失即 `None`（已核对 tauri 2.12.1 的 `CommandItem` 反序列化实现）。
- **查看器的启动模式语义变了**：无路径启动恒为重量模式。带路径启动的推断不变。
- **单实例投递多了一条事件**：`viewer-open-explorer`（空载荷）。窗口置前在 Rust 侧做（AppHandle 拿到窗口句柄，不受前端 ACL 约束）。
- **标题栏的拖动多了一个 4px 阈值**：指针不动就不拖（等 220ms 后仍会拖），拖动起点比原来晚 0~4px 的位移，手感无差别。
- **正文列宽在两个应用里不同**：viewer 96ch / 桌面端 68ch。这是有意的分工——共享包的默认值按窄栏定，viewer 自己覆盖。
- **文档列宽的最终值 96ch 是折中**：再宽行长会失控（>50 汉字/行），再窄又会回到"细带子"。若用户仍觉得不够宽，调这一个数字即可（`apps/viewer/src/styles.css`）。

## Reintroduction conditions

- 若用户嫌 96ch 仍不够宽：改 viewer 的 `max-width` 一个数即可；若要"随窗口自适应"，需要引入 `clamp()` 并重新评估长行可读性——那时属于新决策。
- 若要在纯净模式加阅读增强（目录悬浮、代码块行号、注释侧栏）：以 `packages/preview` 的 `MarkdownView` 为落点，别在 viewer 侧另起一套。
- 若标题栏要加更多按钮（菜单栏、搜索框等）：注意双击判定的前提是「按下先不拖」——任何在标题栏里**立即**起拖的元素都会破坏双击最大化。
- 若 Tauri 升级后 `startDragging` 改成非模态：双击判定的 220ms 延迟可以去掉（届时 `onDoubleClick` 就能直接用），但保留自判也无害。
