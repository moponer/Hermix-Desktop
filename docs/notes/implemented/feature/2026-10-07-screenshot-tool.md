# Decision Note: 系统截图功能（快捷键 + 标题栏入口，区域/窗口双模式，直出剪贴板）

Status: implemented — 2026-10-07 拍板并开工；M1/M2/M3 已交付（M4 打磨项后续按需）。
2026-10-23 起，抓屏方式 / 覆盖窗生命周期 / 坐标换算 / 选区交互被
[截图模块重写](./2026-10-23-screenshot-rewrite.md) 修订——本文保留原始选型与
交互契约，机制细节以重写篇为准。

## Decision

新增**系统级截图**能力，一句话选型：

> **Rust 侧 xcap 抓屏 + 全屏无边框置顶"选区覆盖窗"（独立 Tauri window）做交互 + windows-rs 剪贴板直写 PNG**，不引入 Electron 截图库，不依赖第三方截图进程。

核心体验契约（用户明确要求的四条硬性体验）：

1. **两种触发**：可配置全局热键（默认 `Ctrl+S`……不对——**默认改为 `Alt+Q`**，见「热键选型」节的冲突分析，`Ctrl+S` 是全人类软件的"保存"，默认占用它会在聊天输入框等一切可编辑区引发保存冲突，属设计事故；`Ctrl+S` 作为可配置选项保留）+ 标题栏相机图标点击（主进程内触发，无需全局注册）。
2. **截图直接进剪贴板**：选区确认后 PNG 直写系统剪贴板，立即回到原工作流；**不弹编辑器、不落盘**（可选"另存"进后续版本）。
3. **右键任意位置可粘贴**：剪贴板里是标准 `CF_DIB` + `PNG` 双格式，任何输入框/聊天窗/富文本编辑器右键粘贴直接出图；本项目聊天输入框同时补一条"检测到剪贴板图片 → 粘贴即附件"链路（输入框已有 paste 事件，扩为图片分支）。
4. **三种选区模式**：默认**拖拽矩形**；**自动窗口识别**（鼠标悬停即高亮整窗，点击即截）；矩形与窗口模式随时可切（Tab 键或模式按钮）。不做延时截、不做滚动截（YAGNI，见 Alternatives）。

## 架构与数据流

```
触发（全局热键 / 标题栏按钮 / 以后可加托盘菜单）
  → Rust: screenshot_controller.rs
     ├─ ① xcap 抓屏（~200ms）：光标所在显示器图像 + 坐标 + scale，
     │     原始位图入 static 会话缓存
     ├─ ② 立即建覆盖窗（hidden）：无边框、置顶、skip-taskbar；
     │     首帧是 index.html 的静态 #overlay-boot「正在截取屏幕…」占位
     ├─ ③ 后台线程并行编码幕布 JPEG（q80，比整帧 PNG 小 5-10×）；
     │     前端轮询 screenshot_frame_data（None=编码中 → Ready → 渲染并
     │     show 窗口；Failed → 错误 UI）。30s 兜底：窗口仍存在且未亮
     │     （页面/编码异常）→ 报错回主窗 toast + 关窗。绝不再"3s 亮出
     │     半就绪页面"（那曾把 #splash 启动屏糊成全屏，2026-10-10 回归根因）
     ├─ ④ 覆盖窗交互（前端）：
     │     - 默认拖拽矩形：按下→拖动→松开 = 选区；ESC 取消
     │     - 窗口模式：鼠标移动 → Rust 查询光标下 HWND（EnumWindows 排除
     │       覆盖窗自身）→ 回传 rect → 覆盖窗画高亮框
     │     - 模式切换：Tab / 悬浮工具条（矩形□ 窗口⛶ 确认✓ 取消✕）
     ├─ ⑤ 编辑器（2026-10-08 起，2026-10-10 数据流修正）：选区确认后
     │     前端 invoke screenshot_crop_data 按需取选区无损 PNG 裁剪
     │     （只传选区不传整帧——幕布是 JPEG，编辑底必须无损），
     │     编辑画布（框选/画笔/文本/涂抹/裁剪/撤销 + 色板），完成才提交
     │     a) 前端 canvas 导出 PNG → screenshot_commit_edited →
     │        解码 RGBA → 剪贴板直写（CF_DIB + PNG 双格式）
     │     b) 关闭全部覆盖窗，焦点还给原前台窗口
     │     c) 主窗口 toast「已复制到剪贴板」（唯一可见反馈，不打断）
```

关键设计点：

- **先抓后盖**：进入覆盖窗之前就完成抓屏。覆盖窗显示的是"照片"，用户在照片上画框——这是 Snipaste/微信截图同款的正确模型；反过来（选好区再抓屏）会把覆盖窗自己拍进去。
- **每显示器一个覆盖窗**：多显示器下选区可跨屏（各窗报本地坐标，Rust 侧按显示器原点偏移合成全局 rect）。V1 简化为"抓主显示器 + 光标所在屏优先"也可接受（见里程碑 M1 范围），但架构上按多屏预留。
- **窗口识别**用 Win32 几何（`WindowFromPoint` + `GetAncestor(GA_ROOT)` + `DwmGetWindowAttribute(DWMWA_CLOAKED)` 排除隐形/UWP 幽灵窗 + `GetWindowRect`），**不做** ML/OCR 窗口内容识别——几何法零依赖、<1ms、覆盖 95% 场景（Snipaste 同款思路）。
- **DPI**：xcap 返回物理像素；覆盖窗光标坐标是逻辑像素——统一换算表（每显示器 scale factor）在 Rust 侧持有，覆盖窗只发逻辑坐标。per-monitor DPI awareness 已在 tauri.conf 可配，需确认 `true`。

## 热键选型（默认值重要，单独说清）

- **不用 `Ctrl+S` 作默认**——它是"保存"的事实标准，热键注册在系统层，按下后原应用的保存行为会被全局钩子吃掉，用户在任何编辑器里按 Ctrl+S 都会变成截图，这是灾难。用户说"好像一般没有软件用这个"恰是因为它被"保存"占死了。
- 默认 `Alt+Q`：与主流软件无冲突（Alt 系组合占用率低），单手可按，与本项目已有聊天快捷键（Enter/Ctrl+Enter 系）不在同一修饰域。
- 候选池（设置页下拉）：`Alt+Q`（默认）/ `Ctrl+Alt+A`（QQ/微信习惯）/ `PrintScreen` / `F4`。
- 注册用 tauri-plugin-global-shortcut（官方插件，tauri.conf capability 加一行）；热键冲突时注册失败 → toast 提示引导改键，不静默。

## 交互细节（覆盖窗内）

- 幕布：全屏半透明黑罩（原截图变暗 40%），选区内实时恢复原始亮度（双 Canvas 或 clip 实现）。
- 选区拖拽中显示尺寸 `W × H`（px，物理像素口径）小标签。
- 确认三通道：松开鼠标双击选区内 / 工具条 ✓ / Enter。取消：ESC / 工具条 ✕ / 右键。
- **右键语义**：覆盖窗内右键 = 取消截图（不让它变成"粘贴"——此刻用户心智在"截图会话"里）；确认进剪贴板之后，**任何应用**的右键粘贴才生效（含本项目聊天框）。
- 窗口模式高亮：1px accent 边框 + 4% 染底（遵守 impeccable side-tab 反模式纪律），窗口 rect 抖动消除（连续 hover 同一 HWND 不重绘）。
- 多显示器：光标所在屏进入；选区跨屏 V1 不支持（画到副屏边缘即停），架构预留。

## 剪贴板实现要点

windows-rs 直写（不引入 tauri-plugin-clipboard-manager——它不支持多格式图片直写，且这是系统级操作，Rust 侧做更干净）：

1. `OpenClipboard(hwnd)` → `EmptyClipboard()`
2. `SetClipboardData(CF_DIB, ...)`：BITMAPINFOHEADER + 像素（自下而上 DIB），保证老应用兼容
3. `RegisterClipboardFormatW("PNG")` + `SetClipboardData`：新应用优先取 PNG（无损、带 alpha）
4. `CloseClipboard()`；失败路径（剪贴板被占用）重试 3 次 × 50ms，仍失败 toast 报错

## 里程碑

- **M1 单屏闭环**（核心价值，先交付）：单显示器抓屏 → 覆盖窗矩形选区 → 剪贴板双格式写入 → 标题栏按钮 + 默认热键 → 聊天输入框粘贴出图。判据：任意应用右键粘贴出正确图像，DPI 125%/150% 下选区位置精确。
- **M2 窗口模式**：HWND 几何识别 + hover 高亮 + Tab 切换 + 模式工具条。
- **M3 配置化**：热键可配置 + 冲突提示 + 开关；多显示器覆盖窗（每屏一窗，跨屏选区）。
- **M4 打磨**：尺寸标签、暗幕亮度渐变、`PrintScreen` 原生键接管、失败重试完善。不做：编辑标注、滚动截图、延时截图、录屏（YAGNI，需要时另立笔记）。

## 对抗评审（什么场景会崩）

1. **UAC/提权窗口截图**：覆盖窗非提权，截提权窗口（任务管理器）会黑块/被排斥——SetWindowDisplayAffinity 无法反向。接受此限制（所有非提权截图软件同样如此），文档标注。
2. **覆盖窗抢焦点**：全屏置顶窗必然成为前台——原窗口的 hover 状态/悬停菜单会消失。这是截图工具固有行为（Snipaste 同样），用户心智已接受；窗口模式靠"进入截图前抓屏"缓解（画面是真实的）。
3. **多显示器 DPI 混排**（125% + 100% 双屏）：坐标换算最易错点。换算表单点维护 + M1 先只支持光标所在单屏，把跨屏问题推到 M3。
4. **剪贴板被其他进程长期占用**（云剪贴板工具）：重试后仍失败要给明确报错，不能静默丢图。
5. **热键被占用**：注册失败必须可见（toast），默认 `Alt+Q` 冲突率已尽量压低，但用户机器不可控，改键入口必须在失败提示里直达。
6. **游戏/独占全屏**：GDI 抓不到独占模式画面（黑屏）。xcap 底层 Windows 用 GDI；独占全屏游戏场景接受黑块（非目标场景）。
7. **覆盖窗自己被截入**：由"先抓后盖"根除；若未来加"延时截图"（M4 后），需临时隐藏覆盖窗再抓，注意时序。
8. **右键语义冲突**：覆盖窗内右键=取消，与"右键粘贴"是两个上下文（截图会话内 vs 会话外），文案与交互上明确（覆盖窗内右键即退，无菜单），不会混淆。

## Alternatives considered

- **`Ctrl+S` 作默认热键**：用户初始提议，被否——系统级"保存"键冲突（见热键选型节），保留为可配置项。
- **tauri-plugin-screenshots（社区插件）**：功能止步于全屏抓取，无选区交互/窗口识别/剪贴板双格式，核心交互仍要自写，引入后反而多一层抽象。不用。
- **scap/windows-capture crate**（WGC/Graphics Capture API）：性能优于 GDI 且能抓 HDR，但 API 面大、Windows 10 1903+ 才可用，且本项目截图是"交互后裁剪"场景——GDI 一次性抓帧足够，性能瓶颈在交互不在抓屏。保持 xcap（内部即 GDI），WGC 留作性能证据不足时的升级路径。
- **复用现有浏览器 `navigator.mediaDevices.getDisplayMedia`**：Web API 有授权弹窗、无窗口 HWND 几何、无系统热键，体验达不到契约。否。
- **集成外部截图进程（Snipaste CLI/ShareX）**：便携版要求零外部依赖，且违背"有轮子用轮子"的边界——轮子指库，不是把用户机器上可选软件当依赖。否。
- ~~**编辑标注（画笔/马赛克/文字）**：用户未要求，YAGNI~~ —— **2026-10-08 用户明确要求，已实现**（ScreenshotEditor.tsx：框选/画笔/文本/涂抹/裁剪/撤销 + 色板，选区后进编辑器、完成才复制）。仍不做：滚动截图、延时截图、录屏。

## Consequences

- 新增 1 个 Rust 模块（~750 行）+ 1 个前端覆盖窗（~400 行）+ 2 处现有文件小改；新 crate 依赖仅 `xcap`；`windows` crate 增加 `Win32_UI_WindowsAndMessaging`/`Win32_System_DataExchange` 等 features（编译时间 +数秒）。
- 全局热键常驻：一个 Alt 级组合被系统占用（可配置/可关闭，默认开）。
- 截图会话期间覆盖窗全屏置顶——本应用自身若正在执行长任务（如 automation 跑批）不受影响（覆盖窗独立 window，不阻塞主窗）。
- 剪贴板内容会被覆盖（截图即覆盖用户剪贴板原内容）——标准截图软件语义，不做事前备份（剪贴板历史由 Win+V 系统功能承担）。
- 端到端验证需人工：热键在真实桌面、多屏、DPI 混排、各应用粘贴兼容性（微信/浏览器/WPS）均需手测，自动化只覆盖裁剪与坐标换算的纯函数部分。

## 2026-10-10 回归与结构修复（"启动慢 + 全屏样式"）

用户报修：截图"启动慢、样式是全屏"，且 9945d406（10-08 白屏根修）"之前测过生效"。回归根因三层叠加：

1. **9945d406 只在 JS 层删 splash，兜底路径没堵住**：`#splash` 是 index.html 静态 HTML，覆盖窗加载即渲染（全屏启动屏样式，亮色白底）；JS 移除要等 bundle 加载完。Rust 侧 3s 兜底 `show()` 在页面加载超 3s（vite dev 冷启动、首开 WebView2、机器忙）时先把窗口亮出来——用户看到的就是"全屏白/黑启动屏糊在截图覆盖层上"。条件不同（dev server 热不热、何时测）表现就不同，所以"修好过又回去了"。
2. **覆盖窗加载整份主应用 bundle**：main.tsx 静态 import App，覆盖窗（dev 走 vite dev server 网络拉取）把整套聊天 UI 几百个模块拉一遍，首帧数秒。
3. **串行链路全程隐藏**：抓屏 → 整帧 PNG + base64 → 建窗 → 页面加载 → 多 MB IPC → 解码 → 才 show。

结构修复（同日落地）：

- 窗口在抓屏后（~200ms）即创建；幕布 **JPEG（q80）** 编码移到后台线程与页面加载并行；前端 **轮询** `screenshot_frame_data`（None/Ready/Failed 三态），Ready 才 show。感知等待 = max(编码, 加载)，且页面首帧有静态「正在截取屏幕…」占位（#overlay-boot，CSS data-overlay 控制，JS 崩了也显示）。
- 3s 兜底 show 废除，改 **30s 兜底关窗 + 主窗 toast 报错**：窗口要么 Ready 后被前端亮出，要么 30s 强制收尾，绝不留隐形死窗，也绝不会亮出半就绪页面。
- 编辑器基底改走 `screenshot_crop_data`（选区无损 PNG，按需裁剪）——幕布 JPEG 只服务选区交互，编辑输出不走幕布质量。
- main.tsx 拆分：覆盖窗只加载 ScreenshotOverlay 小依赖图，主应用（App/api/Toast/主 CSS）全走主窗分支动态 import；`#splash` 对覆盖窗 CSS 静态隐藏（JS 移除保留为兜底）。
