# Decision Note: 阿黎的心跳巡查 —— 2 分钟一次、零 LLM、异常才出声

Status: implemented — 2026-11-06。新增 `lib/twinPatrol.ts`（纯函数 + 单测）与
App 顶层 2 分钟心跳：检查卡住 / 待补充 / 上一批失败 / 工单失败 / 队列根本没被
拉走，结果进状态页「巡查」块与右翼「等你决定」（每条带一键入口）。
配套：`【退回】` 退回机制 + blocked 不参与拉取 + 面板「补充 / 取消」。
前端 tsc / vitest 本机跑不起来（node_modules 是悬空 junction），已用 TypeScript
单文件解析校验语法。

## Decision

用户 2026-11-06 提的循环是"每 2 分钟检查有没有任务要拉、进度如何、要不要她出手"。
关键判断：**这个循环不能花 LLM**。2 分钟一次 × 一天 = 720 轮；绝大多数时候答案
是"没事"，成本与信息量都不成立。所以拆成两层：

- **快循环（已有，4s）**：面板非空 + 空闲 → 拉一批开工。负责吞吐。
- **心跳（新，2 分钟）**：只做**机械可判定**的巡查，负责发现异常：
  | 判据 | 结论 | 界面动作 |
  |---|---|---|
  | 在跑 + 距**最后活动** > 15min | 疑似卡住 | "停止这一轮" |
  | `batch.status === failed` | 上一批发不出去 | 去任务面板（带原始原因） |
  | 队列里有 blocked | 等你补充 | 去任务面板 |
  | 本批窗口内工单 failed/cancelled/timeout > 0 | 团队出事 | 看团队看板 |
  | 空闲 + 队列等 > 60s 还没被拉走 | 拉取链路没生效 | 去任务面板 |
  | 工单接口失败 | **查不到**（≠没有工单） | 如实显示"查不到" |

- **待办去重**：有审批/澄清时不再报"卡住"——她停下来等你，不是挂了；
  等待本身已经在「等你决定」里。
- **空转不刷噪音**：没有任何 finding 时只更新"上次巡查 HH:MM:SS · 无异常"，
  不产生记录、不弹通知。
- **定时器不假设精确**：30s 检查一次是否到期（`Date.now() - lastPatrol >= 2min`），
  窗口隐藏被 Chromium 节流、系统休眠之后，恢复时下一次 tick 立刻补做。
- **巡检互斥**：`twinPatrolBusyRef`，工单请求慢时不叠请求。

配套的**退回机制**（同一轮落地）：

- 指令新增：缺关键信息就没法动手的需求，**不猜**，回 `【退回】<需求> → 缺 <什么>`；
  能从上下文推断的按最省事的假设做并注明。
- 前端解析退回行 → `matchReturned()` 按需求原文对齐（字符归一后互相包含；
  本批只有一条时按要点兜底）→ 命中的**从本批摘掉、放回面板标 blocked**，
  带退回原因与次数；对不上的行不处理（宁可不办，也不张冠李戴）。
- **blocked 不参与拉取**，否则 4s 快循环会"拉走 → 退回 → 再拉走"烧钱死循环；
  面板给「补充」（取回草稿改完重新下达）/「取消」两条路，退回 3 次后标注
  "补充后再提交"。

**巡查发现进执行回路（L3-lite）**：`patrolBrief()` 把发现压成一段
「【上一批情况】…」，由**下一次拉取**捎在批次指令前面，一次性消费。
作用是让她在同一轮开工前自己权衡（失败工单重派还是放弃、久无动静继续等还是
收尾），而不是每出现一次异常就单独发一轮问她"要不要干预"——后者既多烧一轮
对话，又容易从"给建议"滑成"直接动手"。

**自动干预开关（L3，默认关）**：状态页「巡查」块底部一个开关
（`hermix.desktop.twin_auto_intervene`）。打开后，只有同时满足下列条件才
单独叫她一次：有 warn/alert 发现、她空闲、没有待审批、**面板里没有待拉取
的需求**（有活让 4s 快循环先走）、距上次自动触发 ≥ 10 分钟。指令明确要求
"能就地处理就处理，不需要处理就回一句结论"——这是唯一允许她没人叫也动手的
路径，所以默认关，开关上直接写明代价。

## Alternatives considered

- **2 分钟让 LLM 巡查一次**：720 轮/天，成本不可控，且会把"我要不要干预"变成
  常态动作（她开始自己找活干）。否决。
- **卡住按批次开始时间判定**：长编译/大文件下载十几分钟没有事件是正常的，
  按开始时间算天天误报。改为按最后活动时间。
- **卡住就自动停止**：杀进程的代价远大于多等十几分钟，只提示 + 给停止按钮。
- **退回时自动重试**：会死循环；改为 blocked 锁住，等人补充。
- **异常时单独发一轮"要不要干预"**：每次异常多一轮对话，且她可能顺势动手
  （有终端和团队权限）。改为把情况注入下一批指令，零额外调用、零自主行为。
- **心跳放 sidecar（关窗也跑）**：窗口关掉时她也不能发消息给你，收益低；
  放前端可随窗口/托盘存活，且能直接读流状态与审批。
- **自动重派失败工单**：有副作用（重复执行），第一版只给建议 + 一键入口。

## Consequences

- 巡查只在前端活着时运行（关窗进托盘仍算活着；真正退出进程就停）。
- 心跳不产生通知，只在状态页/右翼体现；不打扰但需要你主动看一眼。
- "是否需要她出手"目前止于**提示 + 一键动作**，没有自动决策。
- 退回依赖她遵守 `【退回】` 格式；没写就当作没退回（会照常执行），
  这是有意的：宁可多跑，也不让前端凭猜测把需求扣下来。

## Reintroduction conditions

- 需要"关窗也巡查" → 把巡查搬到 sidecar 的 scheduler（已有 automation 调度器），
  前端只读结果。
- 需要她真的做干预决策 → 在 finding 上加"叫她看"的开关（一次短对话），
  默认关；先观察误报率再开。
- 需要按需求粒度追踪完成度 → 见 `2026-11-06-twin-task-queue.md` 的
  `requirement_id` 方案。
