# Decision Note: 分割线密度规则（两允许、两禁止）

Status: implemented — 2026-10-11 拍板并全量落地。

## Decision

界面里画一条横向分割线，等于宣称"这两块内容的关系和别的内容不同"。当每个
列表项、每张卡片、每块 diff 之间都画线时，这句宣称失去信息量——线不再是
层级信号，只是噪声，用户看到的是一片灰白的横纹而不是内容。

规则收敛为**两允许、两禁止**：

**允许**
1. 容器顶边 1 条——对话框 / 模态 footer / 工具栏与内容区边界。每个浮层或
   区域至多一条，作用是声明"这里换了一个容器"。
2. 菜单内部的功能分组线——下拉菜单里"复制 / 粘贴"与"分享"之间，线在表达
   一组相关动作，与列表分隔不同义。

**禁止**
3. 列表逐行线——设置行、模型项、review/subagent 列表项、展开的文件清单。
   行距 + hover 底色已经承担扫描分隔，逐行线是重复表达。
4. 卡片内虚线"缝线"——diff 块之间、操作条上方、审批卡结算脚上方。虚线读作
   "缝合的盒子"，与"这里是独立卡片"的语义矛盾；块标题（文件名 / 相位点）
   加间距已建立层级。

依据是内置设计 skill（`impeccable-design.md` 原则 3「层级靠字号/颜色/间距
表达」）——去线不是减装饰，而是把层级从"线"移到"间距和排版"这两个真正
承载信息的通道上。

## 落地范围

| 位置 | 处理 |
|---|---|
| `ui/SettingsRow.tsx` `SettingsGroup` | `divided` 默认 `true → false`，行间线取消（影响全部设置页） |
| `settings/ModelListTab.tsx` | 逐行 `border-b` 取消，留 hover 底色 |
| `styles/components-layout.css` `.review-row` / `.subagent-card` | 逐行线取消，卡片改 2px 间距 |
| `styles/components-tool-card.css` `.apv-diff-block + …` / `.apv-actions` | 两条虚线取消，间距 10px → 16px / 4px → 14px |
| `styles/inline-approval-card.css` `.approval-resolved-footer` | 虚线取消，同时从 transition 移除 `border-top-width`（layout-transition 反模式） |
| `styles/components-prose.css` `.fcx-list li + li` | 逐行线改 4px 间距；容器顶边线保留 |
| `bubbles/ToolOutputPreviews.tsx` | caption 条上下双实线（三明治）全删，靠 40% 染底色分层 |

**不动**（这些线合规，不是"过多"）：模态 / 对话框 footer、工具栏与内容区
边界、菜单内分组、数据表格行线（`DiagnosticsTab` 等真实表格）、代码预览
h1/h2 下的标题分隔、`.app-detail-filebar` 活动 tab 的 2px 下划线
（tab 的选中指示物，不是分隔线）。

## Alternatives considered

- **只删设置页的行间线就收工**：设置页确实是最密的一处，但逐行线在模型列表、
  review 列表、工具卡 diff 里同样存在。用户反馈的是"分割线过多"这个整体
  观感，按点位逐个打补丁会留下一套没有共识的例外——所以定规则而不是定点。
- **把线调淡（改用更浅的 border token）**：保留结构、只降对比。否决——
  线的问题不在可见度而在**数量**：五条 8% 透明度的线仍然把内容切成六段，
  扫视路径被切成六次跳。淡化是掩盖不是修复。
- **反过来加线、统一加粗**：视觉上更"整齐"，但违背内置设计 skill 原则 3，
  且把层级表达完全押在描边上——4K 屏上 1px 线在高对比桌面下依旧刺眼。
- **逐行线换成 `divide-y` 之类工具类**：实现等价，仍然是逐行线，不解决问题。

## Consequences

- 设置页整屏线数减少约 40%（每组 N 行从 N−1 条线降为 0）；对话内工具卡的
  虚线缝线全部消失；工具输出预览条少两层"三明治"线。
- 分割线的语义重新变得可读：屏幕上还剩下的线一定在声明容器边界，扫视时
  可以放心跳过。层级改由行距、底色、字号承担。
- 逐行线消失后**行高成为唯一分隔线索**：长列表（上百个模型、百个文件命中）
  靠 hover 底色定位，键盘/触屏滚动时定位感略弱于有线。这是本规则接受的
  代价——若将来出现实测的定位困难，正确解法是加大行距或加 sticky 表头，
  不是把逐行线加回来。
- 没有引入新令牌、新组件或新依赖：规则落在既有 `border-subtle` 之上，
  逐个 CSS 规则删除即可。`SettingsGroup` 的 `divided` prop 保留（默认关闭），
  确需"表格感"的分组仍可显式开启。
- 规则需持续执行：新增列表/卡片时默认不带逐行线。已落地的位置在代码里留
  了「分割线规则（2026-10-11）」注释，detect 不覆盖这类约定，故以注释固化。

## Reintroduction conditions

本笔记是规则而非功能，无"功能回归"问题。若将来出现以下情形，说明这条规则
在那个局部确实被误伤，可局部破例（不必推翻全局规则）：

- 某个列表**确实承担表格语义**（列需严格对齐、需按列比较数值），逐行线
  表达的是数据关系而非容器关系——数据表格的行线本就在允许范围内。
- 某个列表项**存在状态差异且行距不足以表达**（如审批流中"待决 / 已完成"
  两态需一眼区分），可给状态变化那一侧加线或加底色，仍不是全线。
- 出现实测的扫视定位困难（用户反馈长列表找不到行），先加行距或分组小标题，
  两者无效再考虑逐行线。
