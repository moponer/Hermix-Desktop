# Decision Note: 阿黎的任务面板 —— 输入即下达、面板即优先级、归类归她判断

Status: implemented — 2026-11-06。输入口改为「下达需求」入队；她按面板顺序
定时拉取一批开工，**由她判断每条需求与当前任务是否同一件事**（并入同一任务线
或新开），判断结果以 `【归档】` 行原样上报；状态页展示本轮需求、她的归档判断、
发布到团队的流水；团队看板按批次起点筛工单。前端 tsc / vitest 本机跑不起来
（node_modules 是悬空 junction），已用 TypeScript 单文件解析校验语法。

## Decision

用户 2026-11-06 实报四件事，前三条是同一根因的三张脸：

1. 输入框是「聊天」——她输出未结束时被禁用；用户也无法表达优先级。
2. 错误提示与实际不符：截图上是「这一轮没发出去（原因见下方错误）」，
   而下方没有任何错误文本。
3. 值守页「刚才发生」只有工具名（`terminal`），看不出跑的是什么命令。
4. 放手模式配了仍在问（见 2026-10-28 / 2026-11-06 两篇笔记）。

决策：**把输入口从"对话"改成"下达需求"，用任务面板承载优先级，把"是不是
同一件事"交给阿黎判断。**

- **队列**（`lib/twinQueue.ts`，纯逻辑 + 单测）：`{id,text,createdAt}` 数组，
  顺序即优先级；`↑/↓` 交换相邻项，删除即时生效；落
  `localStorage["hermix.desktop.twin_queue"]`，关窗口不丢未开工的需求。
- **拉取**：每 4s 一次 tick（App 顶层，切页照跑），空闲且面板非空 → 取
  **队首最多 6 条**（`BATCH_MAX` 是消息体量上限，不是语义分组）→ 编译成
  带编号清单下发。轮次结束**立即接力**，不等 tick。
- **归类/并批由她做**：指令明确要求「先判断，再动手」——逐条比较这条需求与
  她当前正在做的任务、以及本批其它需求；是同一件事就并入同一任务线
  （沿用已派工单/成员，不重复开工），不是就新开。每条先写一行
  `【归档】<需求要点> → 并入|新开 <任务名>`。
- **前端只摘不猜**：`verdictLines()` 从回复里摘 `【归档】` 行**原文**，
  状态页照登；她没写就显示"没写"，不拿关键词反推一个分类。
- **界面**：中轴四态 `对话 / 任务面板 / 团队看板 / 状态`。任务面板只显示
  待拉取（拉走的只剩一行"本批 N 条 · 状态"）；状态页有「本轮需求」「她的
  归档判断」「发布到团队」（delegate_task / assign_task / task_create /
  task_update / review_result 的原始行）。团队看板增 `since`，按批次开始
  时刻筛工单 —— 这是"这批需求派出去了什么、做到哪一步"。
- **错误如实**：入队是纯本地操作，不产生"发送失败"；下发失败时原因写在该
  批次上（原始文本）。**动过手不自动回队**（删文件/发消息/交作业都不幂等），
  面板给「把这一批放回面板」的显式入口；完全没发出去才自动放回。

## Alternatives considered

- **按关键词归类再合批（上一版，已撤回）**：把需求分成 学习/查询/整理…，
  相邻同类并成一批。用户当场指出这是错的 —— "把课程刷完"和"把作业交了"
  都归学习但未必该并成一条任务线；"整理笔记"和"写周报"分属两类却可能正是
  同一件事的两半。关键词判不出语义，归类交还给她。
- **mid-turn 注入（流式期间把新需求塞进当前轮）**：协议层没有 steer 通道；
  流式期间到达的 Text 帧由转发循环吞下、当前轮结束后再重新驱动
  （`StreamSendOutcome::DeferredUserMessage`），本来就是"下一轮"；若落到
  `handle_ws_stream_send` 入口还会命中 `task_in_flight` 分支回一个终态
  Done，把正在看的流提前结算。收益为零、风险是丢流，**不做**。
- **后端建队列表 + HTTP 端点**：队列是"这台机器上这个人的待办"，没有跨设备
  一致性需求；新端点要接鉴权/迁移/清理，收益不抵成本（见 Reintroduction）。
- **每批内单条需求打"完成/未完成"**：后端没有按需求粒度的完成信号，
  标了就是假进度。完成情况由团队看板的真实工单承担。
- **拖拽排序**：`↑/↓` 已满足"手动调优先级"，键盘可达、无拖拽命中区问题。

## Consequences

- 她只在**应用运行时**值守：窗口关掉，面板里的需求留在本地等下次打开。
- 队列是**本机偏好**，不随 `twin:ali` 会话跨设备同步（手机端投递仍走原来的
  `target=twin` 路径）。
- 「并入当前任务」只能在**轮次边界**发生：新需求在本轮结束那一刻接入同一
  会话/同一任务线，不会打断正在跑的那一轮。
- 单轮最多 6 条；一天里排在后面的需求会在前一批结束后按面板顺序接上。
- 团队看板的「本批」是**按开工时刻**近似的：工单没有需求 id，若复用本批
  之前就在跑的长工单，它不会出现在本批视图里。
- 无人值守的自动化独立会话不受影响：仍按默认权限档跑（不继承值守页的放手档）。

## Reintroduction conditions

- 需要手机端也看到/调整同一个面板 → 队列入后端（`/api/twin/queue`），
  localStorage 降级为离线缓存。
- 需要按需求粒度追踪完成度 → 给 `assign_task` / 工单加 `requirement_id`，
  团队看板改为按 id 聚合，替代按时刻筛选。
- 协议层出现真正的 steer 通道 → 新需求可即时并入正在跑的那一轮，替代
  "轮次边界接入"。
