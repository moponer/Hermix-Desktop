# Decision Note: PDF 页面标注 —— 自建编辑面 + 标准注释写回（不 lift 官方批注引擎）

Status: implemented — 查看器 PDF 编辑器新增「标注」模式：自由文字 / 高亮 / 墨迹 / 图章 / **手写签名域** / **空签名域**写进 PDF；页内文本替换从只认 `Tj` 扩到 `Tj` / `TJ` / `'` / `"`；写出的文件经 pdf.js 交叉验证可被真实阅读器识别

## Decision

PDF 编辑器从「只能管页面 + 整串替换文字」扩到「能在页面上写字、划高亮、画墨迹、盖图章、签名」，产物是 PDF **标准注释**：

- 自由文字 → `/Subtype /FreeText`（`/Contents` + `/DA` + `/C`）
- 高亮 → `/Subtype /Highlight`（`/QuadPoints` + `/C`）
- 墨迹 → `/Subtype /Ink`（`/InkList` + `/BS` + `/C`）
- 图章 → `/Subtype /Stamp`（`/AP` 外观流 + 图片 XObject）
- 手写签名 → **AcroForm 的 `/Sig` 域**（`/Subtype /Widget` + `/FT /Sig` + `/AP` 外观流）
- **空签名域** → 同样是 AcroForm 的 `/Sig` 域，但**没有签名位图**（`/V` 缺席 = 还没人签），只留一个带边框的框

写回走 Rust（lopdf 0.34，`pdf_add_annotations` 命令），编辑面是自绘的 React 覆盖层（画布用 pdf.js 渲染，标注用绝对定位层叠加），坐标经 `viewport.convertToPdfPoint()` 换算成 PDF 用户空间。

**手写签名与图章的区别在于"它是什么"**：图章是普通注释（Acrobat 里显示为一张图）；签名是 **AcroForm 的签名域** —— 还要在 catalog 上挂 `/AcroForm`（`/Fields` 收签名 widget、`/DA`、`/DR`、`/SigFlags 1`），这样 Acrobat / 福昕 把它显示成"签名"（可双击重签、可校验），而不是一张贴图。前端对应一个**签名板**：独立画布上手写 → 自动裁掉四周空白（按 alpha 扫包围盒）→ 导出透明 PNG → 在页面上拖框放置。

**页内文本替换同步扩面**：从「只认 `Tj` 算子」扩到 `Tj` / `'` / `"` 以及 **`TJ` 数组里的每个字符串项**。旧实现漏掉 `TJ` 是实际影响很大的坑 —— Word / LaTeX / 报表工具生成的 PDF 大量用 `TJ` 数组做字距微调（一句话被拆成十几段），于是用户明明看得见那行字，替换却报"未找到"。替换时用**同一字体的编码**把新文写回（`Document::encode_text`），中文不会乱码。

**没有采用 pdf.js 官方 AnnotationEditor**（本轮评估后否决）：官方引擎写进文件的本来就是上面这几种标准注释，产物一致；但 `AnnotationEditorLayer` 对 `AnnotationEditorUIManager` 有 **40+ 处调用**（`getMode` / `combinedSignal` / `commitOrRemove` / `addToAnnotationStorage` / undo 栈 / `eventBus`…），而那个管理器的构造函数要 **16 个参数**、绑着官方 eventBus、altText 与 signature 管理器、undo bar、l10n。单独 lift 等于重写半个官方查看器；带官方外壳进来则整个 PDF 界面换成 pdf.js 的样子，与本应用的视觉体系冲突。**于是：引擎的产物用标准注释复刻，交互与视觉自己做。**

图章的做法与前三种不同：注释只存位置，**长什么样在外观流里** —— 图片编成 JPEG 放进 `/XObject /Image`（DCTDecode），外观流是 `/XObject /Subtype /Form`，`BBox` 取注释矩形，内容 `q w 0 0 h x y cm /Im0 Do Q` 把图铺满矩形。图片路径由用户在系统文件对话框里自己选，Rust 侧读文件（不把图片塞进 IPC 载荷）。

写注释时踩到的两个坑（都写成了注释钉在代码里）：

1. **`/QuadPoints` 必须是扁平的 8n 个数**，不是数组的数组。写成嵌套数组时 pdf.js **静默丢弃这条高亮**（不报错、只是不显示）—— 最难查的一类失败。
2. **PDF 字符串非 ASCII 必须是 UTF-16BE + BOM**。把 UTF-8 字节直接塞进字面串是非法的，阅读器按 PDFDocEncoding 解 → 中文乱码。现在统一走 `pdf_text()`。
3. **拖框时不能改草稿的 kind**（2026-10-21 修）：拖拽过程更新矩形时，把草稿种类写死成"高亮" —— 于是**放图章、放签名拖出来的都是一条黄色高亮**。这类 bug 的特征是「后端完全正常，前端产物类型错了」：Rust 侧的类型分支都写对了，坏在前端把 kind 覆盖了。

## 空签名域（留给别人签）

手写签名是「替人签好」，空签名域是「留个框让别人以后签」——合同发给对方签字时需要的是后者。手写签名那条路做不到（它必须带一张签名位图）。

做法与手写签名共用同一套结构（`/Subtype /Widget` + `/FT /Sig` + 登记进 `/AcroForm`），差别只有两点：**没有签名位图**、**没有 `/V`**（`/V` 是签名值域，缺席即「尚未签署」）。另外给它写了一个**只画边框的外观流**（`0.7 w 0.45 G … re S`）—— 没有 `/AP` 的话，部分阅读器把域画成「什么都没有」，用户根本不知道这里能签。

PKI 数字签名（可验签、带证书与时间戳）**不做**：要引入证书体系与新依赖，与「便携、零安装、文件不出本机」的前提冲突。

## Alternatives considered

- **整体换成 pdf.js 官方查看器外壳**：能力最全（表单、查找、缩略图、官方批注 UI 一并到手），但把 PDF 界面整个换成别人的样子，两端共享预览层都要跟着变；为了三个批注工具付这个代价不划算。
- **往页面内容流里插字**（真正"印"在纸上）：标准 14 号字没有中文字形，中文渲染成空白；要正确显示必须嵌入并子集化中文字体（引入新依赖 + 授权与体积问题）。
- **只做便签批注就收工**（上一轮的做法）：便签是"贴在页边上的话"，不能写在正文位置；用户要的是"在这一行写个字 / 把这几行涂黄"。
- **自己写一个 PDF 渲染层**（不用 pdf.js）：pdf.js 已经在用，没有理由再造一遍。

## Consequences

- 页面上的标注是**注释层**，不是"烧进内容流"：在 Acrobat / 福昕 / Edge 里能看见、能继续编辑、能被别的工具识别；但也意味着**改不动已烧进内容流的原始文字**（那是另一条能力，PDF 本来就不支持）。
- 中文/emoji 在别的阅读器里靠**阅读器自己的字体替换**渲染（pdf.js 与 Acrobat 都会替换）；个别严格的阅读器可能显示不出 FreeText 的字形。批注内容本身是完整保存的，不丢。
- 页内文本替换仍然是**整串精确匹配**（不是"选中即改"）：能改的只有"整段文字原样出现"的情况；文字被拆成多段、用了字距微调、或字体编码解不出来时，仍然报"未找到"。这是 PDF 的物理约束 —— 它没有段落与行的模型，只有绝对定位的绘制指令，**做不了 Word 式的重排**。真正的"编辑正文"只能靠转成可编辑格式（PDF→Word 需要 LibreOffice/商业引擎）。
- 图章是**追加**语义：一次写入一批，导出新文件；连续多批需要自己依次套用产物。
- 签名是**手写签名**，不是**数字签名**：没有 PKI 证书、没有 PKCS#7/CAdES 封装，因此 Acrobat 里它是"一个可重签的签名域"，**不是**可验证的已签名文件。要做真数字签名得引入证书体系（证书存储、私钥、签名算法、时间戳），那是另一个量级的工程。
- 官方引擎还有一样我们仍然没有的：**成熟的编辑器内撤销栈**。撤销目前是"删掉刚画的那条"。
