# Decision Note: 手机端被撤凭据的判活探测与终态停机

Status: implemented — `relayClient.ts` 握手连续被拒时以 `/health` 判活，判死即终态停机；聊天页失效横幅带「去处理」直达设备管理（hm 62 tests + vue-tsc 全绿）

## Decision

电脑端撤销配对后，手机端不再无限重试。`apps/hm/core/relayClient.ts` 的出站
连接循环增加一条判据：**握手连续失败 ≥2 次**时，用 `GET {relay}/health`
（无需凭据、恒 200）探测中转——

- health 不可达 / 非 200 → 是网络或中转问题，什么都不改，照常退避重连；
- health 200 但握手仍被拒 → 中转活着，被拒的只能是这条凭据（撤销/换绑），
  **终态停机**：清掉重连定时器、置 `closed`，报出可行动文案
  「中转在线，但拒绝了这台手机的凭据——多半是电脑端已撤销配对。
  到『设置 → 已配对的电脑』移除这台电脑，重新扫码即可」。

配套两处：`session.ts` 识别该终态文案并销毁失效 client（与既有 401 分支
同一出口）；聊天页链路横幅对终态文案渲染「去处理」按钮，直达设置页设备
管理区（移除入口本就存在，缺的是从报错状态到它的路标）。

动机：relay 对被撤凭据的拒绝发生在 **WS 握手期（HTTP 401）**，而 App 端
原生 socket 的 `onError` errMsg 不透出状态码——`/401|unauthorized/` 的
既有判断在真机上永远匹配不上，于是「凭据已死」走了「网络抖动」的分支，
无限退避重试（上限 30s 一轮），横幅永远显示「relay 连接错误，Xs 后重连」。
现场实测（2026-10-15）：撤销后手机端循环重试一整天，用户既看不到撤销事实，
也找不到处置入口。health 探测是 App 端唯一可靠的「中转在线但拒绝我」信号。

顺带修一个 pre-existing 缺陷：`onError` 与 `onClose` 对同一次握手失败常
先后到达，各自 `scheduleRetry` 会叠出两条并行重连循环。现在重连定时器
只允许排一个（`retryTimer` 互斥），`close()` 与终态停机都会清掉待触发的
定时器。

## Alternatives considered

- **relay 加凭据校验端点**（如 `GET /api/relay/validate`，Bearer → 200/401）：
  否（本次否决，非永久）。它是最精确的判死信号，但要改 `apps/relay` 并重新
  部署才能生效——手机端的问题不该卡在服务端发版上。若日后需要区分
  「撤销」与「换绑/角色错误」，再上这个端点不迟。
- **继续只靠 errMsg 正则匹配 401**：否。它在 H5/开发者工具里碰巧工作，
  在 App 原生 socket 上永远失配——这正是线上现象。保留该分支（有的平台
  确实透出状态码），但不再作为唯一判据。
- **连续失败 N 次后停止重试（不看 health）**：否。弱网/地铁场景的重试
  是有意义的，盲目停机会把「暂时连不上」误报成「凭据已死」；health 探测
  把两者分开，代价只是一次 5s 超时上限的 GET。
- **把「已撤销」持久化进 DeviceRec（列表标失效）**：本次不做。判活是
  推断不是事实（health 200 + 握手拒也可能是网关升级类部署故障），持久化
  会让错误推断沉淀成用户看到的状态；终态消息 + 处理入口已闭环，先不加态。

## Consequences

- 被撤凭据的手机在 ~2 次握手失败 + 一次探测（约 6–8s）后停机，横幅从
  无限刷新的「Xs 后重连」变为稳定的一句终态文案 + 「去处理」按钮。
  用户重新扫码配对后自然恢复（新凭据、新 client）。
- 若 relay 出现「health 正常但 WS 网关坏了」的部署故障（nginx 丢升级头等），
  会被误判为凭据问题。文案用「多半是」保留余地，且处置路径（移除重新配对）
  对该场景无害。
- `scheduleRetry` 的单定时器互斥是行为修复：此前双触发时退避计数会被两条
  循环交错推进，重试节奏不可预期。
