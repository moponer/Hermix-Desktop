# Decision Note: 文件索引的重建入口、主动建索引与真实状态

Status: implemented — 2026-10-23 落地（查看器「资源管理器 → 文件索引」页）

## Decision

本机文件索引（`crates/hermix-filesearch` + 查看器「资源管理器」弹窗的**文件索引**页）
按四条规则重做「看得见的进展」：

1. **重建索引是协议里的一等公民**。helper 的 JSONL 协议新增 `rebuild` 方法
   （`crates/hermix-filesearch/src/bin/daemon.rs`），立即返回并转后台任务；
   进度通过既有的 `status` 轮询给出（每卷独立阶段 + 计数）。
   **为什么必须立即返回**：一次全盘 MFT 扫描要几十秒到几分钟，而协议层读取
   超时只有 15s——同步等必然超时，用户只会看到「点了没反应」。
2. **索引主动建立**。helper 启动即发现卷并建缺失的索引；卷探测每 30 秒补漏
   一次（只登记新卷，不动已有索引）。查看器进入「文件索引」页时，若服务未起
   就提权起、起了但无数据就自动重建一次（前端 `autoRan` 去重 + 服务端
   `rebuilding` 去重）。
3. **状态字段全部为真值**。条目数 = 索引内条目数；已索引体积 = 索引内文件字节
   和（`SearchIndex::total_bytes` 增量维护，不再是死值 0 B）；上次同步 =
   **最后一次有实际变更**的同步时间（USN 每秒轮询一次，若每次都刷新就是永远
   「刚刚」）；状态 = 真实状态机（未建立 / 扫描中 / 索引中 / 已就绪 / 失败 + 原因）。
4. **索引必须与本机当前卷一一对应**。快照按**卷序列号**（`GetVolumeInformationW`
   的 serial）校验：序列号对不上（换过盘、从别的机器带来的残留）→ 丢弃快照
   重建。快照格式版本随之升到 v4。

## Alternatives considered

| 方案 | 为何否决 |
|---|---|
| 重建做成同步请求 | 协议读取超时 15s，全盘扫描必然超时——「点了没反应」的根因之一 |
| 进度走 Tauri event 推送 | 要给 `IndexStatus` 加观察者、给前端加 `listen` 生命周期；轮询 2s 足够（对齐 2026-10-04 笔记「独立只读状态命令」的取舍） |
| 单独加 `viewer_filesearch_rebuild` 等 Tauri 命令 | 查看器命令要在 `lib.rs` 注册，每加一个就动一次中央注册表；改为给既有 `viewer_filesearch_status` 加 `action` 参数（status / start / rebuild），改动面收在一个文件 |
| 「上次同步」继续按轮询刷新 | USN 每秒轮询一次 → 永远是「刚刚」，用户看不出索引有没有在保鲜 |
| 用 USN journal id 判断快照是不是本卷的 | journal id 会随卷重建变化但**不随盘符复用变化**；换一块物理盘、盘符不变时它可能一致 → 挡不住「数据不对」 |
| 保留旧快照格式（不升版本） | `VolumeIndexState` 加字段后旧快照反序列化必失败，版本号只是把这件事显式化 |

## Consequences

- What we give up：
  - 旧快照（v3）全部作废，升级后第一次启动会对每个卷重建一次索引（分钟级，
    后台进行，不阻塞界面）。
  - 「上次同步」变成「最后一次有变更的时间」，没有变更时它会停在旧值——
    这是有意的：它现在表达的是「索引内容最后一次更新于何时」。
  - helper 的 `status` 响应新增字段（`totalBytes` / `state` / `message` /
    `mftReadable` / 每卷 `buildPhase` 等），桌面端 `FileSearchWindow` 按旧字段
    读取，不受影响（多余字段被忽略）。
- 代价与风险：
  - 卷探测超时不再丢弃该卷，而是明确报「卷设备无响应（探测超时）」——
    代价是 `skipped` 列表里会多出这类条目。
  - 查看器「文件索引」页首次打开会弹一次 UAC（读 MFT 的固有成本）。
  - 每 30 秒一次的卷发现会对坏卷反复探测（探测本身有 5s 超时，不阻塞）。
