# Decision Note: 菜单被内容区遮挡 —— 子 webview 让位，而不是加 z-index

Status: implemented — 查看器的标题栏下拉菜单与右键菜单在网页标签打开时不再被内容区盖住

## Decision

菜单展开时，把**网页子 webview 隐藏**（`hide()`，不是 `close()`），菜单收起后再 `show()` 回来。

## 根因：不是 z-index，是**不在同一层**

网页不是 DOM，是**独立的子 webview（独立 HWND）**。Windows 上它是主 webview 的子窗口，**永远画在父 webview 的 DOM 之上** —— 不管父窗口里的元素 z-index 写多大，都压不过一个原生子窗口。

所以症状是：菜单展开到内容区的部分，被那块网页**沿一条笔直的水平线切掉**（子 webview 的上边缘），而菜单上半截（还在标题栏区域里）露着。看起来像"z-index 不够"，实际是"根本不在同一层"，改 z-index 不会有任何效果。

## 为什么是 hide 而不是 close

`close()` 会丢掉页面状态：重新加载、滚动位置、表单里填的内容、登录态全部归零。`hide()` / `show()` 只动可见性，页面原样还在，收起菜单后立刻回到原状。

## 为什么用计数而不是布尔

标题栏菜单与右键菜单**可能同时展开**（右键菜单是在页面里触发的，标题栏菜单还开着）。用计数：任一菜单展开 → 计数 > 0 → 网页隐藏；全部收起 → 计数回到 0 → 网页恢复。

## Alternatives considered

- **把菜单的 z-index 调大**：无效 —— 原生子窗口不在父窗口的层叠上下文里。这是本次最值得记的一点：**"被盖住"不等于"z-index 太小"**。
- **把网页改用 iframe 内嵌**：能解决层叠，但会丢掉独立 webview 的收益（独立进程、CDP 调试、独立的浏览历史与 Cookie 空间），代价远大于收益。
- **菜单展开时关闭网页**：同上，会丢页面状态。
- **把菜单也做成原生窗口**：Windows 上要用 Win32 菜单，跨平台与无障碍都要重做，不划算。

## Consequences

- 菜单展开的那一瞬间网页会**闪一下**（隐藏 → 露出下方的内容）。这是"让位"的必然代价，比被整块遮住好；网页本体不受影响，收起菜单即恢复。
- 只有**查看器**做了这个处理。桌面端也有子 webview（浏览器面板），如果那边也出现"菜单被内容区遮挡"，需要同样处理 —— 桌面端的弹出层与浏览器面板不重叠时不受影响。
- `web_set_visible` 是新增的 Tauri 命令，只影响当前活动的那一个子 webview；没有活动网页时是空操作。
