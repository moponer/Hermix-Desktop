# Decision Note: relay E2EE —— 托管形态的加密层

Status: proposed — 加密粒度、密钥模型、撤销语义已定；E2EE 被 [托管 relay（2026-10-06）](2026-10-06-relay-hosted-multi-tenant.md) 列为上线门槛，而现有实现是零加密，本篇补上这一层

## 背景与缺口（已查实，非推测）

`2026-10-06-relay-hosted-multi-tenant` 定下「E2EE 为托管形态上线门槛：运营方可见明文 = 数据自主承诺破产」。而 `2026-10-04-mobile-relay-selfbuilt` 交付的实现里：

- `apps/relay/src/` 加密原语为零——grep `createCipher` / `encrypt` / `decrypt` / `aes` 全空；
- `apps/relay/src/proto.js:40-48` 主动 `raw.toString('utf8')` + `JSON.parse(text)`，**relay 不只转发，还读懂每条消息的结构**；
- `request_signature.rs` 的 HMAC 是**认证**（防冒用与重放），不是**加密**（防偷看）。两者不可互替。

单租户自用形态下这不构成问题（运营方是自己）；一旦转托管多租户，全部用户的对话内容对运营方透明。

**审计层无需改动**：已逐个核实 `apps/relay/src/` 里 `audit.write` 的全部调用点，`detail` 实参无一例外是固定枚举（`node_attached` / `phone_replaced` / `delivered` / `dropped_no_node` / `role_mismatch` / `denied` …），唯一动态值是 `delivered_x${n}`（并发连接数）。审计本来就只钉"谁在什么时间说了"，不碰载荷——E2EE 与之天然兼容。

## Decision

### 1. 加密粒度：整帧密文 + 明文路由头

帧结构拆成 `header`（明文）与 `body`（密文）：

| 字段 | 可见性 | 理由 |
|---|---|---|
| `v` 协议版本 / `type` 帧类型 | 明文 | relay 要按类型分派 |
| `from` / `to` 身份 | 明文 | relay 是路由器，不认身份就没法路由 |
| `seq` 序号 / `ts` 时间戳 | 明文 | 重放防护、限流、审计 |
| `nonce`（XChaCha24 字节） | 明文 | 密文必需 |
| **everything else** | **密文** | 消息文本、审批内容、任务记录、`sign` 签名原像 |

**不采用字段级加密**：字段级把"哪些字段算内容"变成协议约定，两端一旦版本不同步就是静默泄露；而 relay 本来就得解析帧头，分级带来的收益抵不上复杂度。

### 2. 密钥模型：P-256 ECDH + AES-256-GCM，每帧独立 ephemeral

> **2026-10-06 03:2x 修正**：初稿写的是 X25519 + HKDF + XChaCha20-Poly1305。
> **那是错的**——uni-app 各端只有 WebCrypto，**没有 ChaCha20**，只有 AES-GCM。
> 已实测确认（Node WebCrypto）：P-256 ECDH 两侧导出的对称密钥逐字节一致，
> AES-GCM 12 字节 nonce 与中文往返均正常，公钥 65 字节（未压缩）。
> 改用 P-256 + AES-GCM 后，**App 侧零新增依赖**（全部 WebCrypto 原生），
> Rust 侧 `aes-gcm` / `sha2` workspace 里已有，只需补 `p256` 做 ECDH。

- **配对时**交换长期静态公钥：`node_pub`（桌面端）、`device_pub`（手机端），均为未压缩 P-256 SPKI（65 字节）。走二维码，与证书指纹同一条通道（`relay-hosted-multi-tenant` 已定「二维码内含证书指纹」，密钥交换复用该通道，不新增交互）。
- **每帧**：生成 ephemeral P-256 密钥对 → `shared = ECDH(eph_sk, peer_static_pub)` → `key = HKDF-SHA256(shared, salt=frame_id, info=方向标签)` → `AES-256-GCM`（96-bit nonce）加密 body。
- **每帧一个独立 ephemeral**，因此单帧密钥泄露不影响其他帧——这已经是前向保密的最小实现。

**不实现 Double Ratchet / X3DH**：本链路是单向控制流（手机发起 → PC 执行 → 审批回执），不是双向持续会话。Ratchet 协议解决的是"长期密钥泄露后回溯历史会话"，而每帧 ephemeral + 静态公钥定期轮换已经覆盖了实际威胁模型。引入完整 Signal 协议是为不存在的问题付复杂度。

**为什么不是 X25519**：WebCrypto 不支持 Curve25519，App 侧只能引第三方 JS 库补——为一个密码学原语给客户端加依赖，不值。P-256 是 WebCrypto 的 `subtle.deriveBits` 原生曲线，两端都不必自研或引额外库。

### 3. 撤销：绑定作废 + 静态密钥轮换，不做 KRL

`relay-hosted-multi-tenant` 定的硬约束是「一台桌面端同时只绑一个手机；重新扫码 = 换绑，旧手机凭据立即失效」。

- **换绑** = 重新握手生成新的静态密钥对。路由表里旧绑定移除后，旧密钥无处可用，自然失效。
- **不做密钥撤销列表（KRL）**：KRL 解决的是"已泄露的密钥需要紧急作废"这一运营事故场景，不是日常换绑的机制。真需要时由换绑流程顺带完成。

### 4. 签名与加密的分工不变

`request_signature.rs` 的 HMAC 继续存在，职责不变：**对 hermix 的 REST 接口**做认证与防重放。E2EE 保护的是 **relay 帧**。两者覆盖面不同，都需要——且签名必须在密文**外**签名（签 `header || nonce`），否则 relay 无法在不解密的情况下校验路由头。

### 5. PC 侧静态私钥：DPAPI 加密后落盘

调研了本机 `~/.hermix/` 的现状：`auth.json` / `approval_allowlist.json` / `.env` **全是明文**，且项目里**没有任何 DPAPI / keyring / wincred 设施**。照抄明文最省事（符合"现有依赖优先"），但**不采纳**，因为量级不同：

- `auth.json` 里的 token 泄露 → 撤销即可
- E2EE 静态私钥泄露 → 攻击者能**冒充这台 PC 接收后续所有加密帧**。每帧 ephemeral 把历史范围限住了（这正是 §2 的价值），但未来流量全归对方，**撤销不掉**

引入成本比看起来低：hermix 是 Windows-only（PR 禁区明确写了），`windows` crate 已是 workspace 依赖，DPAPI 是系统 API，**零第三方密码学库**。

落地形态：`~/.hermix/identity.json` 存 DPAPI 加密后的私钥 + 明文公钥。**私钥本身永不以明文落盘**，进程内解密后驻留内存。

### 6. 公钥交换：走现有配对二维码

`relay-hosted-multi-tenant` 已定「二维码内含证书指纹」，静态公钥**复用同一条通道**，不新增交互步骤。配对码仍是分钟级一次性短码，扫码一次同时完成：绑定关系 + 证书指纹核对 + 静态公钥交换。

**风险点**：`pairing.rs` 刚被 A 线批次 1 改过 TOCTOU（mint + insert 收敛到同一临界区）。接入时只能在其临界区**之后**做密钥写入，不要把密钥生成并进那个临界区——生成 P-256 密钥对不是快操作，放锁里会放大锁持有时间。

### 7. 不做双轨，直接强制密文

**2026-10-06 定：没有存量客户端**——Hermix M 尚未发布，链路上不存在旧版 App。因此最初设想的「双轨过渡 + 运行时开关」被取消，改为：

- relay 收到**明文 payload 的 route 帧 → 直接拒绝**并记审计事件（`plaintext_frame_rejected`）
- **不做配置开关**。省掉的是一整套"两套收发路径 + 灰度判断 + 兼容期告警"，代码更小，且不存在"开关被忘了拧、托管形态悄悄跑在明文上"这个风险类别
- 代价：一旦上线，协议不兼容就是硬不兼容。**但这个代价在当前时点为零**——没有客户端可断。等真有存量时若需要平滑，那是另一个决策

配套：`PROTO_VERSION` 递增到 2。**旧版明文帧在新 relay 上必须显式拒绝，不能静默降级**——静默降级等于 E2EE 被无声关闭，而且失败形态是"消息莫名消失"，最难排查。握手期就会比对版本号（`proto.js` 现有机制），所以不兼容会在连上时就暴露，不是等到发消息。

## Alternatives considered

**字段级加密（只密 `text` / `approval` 等字段）**。否决：让"什么算内容"成为协议约定，两端版本漂移即静默泄露；且 relay 已需解析帧，收益不抵复杂度。

**端到端 TLS / 透传 CONNECT**。否决：relay 是多租户路由而非单一 TCP 代理，透传会让运营方看到 TLS 握手元数据（连接时间、频率、目标），且无法做绑定路由与限流。

**不做 E2EE，改为"运营方签署保密协议 + 可信执行"**。否决：这是承诺不是技术保证，而 `relay-hosted-multi-tenant` 已经把 E2EE 定为**上线门槛**，用承诺替代门槛等于自我否决已定决策。

**照搬 Signal 双棘轮协议**。否决：见 §2 末。单次 ephemeral 交换的复杂度与真实威胁模型不匹配。

**现在就把 E2EE 合进功能分支**。否决：E2EE 必然改动 `apps/relay/src/proto.js` 与 `relay_proto.rs` 的帧结构，而功能分支的 16 个提交尚未并入 main。先合再改会把同一批冲突付两次成本。

**双轨过渡 + 运行时开关**（本篇上一版的做法）：relay 同时收密文与明文帧、后者打告警，给存量客户端留迁移期。**2026-10-06 否决——当时点上不存在存量客户端**（Hermix M 未发布，链路上没有旧版 App）。双轨要付的代价是两套收发路径、灰度判断分支，以及"开关被忘了拧、托管形态悄悄跑在明文上"这一整类运维风险，一分换不来。改为直接强制，见 §7。

**协议不兼容做成硬失败**（旧版 App 升级后连不上）。**2026-10-06 接受**——没有存量可断；且不兼容在**握手期**就暴露（`proto.js` 已有 `proto_version` 比对），退化成"能连上但消息莫名消失"才是真正难查的失败形态。

## Consequences

- **内容级审计能力永久放弃。** 事故复盘只能靠"谁在何时发了多少"配合端侧留存的对证，无法由运营方回看内容。这是 E2EE 的定义性代价，不是缺陷——但必须写明，否则日后一定会有人要求"加个开关"来破它。若真要保留可审计性，代价是放弃托管形态、退回自建。
- **relay 侧几乎不用改。** 初稿误判「relay 在拆包再组包，要改成透传」——实际上
  `apps/relay/src/proto.js` 顶部注释就写着「只放 tag 与版本号，帧定义不在这里」，
  且明确说明**故意不解析内层帧**（因为重组请求会让手机端 `X-Hermix-Signature`
  失效）。转发是 `router.js` 的 `sendFrame(envelope)` 整包透传。E2EE 只需要把
  body 换成密文字段，relay 的解析与路由逻辑一行不动。**这是本篇最大的省事处。**
- **协议版本号必须递增**（`proto.js` / `relay_proto.rs` / `envelope.ts` 三处
  同名常量）。旧的明文帧在新 relay 上必须被显式拒绝而非静默降级——静默降级
  等于 E2EE 被无声关闭。
- **两端都要实现密码学**：Rust 侧需引入 X25519 / XChaCha20-Poly1305 / HKDF 依赖；App 侧（uni-app）需 WebCrypto 路径。**App 侧是最大不确定性**——uni-app 各端的 WebCrypto 可用性不一致，需先验证，不能假设。
- **帧格式不兼容**：协议版本号需递增，旧的明文帧在新 relay 上必须被显式拒绝而非静默降级——静默降级等于 E2EE 被无声关闭。
- **性能**：每帧一次 X25519 + 一次 HKDF + 一次 ChaCha20，在 1~4KB 帧上开销可忽略；帧频率受限于 LLM 往返，远低于需要批量化的量级。
- **与自建形态的关系**：自建与托管共用同一客户端代码，本篇只改帧格式与密钥交换，不触碰 base-URL 可替换这条硬约束。
