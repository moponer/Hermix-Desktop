# Decision Note: 案台架构 · 开发/办公统一工作空间

Status: proposed — 「IM 隐喻 → 工作台隐喻」的架构重设计，覆盖入口体系、任务归属机制与人性化交互；效果稿 `apps/desktop-tauri/design-previews/2026-10-15-workspace-cockpit.html`

Supersedes: `docs/notes/proposed/feature/2026-10-15-app-layout-redesign.md`（增量式优化，已被推翻）

## Decision

### 0. 出发点（为什么必须换架构）

Hermix 现在的结构是聊天软件：会话列表常驻、气泡流居中、产物挤在右栏。但用户要它完成的是**工作**——开发任务（改代码、跑命令、看差异）与办公任务（写材料、审校、出报表）。这两类工作的主体是**过程与产物**，对话只是叙事层。

三条物理约束推导出架构：

1. LLM 的产出形态是**事件流 + 产物**，而对话同时承担**驱动**与**记录**两个职责——所以对话流恒定占主列，终端/差异/预览/文档/表格在右侧**副屏**并排出现，而不是被塞进底部或抽屉
2. 会话是**检索物**不是**常驻物**（开发者靠 ⌘K 找，不靠扫列表）——所以 280px 会话列退位成 60px Rail
3. 输入动作是**下命令**不是**写信**——所以输入框变全局命令行，而非对话区底部的大卡片

### 1. 内置能力与项目功能的入口布局

三级入口体系，**每层有硬上限**：

| 层 | 位置 | 上限 | 内容 |
|---|---|---|---|
| 一级 · 能力域 | Rail 顶部（暗墨） | 6 项 | 工作台 / 任务 / 专家 / 自动化 / 知识 / 洞察 |
| 二级 · 上下文工具带 | Stage 头部 44px | 7 项 | 随能力域 × 领域（开发/办公）变化，见 §2 |
| 三级 · 万能检索 | ⌘K 命令面板 | 无限 | 全量命令、会话、任务、文件、设置，分类分区 |

- **Rail 底部**恒定两项：任务队列计数（badge）+ 设置。
- **项目功能**（区别于内置能力）不占 Rail：它们挂在**任务内部**——进入某个任务后，Stage 工具带里的项目专属动作（如“运行该项目测试”）才出现，退出即消失。
- 入口不留两位数以上，超出的必须降级到 ⌘K：这是守住 Rail 60px 与工具带 44px 几何约束的必要代价。

### 2. 入口分类与优先级

**三类动作，各自的行事规矩**：
- 任务型（动词）—直接产生执行，进工具带：*运行测试 / 生成大纲 / 导出汇报*
- 导航型（名词）—切换视图，进 Rail：*任务 / 专家 / 知识*
- 配置型（齿轮）—低频，只进 ⌘K：*模型设置 / 权限策略*

**优先级模型**：`优先级 = 领域匹配度 × 使用频率 × (1 / 破坏性)`。

- 领域匹配度由**当前任务的领域标签**决定（开发 / 办公），同一入口在另一领域自动降级
- 破坏性高的动作（删除、强制覆写、改权限）强制降级到 ⌘K + 二次确认
- 每领域工具带只留前 7 项，第 8 项起进 ⌘K

**工具带对照（示例）**：

| 开发任务 | 办公任务 |
|---|---|
| 终端 / 运行测试 / 差异审查 / 索引代码库 / 构建产物 / 调试会话 / 依赖清单 | 大纲 / 语言审校 / 版式套用 / 表格提取 / 引用核校 / 导出汇报 / 素材库 |

### 3. 命令行任务归属识别机制（核心）

底部命令行是**全局**的，所以必须回答"这条指令投给谁"。

**归属三要素**：目标环（输入左侧彩色任务 chip）+ 输入容器整体染色 + 投放回执（右下角 toast 指向目标任务）。

**四种归属来源**：
1. **当前聚焦任务**（默认）——命令行继承上次聚焦的任务，chip 显示任务名与色点
2. **显式切换**——点 chip 弹出任务选择器；或输入 `@` 触发任务补全（`@审查`）
3. **逐任务草稿**——每个任务保存独立草稿，切任务时草稿跟着切，不丢半句话
4. **无归属 = 新任务**——chip 显示"新任务"，发送即建档

**并行时的状态语言**：

| 目标任务状态 | 命令行表现 |
|---|---|
| 空闲 | 常规态，`❯` 提示符绿亮点 |
| 执行中 | chip 右侧显示进度点 + “执行中”，发送时提示「将排队第 2 位」，仍可发送 |
| 等待审批 | 命令行上方浮出待办条：「任务 X 需要确认 1 步」+ `⌘A` 直接通过 |
| 已结束 | 自动切回上一个活跃任务，chip 变回该任务色 |

- 任务色取自**固定的 8 色任务笺色板**（`--task-c1…c8`），不从强调色现场推导——任务是并行的客体，允许有色方块彼此区分，但必须与品牌绿强调色分开两个语义：强调色表态，任务色表物。
- 键盘：`⌘1…9` 切任务 · `⌘↩` 投送 · `⇧⌘K` 归档当前任务 · `⌘A` 通过审批。

### 4. 人性化体验设计

**任务上下文记忆**
- 案卷（右侧）自动累积：最近文件（带 ±行数）、本次用到的专家、本任务偏好（如"始终先跑测试"）
- 切回任务时恢复三样东西：工具带焦点、草稿、上次会话的滚动位置
- 闲置 >30 分钟再回到任务，Stage 顶部给一张「上次做了什么」小卡：三行摘要 + 继续/重做

**状态提示**
- 三级：空闲（无装饰）/ 执行（日志滚动 + 案卷进度）/ 需决策（Rail badge 红点 + 命令行上方待办条）
- 通知不打断：桌面通知 + Rail badge + deck 状态灯三路，窗口聚焦时只走后两路（避免自己通知自己）
- 审批一律可 `⌘A` 键盘通过，不必移鼠标到那种卡片上

**快捷操作**
- ⌘K 万能面板：命令 / 会话 / 任务 / 文件 / 设置五区混排
- 斜杠命令：`/diff`、`/test`、`/沟通`
- 选中浮动工具条：在对话结果里选中一段文字，浮出"解释 / 改写 / 存入知识库 / 生成子任务"
- 拖拽投放：拖文件到命令行 = 附加到目标任务上下文

**通知与协作**
- 批注：在差异卡 / 文档卡上留 comment，附到任务上，后续开始新任务时可继承
- 移交：任务卡可转交给另一个专家（切换 persona 但保留上下文）
- 汇报导出：把一次任务的叙事流渲染成汇报文档（Markdown/PDF），是办公域的一级能力而非打印功能

### 5. 任务类型适配评估（对抗性自检）

> **2026-10-16 修正（重要）**：本节初稿把"对话"当成了**叙事层**（记录发生了什么），并据此提出"批式任务不进叙事流"——**这条是错的，已废弃**。
> 用户指出：几乎所有任务（写文档、调表格、批量转换、图片处理、脚手架）**都是通过对话过程推进的**，对话是驱动层而非旁白。
> 因此形态维度不决定"要不要对话"，只决定**对话旁边并排显示什么**。Stage 结构随之改写，见下。

用八类常见任务压测架构。**领域标签（开发/办公）只回答了"是什么活"，没回答"活的形状"**——这是本次自检最大的发现。

| 任务类型 | 主体产物 | 适配度 | 缺口 | 补丁 |
|---|---|---|---|---|
| 代码开发（改功能 / 修 bug） | diff + 终端 + 测试 | **高** | 多文件 diff 在卡片里太窄 | 卡片最大化（焦点态） |
| 代码优化（跨文件重构 / 性能） | 前后基准对比 + 改动集 | **中** | 缺"对比卡"；跨 30+ 文件时案卷文件列表爆炸 | 对比卡 + 改动集按模块聚合 |
| 新建开发项目（脚手架） | 目录树 + 初始文件 | **低** | 对话比例极低，需要多选表单（选技术栈）；叙事流几乎空转 | Stage 增加「表单/清单模式」 |
| 写 Word 文档 | 文档本体（需持续编辑） | **中** | 要章节大纲 + 编辑区；反复改同一份会产生 N 个版本，叙事流被草稿淹没 | 产物版本 + 编辑模式（大纲/正文双栏） |
| Excel 表格 | 表格数据（大面积 + 表格工具） | **中** | 小卡片装不下；此时工具带该显示表格工具而非领域工具 | 卡片最大化 + 焦点产物接管工具带 |
| PDF 批量转换 | 批处理队列（几十文件、进度、失败重试） | **低** | 无话可说也无物可看，强行套叙事流很别扭 | 任务形态第二维度 + 批处理面板 |
| 图片处理 | 视觉资产（需对比、参数微调、多版本） | **中高** | 缺画廊视图与参数面板；反复生成产生多版本 | 画廊态 + 参数面板 + 版本 |
| 创建工作台 | 配置类产物（工具集/布局/专家绑定） | **中** | 产物既不是文件也不是图片，现有卡片类型表达不了 | 结构预览卡（树形）+ 一键切入 |

**五条补丁（已按"对话是驱动层"重写）**

- **P-1 形态 = 副屏类型（不是"是否对话"）**：`领域（开发/办公） × 形态（差异 / 文档 / 表格 / 批队 / 画廊）`。对话流恒定占主列；形态只决定**右侧副屏显示什么**：
  - 开发 → 差异 + 终端
  - 写文档 → 文档大纲 + 批注
  - 表格 → 表格预览（可最大化）
  - 批量转换 → 队列进度（成功/进行/失败可重试）
  - 图片 → 画廊 + 参数
- **P-2 Stage = 主列（对话） + 副屏（产物）**：副屏可最大化铺满（写文档、改表格时把对话收成窄列，而不是关掉）。画布模式是副屏最大化后的多卡片态，不是替换对话。
- **P-3 焦点产物接管工具带**：工具带 = f(领域, 焦点产物类型)。表格获得焦点时工具带是表格工具，不是"运行测试"。
- **P-4 产物版本**：对话流记录**过程与决策**；草稿与中间稿归入产物的版本树（v1/v2/v3 可对比）。没有这条，长文与图片微调会把对话流冲垮。
- **P-5 聚合视图**：改动集按模块聚合（不铺平文件列表），批处理按状态分组（成功/失败/重试中）。

**边界（诚实说明）**：案台架构成立的前提是**任务由对话驱动**——按用户反馈，Hermix 几乎所有任务都满足（含批量转换与图片处理），所以边界很窄。真正不适用的是"无需对话、纯按钮式吞吐"的工具（例如一个只有上传按钮的格式转换小工具），那种产品该直接用作业队列 UI，对话流与案卷都是负担。

## Alternatives considered

- **会话列表常驻 280px（现状）**：否——会话是检索物；常驻会把 Stage 压到 640，而 OCR/diff/终端都没法舒服地看
- **每个任务一个独立窗口 / 多窗口**：否——桌面吃内存，且失去统一命令行；用 Rail + 任务队列在同一窗口内解决并行
- ** assigning 色随机生成**：否——随机色会让“色相只给主行动”的规矩崩掉；用固定 8 色任务笺 + 强调色分离
- **命令行按会话切换 Tab（即多 Tab）**：否——Tab 让用户管理容器；命令行+目标环让任务管理容器，认知负担低一级
- **每任务一个独立输入框**：否——重复 UI；单输入框 + 目标环 + 逐任务草稿更省且更一致

## Consequences

- 代价：**学习成本**。用户第一天要重新理解"会话去哪了"——用 Rail hover 检索 + ⌘K 缓解，并提供旧布局短期开关（一个月的迁移期）
- 开发成本：Canvas 模式依赖 `react-grid-layout`（已是依赖）；任务笺色板需新增 8 个令牌并进 CONTRACT（每套主题必须声明）
- 需要新的持久化对象：`Task`（含领域标签、任务色、草稿、上下文快照、lastActive）
- 验收点：并行 3 任务下，指令投错任务的概率应趋近 0——这是本设计的唯一硬性指标，需做可用性测试
- 「案台」架构一旦落地，会话列表不再是一等公民；IM 式连续追问由叙事流承担，不再由会话列表承担
