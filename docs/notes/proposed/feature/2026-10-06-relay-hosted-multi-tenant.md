# Decision Note: 手机端产品化——扫码配对 + 一手机多桌面（修订自建 relay §待拍板 3）

Status: proposed — 2026-10-06 立项。产品前提：**多用户、多客户端 + 手机端**（产品负责人 2026-10-06 明确）。修订 [手机端伴侣客户端 + 自建 Relay（2026-10-04）](2026-10-04-mobile-relay-selfbuilt.md) §待拍板 3，新增运营方托管形态。实现细节归实现，本篇钉死**用户可见的交互规格**。

## Decision

### 用户可见的交互规格（产品契约，实现不得偏离）

1. **装好桌面端 → 出码**：需要手机远程时，桌面端出示配对二维码（手输配对码为无摄像头兜底）。
2. **手机扫码 → 完成**：手机扫码即完成与该桌面端的绑定，随后即可像 QQ 机器人式远程对话一样指挥这台桌面端。全程两个用户动作，中间环节（relay、token、指纹）一律不可见。
3. **绑定关系硬约束**：一台桌面端同一时间**只能绑定一个手机**；重新扫码 = 换绑，须桌面端当场确认，旧手机凭据立即失效。**一个手机可绑定多台桌面端**（家 / 办公室……），手机上切换操作对象。
4. 桌面端在配对当场显示"有新手机绑定"提示；解绑双向（手机端移除 / 桌面端重置）。

### 手机端设计要点（随本篇实施）

- **首页 = 桌面端列表**：名称（可改名）、在线状态、位置标签；右上「添加」= 扫码。
- **点入即会话**：聊天式远程指挥界面；审批卡片内嵌会话流（按 10-04 已拍板：只给「允许一次 / 拒绝」，不给持久允许）。
- **通知**：任务完成 / 待审批走系统推送（App 切后台也收得到）。
- **管理**：长按桌面端卡片 → 重命名 / 解绑（解绑调服务端撤销该绑定）。

### 实现层（归实现，列出即评审过的关键决策）

- **桌面端开箱连默认中央 relay**（运营方托管，多租户）：用户无感知，出码即用。高级设置保留「自建 relay 地址」入口——自建形态（10-04 已实现路径）继续可用，作为数据自主与 dogfood 形态。
- **商业限制后置**：收费 / 名额等策略是服务端策略，**不进配对关键路径**（此前版本的"邀请码先输"设计废除——它把运营问题塞进了用户体验）。
- **凭据阶梯**（内部）：node token（桌面身份）↔ device token（手机身份），绑定关系 1:N 落在 relay 的路由表；配对码仍是分钟级一次性短码，扫码 = 换取绑定的载体，二维码额外携带 relay 定位与指纹实现自动 pinning。
- **指纹自动 pinning**：二维码内含证书指纹，手机扫码后与 `/health` 头自动比对、一次确认——人工核对仅在比对失败时出现（自备形态降级 UX 保留人工核对）。
- **E2EE 为托管形态上线门槛**：多用户共用触发 10-04 预留的二期条件；运营方可见明文 = 数据自主承诺破产。

## Root facts

10-04 §待拍板 3 拍板"用户自备服务器"，否决"项目方公共 relay"的理由（数据自主、运营负担）针对的是**替代**自建；产品化以**并列新增**处理：自建保留，托管新增，且数据自主由 E2EE 正面承接。部署实操证据（2026-10-06 运营者视角）：自备形态全套约 1 小时、含 3 个命令行步骤——对最终用户不可用，对运营者是一次性成本。

## Alternatives considered

- **邀请码进配对关键路径**（本篇上一版）：把运营问题塞进用户体验，用户装好桌面端还要先搞一张码才能出码——背离"出码-扫码"两步契约。废，商业限制后置为服务端策略。
- **维持单一自备形态**：多终端普通用户无法上手。弃。
- **砍指纹**：配对防伪锚（防 relay 掉包偷凭据）且手机端 `canSubmit` 硬依赖。弃；改自动 pinning。
- **无 relay 直连**：10-04 §待拍板 4 已拍板否（唯一通道），不重开。

## Consequences

- relay 多租户化：绑定关系（1:1 硬约束、换绑失效）落在路由表与凭据层；DB schema、限流、撤销、审计扩展。
- 运营方承担可用性与滥用治理；E2EE 上线前托管形态不得收用户。
- 桌面端需新增：出码 UI、换绑确认、绑定状态展示；手机端为全新 App 形态（列表 + 会话 + 审批 + 推送）。
- 自备形态与托管形态共用同一客户端代码，仅 relay 地址来源不同（10-04 §待拍板 4 的"base-URL 可替换"硬约束继续成立）。

## 待拍板（拍板前托管侧不开工）

1. E2EE 是否为托管上线门槛（推荐：是）；
2. 商业模型（免费额度 / 收费）——归主人；
3. 默认中央 relay 的域名与品牌——归主人。

## Reintroduction conditions

（新增能力，无删除项。）若"手输配对码"在扫码不可用场景证明高频，按新笔记恢复增强输码引导，不回退扫码契约。
