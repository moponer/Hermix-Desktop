# Decision Note: 托管 relay（多租户）——手机端产品化形态

Status: proposed — 2026-10-06 由部署实操触发立项（个人自建形态的全套 VPS/证书/指纹/CLI 签发流程对最终用户不可接受）；**修订 [手机端伴侣客户端 + 自建 Relay（2026-10-04）](2026-10-04-mobile-relay-selfbuilt.md) §待拍板 3 的决策**，新增"运营方托管"部署形态。本篇在 main 工作区，合并入功能分支后相对链接生效。

## Decision

在已拍板的「用户自备 relay」之外，**新增第二个部署形态：运营方托管 relay（多租户）**，作为面向普通用户的默认产品形态。两形态并列、不互斥：

| 形态 | 适合人群 | relay 运维 | 数据位置 |
|---|---|---|---|
| 用户自备（已实现，保留） | 极客 / 数据自主优先 | 用户自己（VPS + 域名 + relayctl） | 用户自己的 VPS |
| **运营方托管（本篇新增）** | 普通多终端用户 | 运营方（一台中央 relay） | 运营方 relay，**E2EE 保障内容自主** |

托管形态四件套（全部待实施）：

0. **四级凭据阶梯**（实现者必读，防混淆——"邀请码"≠"六位配对码"）：
   **邀请码**（新增，租户层：桌面端首启一次性输入，向托管 relay 注册名额，长期有效/限量）→ **node token**（桌面长效身份，注册即发）→ **六位配对码**（会话层：桌面出码、手机扫码/输码，分钟级 TTL 一次性，现状已有）→ **device token**（手机长效身份，现状已有）。邀请码取代的是"管理员逐个 `relayctl add-node`"，配对码不动。
1. **多租户 relay 改造**（`apps/relay/`）：node↔phones 按"用户组"隔离；凭据生命周期从 CLI 扩展出**注册接口**（邀请码 → 桌面端首启自助换 node token）；管理面（列表 / 撤销 / 限流 / 审计扩展）。
2. **扫码自动配对**：桌面端展示二维码（内含 `relay_url + pairing_code + cert_fingerprint`），手机扫码自动比对指纹并完成 pinning——用户只点一次确认。现有"手输六位码 + 肉眼核对指纹"保留为自备形态的降级 UX。
3. **桌面端首启激活 UI**（DevicesTab 扩展）：二选一——「我有自己的服务器」（填地址 + token，走已实现路径）/「我有邀请码」（走托管注册）。
4. **E2EE 成为托管形态的上线门槛**：10-04 笔记已预留"二期采纳 dshmobile `plan-e2ee.md`（X25519 + XSalsa20-Poly1305），触发条件是 relay 部署到不可信主机或多用户共用"——**多租户正好触发**。运营方可见明文 = "数据自主"承诺破产，所以托管形态不带 E2EE 不得上线。自备形态维持明文 + 已有鉴权不变。

## Root facts（为什么修订 §待拍板 3）

§待拍板 3 否决"项目方提供公共 relay"的两个理由——数据自主、长期运营负担——都成立于"用它**替代**自建"的前提。产品化不替代它：自建保留（数据自主用户与 dogfood），托管作为新增 tier，且把"运营方不可信"问题用 E2EE 正面解决（否决理由被技术手段吸收而非无视）。部署实操证据（2026-10-06，运营者本人视角）：VPS + Node 项目 + 域名 + LE 证书 + 指纹注入 + relayctl 签发，全套约 1 小时且含 3 个只能命令行完成的步骤——对最终用户是适用性死刑。

## Alternatives considered

- **维持单一自备形态**：多终端普通用户无法上手，产品不成立。弃。
- **砍掉指纹核对简化配对**：指纹是配对瞬间的防伪锚（防 relay 掉包偷 device token），且手机端 `canSubmit` 硬性依赖。改为扫码自动 pinning 保留安全价值、UX 降为一次点击。弃（指简化版）。
- **直接上账号体系**（邮箱登录换 token）：比邀请码重一个量级，用户量未证。邀请码起步，账号体系列入 Reintroduction。
- **公共明文 relay（无 E2EE）**：违背数据自主，否——见 Decision 4。

## Consequences

- relay 从单租户变多租户：DB schema、审计、滥用治理（限流 / 泄露撤销）都是新增面；"只路由不执行"的零业务逻辑硬约束**不放松**。
- 运营方承担 SLA / 滥用 / 撤销响应责任；单点故障域覆盖所有托管用户（10-04 §待拍板 4 "无退路"的后果被放大，E2EE 后内容风险可控但可用性风险仍在）。
- 自备路径继续可用，作为 dogfood 与高级形态；两条路径共用同一 App/桌面端代码，仅配置来源不同。
- 需要新增的待拍板（拍板前不得开工托管侧）：
  1. 邀请码起步 vs 直接账号体系（推荐邀请码）；
  2. 托管服务商业模型（收费 / 免费额度）——商业决策，归主人；
  3. E2EE 是否作为托管上线门槛（推荐：是）。

## Reintroduction conditions

（本篇为新增能力，无删除项。）若未来"数据自主"要求升级到自建形态也可用 E2EE，按 dshmobile plan-e2ee 的演进笔记另立。
