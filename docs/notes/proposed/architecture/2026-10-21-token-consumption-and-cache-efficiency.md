# Decision Note: Token 消耗结构分析与缓存命中率优化方案

Status: proposed — 2026-10-21 完成全量盘点 + provider 级对照实验；**2026-10-22 复核后重心更正**（见「事实 6」：真正的头号浪费不是 prompt 层，而是会话历史无界累积）。方案待拍板后实施

## ⚠️ 复核更正（2026-10-22）

本篇初稿把「prompt 层的冗余与 churn」当成主项。复核后**这个重心是错的**：

- 初稿写「单次请求真实输入 ≈ 43K token / 每章 ≈ 320K」—— **错了**，那是拿
  `prompt_cache` 日志里 `chars÷4` 的估算值当成真实 token。实测 provider 报的
  单次请求是 **~1M token**，比系统提示大两个数量级。
- 真正的构成：**会话历史占了 99%**，系统提示只占 1%。所以 P1 档（prompt 瘦身）
  最多省 1%，**降级为锦上添花**；头号措施换成「有界历史窗口」（已实施，见下）。

下面「事实 6」是复核时补的，「Decision」一节已按新重心重排。

## 事实 6（复核补，最重要）：会话历史无界累积，占请求的 99%

### 6.1 provider 的 `prompt_tokens` 是「单次请求大小」，不是累计计数

初稿怀疑它是累计计数器（会话第 7 分钟就报 2.8M）。实测排除：

| 请求 | system 字符 | provider 报的 `prompt_tokens` |
|---|---|---|
| 1 | 12K | 3,816 |
| 2 | 24K | 7,416 |
| 3 | 36K | 11,016 |

随 system 线性变化（比值 2.89 ≈ 设计值 3.0）→ **单次请求大小**。
于是生产里的 `prompt_tokens = 8,027,881` 是**真的**：那一次请求带了 800 万 token。

### 6.2 请求里 99% 是累积的会话历史

该会话（41 轮）的 `messages` 表：

| 列 | 字符 | 是否进 LLM 请求 |
|---|---|---|
| `content` | 561,460 | ✅ |
| `tool_calls`（模型自己发起的工具调用的 JSON） | 2,051,896 | ✅ |
| `extra`（自动化投递元数据：`automation_name` + 完整提示词） | 3,525,402 | ❌（`load_session` 过滤 `role='automation'`） |
| 系统提示 | 68,796 | ✅ |
| 工具 schema | 31,381 | ✅ |

模型窗口（`minimax/minimax-m3.1-flash:free`）= **1,000,000 token**，实测请求 ~1M → **顶满整个窗口**。
系统提示在其中占 **1%**。

### 6.3 为什么压缩一直没救场

压缩阈值 = `(max_context − output_reserve) × 0.8` ≈ **380K token**。
压缩器是接了的（`local_agent_service.rs:1165`），`archive_context_section` 也无条件执行
—— 但它只把中间内容**写到磁盘**（`ctx.get_messages()` 是不可变引用，**并不缩短活上下文**），
真正会缩短的 LLM 压缩器要等到逼近阈值才动手。

结果：**前 40 轮历史无界增长，第 41 轮才刚够到阈值**。压缩在这个任务上等于没有。

### 6.4 「89.21% 命中率」的真实含义

它是「**一个巨大的请求**里 89.21% 被缓存了」，不是「小请求被缓存了 89%」。
新鲜部分 ~10.8% ≈ **800K token/轮** —— 这才是每轮真正在付的钱。

## 事实 7（2026-10-22 补）：每轮调用都在重复注入同一份 skill 正文

探针加了分项之后，messages 段的构成一目了然：

```
#1  system=50068 tools=26272 messages=84194  (内容25073 + 工具调用0   + 工具结果59121)
#5  system=50068 tools=26272 messages=197282 (内容110549+ 工具调用913  + 工具结果85820)
#11 system=50068 tools=26272 messages=319523 (内容238763+ 工具调用3651 + 工具结果77109)
```

「内容」以 **~21.7K 字符/次调用**线性增长，而模型输出才 ~2.2K token/次 —— 说明
**每次 API 调用都在往 messages 里追加约 21.7K 字符**，追加的不是模型的输出。

根因（`run_loop/pre_turn.rs`）：**每次工具迭代**都重新注入

| 块 | 上限 | 位置 |
|---|---|---|
| 自动匹配的 skill 正文 | `skill_injection_char_budget` = **16,000 字符** | `pre_turn.rs:204` |
| 跨会话教训 | 1,200 字符 | `pre_turn.rs:179` |

旧注释写「Compression folds them on context pressure」—— 但压缩要逼近模型窗口才
触发，这里根本等不到（见事实 6.3）。**同一文件的 plan-mode 块有去重守卫**
（"skipped when a recent message already carries it"），skill / 教训块**没有**。

每次追加都是**新的字节** → 在块级前缀缓存下**全部变成 fresh token**。这正是
「命中率只有 83.6%、但绝对消耗已经降了 10 倍」的原因。

修法：新增 `ctx_has_same_block(ctx, marker, new_content)` —— **最近一份**同类块的
内容与新的相同就不重复追加（不是「任意一份」，否则换了用户消息、命中集合变了
就不会注入新的）。

## 事实 8（2026-10-22 补，最隐蔽的一个）：MCP 掉线 → 工具整批缺失 → 25% 的调用在「摸工具」

P2 档的实测把「摸工具」这件事拆开了，结论比预想的重要得多：

| | 次数 | 占比 |
|---|---|---|
| `list_tools` | 73 | 8% |
| `tool_describe` | 49 | 5% |
| `search_files` | 45 | 5% |
| `terminal` | 27 | 3% |
| `tool_search` | 42 | 5% |
| **摸工具合计** | **236** | **25%** |
| 真正干活的 `tool_call` → 查看器工具 | 644 | 70% |

**根因不是模型笨、也不是 skill 写得不好** —— 是**那批工具压根不在注册表里**：

```
08:27:41 INFO [hermix_mcp::client] Connecting to MCP server: hermix-viewer
08:27:41 INFO [hermix_server::state] MCP server connected
08:33:25 INFO [hermix_server::state] MCP server connected
10:20:43 WARN [hermix_server::state] MCP server connect failed at startup; skipping   ← 视图器进程中途死了
10:30:52 WARN [hermix_server::state] MCP server connect failed at startup; skipping
```

MCP 客户端**只在 sidecar 启动时连一次**，连不上就 `skipping` —— 于是那 30 个
`hermix-viewer__*` 永远不进注册表。佐证：

- `/v1/tools` 从 110 个掉到 **80 个**（查看器工具归零）；
- `tool_search` 搜 "webview" → `{"matches":[],"total_deferred":25}`；
- agent 直接调 `hermix-viewer__webview_eval` → 报
  `'hermix-viewer__webview_eval' not found`（这条来自桥接处理器，
  `tool_search.rs:586`）。

**而每次摸工具的调用都带着整个上下文** —— 5 次摸工具 ≈ 白烧 5 个完整请求。
这是长跑任务最大的单项浪费，比系统提示里的冗余大一个数量级。

### 修法

1. **MCP 掉线自动重连**（`state.rs`）：连接改成后台循环，每 30s 重读配置、给
   「启用但未连上」的 server 重连。覆盖「启动时 server 还没起」（桌面端先起
   sidecar、再拉查看器）与「新加的 server 不用重启 sidecar」。
   端到端验证：sidecar 先起、查看器后起 → 工具 0 → 拉起查看器 45s 后自动变回
   30，**全程无需手动操作**（以前得去「连接器 → MCP」把服务器关一次再开一次）。
2. **skill 纠正**：查看器工具是**常驻**的（这批只有 25 个延迟工具，而桥接阈值是
   `>25`，桥接根本不激活）→ **直接点名调** `hermix-viewer__webview_eval`，
   不要绕 `tool_call`（绕了会多一层，而且桥接在注册表缺它时直接报 not found）。
   实测直接调返回 `{"result":"2"}` ✓。
   并加一句「摸了也没用 → 先怀疑 MCP 没连上」，让 agent 报告真实原因而不是
   继续找替代路径。

### 事实 9（2026-10-22 补）：桥接三件套「看得见、调不动」，且多数时候是纯开销

`tool_search` / `tool_describe` / `tool_call` 是「找工具 → 取 schema → 调工具」
三步链。实测两个问题：

**(a) 看得见、调不动。** `assemble_tool_schemas` 在桥接激活时用
`bridge_tool_schemas(count)` **凭空合成**三个 schema 塞进工具表；而
`tool_describe` 所在的 toolset 不在用户那份 `enabled_toolsets.json`（**10-17**
写的）里 → 按 `apply_persisted_toolset_state` 的「新 toolset 默认关」规则被关掉
→ 它的 handler 不在 agent 的派发注册表里 → 模型看得见 schema、调它必被拒。
证据：`/v1/tools` 里 `tool_describe.isEnabled=false`，而系统提示仍在宣传它
（`directions.rs` 的 `TOOL_DISCOVERY_GUIDANCE`），实测 agent 连着几轮调它都被拒。

**(b) 多数时候是纯开销。** 延迟工具数 < 阈值（25）时桥接**不激活** → 所有工具
都直接可见 → 桥接三件套毫无用处，却占着工具表的位置（prompt token），还
**诱导模型去摸工具**（实测 25% 的调用花在摸工具上）。

### 修法

- **桥接三件套进 `HARD_ESSENTIAL_TOOLSETS`** —— 桥接是**机制**不是可关的功能，
  它的每一步都必须可调度（与 `core` 里的 `list_tools` 同性质：模型的逃生口）。
- **桥接未激活时不把这三个放进工具表** —— `directions.rs` 的指引按可见工具名
  gate，于是模型也不会再被告知桥接存在。

### 事实 10（2026-10-22 补）：成本公式落地 —— 窗口 × 未命中率 × 调用次数

修完上面几条之后重新量了一轮（`task-1792560224893`，run 84），发现**成本不再由
「单次请求多大」决定，而由下面这个乘法决定**：

```
每轮计费 token ≈ 窗口 token × 未命中占比 × 每轮调用次数
```

实测代入：

| 项 | 实测值 | 来源 |
|---|---|---|
| 窗口（送进模型的历史） | 237,258 字符 ≈ **60K token**（卡满预算） | `prefix_probe` 的 `messages=` |
| 未命中占比 | **9.8%**（命中率 90.2%） | `token_usage` 的 `cache_read/prompt` |
| 每轮调用次数 | **67** | `messages` 表 assistant 行 |
| 每轮计费 | 5,727,989 − 5,164,728 = **563,261 token** | `token_usage` |
| 验算 | 60K × 10% × 67 ≈ 402K ＋ 新增字节 ≈ **563K** | ✅ 对得上 |

**所以省成本只有三条路，且互相独立**：
1. **调小窗口** —— 未命中那 10% 按比例下降（每轮省 ~200K token/档）；
2. **提命中率** —— provider 侧，已到「命中时 97~98.5%」的天花板；
3. **减少调用次数** —— 每少一次调用省 ~8.4K token。

**窗口内部是什么（`prefix_probe` 的括号拆分）**：

| 组成 | 字符 | 占窗口 |
|---|---|---|
| 内容（user + assistant 文本） | 94,912 | 40% |
| 工具调用（JSON 参数） | 9,709 | 4% |
| **工具结果** | **132,637** | **56%** |

**这里有个反直觉的点**：工具结果看着最大，但 `rollup_tool_results` 已经把 30K 字符
的 DOM 压成了一行存根。DB 里 1,223 条工具消息的分布是 `<200 字符` 1,118 条、
`200-1k` 92 条、`1k-5k` 13 条 —— **存根平均只有 81 字符，却有 1,118 条
（90,870 字符）**。

**存根从不清除**：rollup 把内容换成一行摘要，但那一行摘要会跟着会话一直活到被
窗口裁掉为止。于是 56% 的窗口装的是「1,118 条已经没有信息量的占位行」。
真要省，砍的应该是**存根的数量**，不是单条存根的长度。

### 事实 11（2026-10-22 补）：会话 id 带冒号 → 归档 / 记忆 / 清理三处静默写不出

Windows 不允许目录名、文件名含冒号，而自动化会话的 id 形状就是
`automation:<task-id>`。写 `.md` / trajectory 早就走 `session_stem`（2026-10-16 的
`im:device:*` 案），但**归档索引、rollup 证据档、会话级记忆目录、删会话清理**
这四处漏了它。

实测后果（跑 84 轮之后）：

- `rollup archive: failed to create dir ...\sessions\automation:task-…: 目录名无效
  (os error 267)` —— 每轮一条；
- `~/.hermix/sessions/` 下**只有 UUID 命名的目录**，没有 `automation:task-…`；
- `compression_archives` 表至今 **0 条**；
- **会话级 `MEMORY.md` 写不出来** → agent 每轮都无法留下持久笔记，只能每轮
  重新摸状态 —— 这是「每轮 67 次调用」的一部分成因。

**修法**：`session_stem` 提升为 `pub`（「凡是拿会话 id 拼路径的地方都必须共用本
函数」），四处统一改用它，补回归测试钉死（`colon_session_id_still_writes_archive_files`）。

### 事实 12（2026-10-22 补）：摸工具占比 34% → 8%

修完「桥接看得见调不动」+「MCP 掉线自动重连」之后，干净窗口（run 84 落地后，
`id > 212428`）重测：

| | 修复前（最近 950 条助手消息） | 修复后（run 84） |
|---|---|---|
| 摸工具调用 | 401 | **6** |
| 占全部工具调用 | 401/1,156 = **34%** | 6/67 = **8%** |
| 明细 | list_tools 98、search_files 84、terminal 93、tool_describe 55、tool_search 71 | list_tools 4、tool_search 2 |

命中率同期从 78~84% 升到 **90.2%**（`token_usage` id 772）。

### 事实 13（2026-10-22 补，**推翻事实 10 的成本模型**）：探针的 `messages=` 不是真实载荷

事实 10 用 `prefix_probe` 的 `messages=` 当窗口大小，算出「窗口 × 未命中率 ×
调用次数」。**这个口径是错的**，实测才发现：

自动化的 assistant 消息在 DB 里存的是 `role='automation'`，而
`session_persistence::load_session` 的 SQL **明确排除该角色**
（`role != 'automation'`）—— 它只给前端时间线看，不进 LLM 上下文。
于是从 DB 载回来的历史里**一条 assistant 消息都没有**，只剩 tool 结果：

```
DB 载入 2,553 条 → assistant 消息 0 条 → tool 结果 1,341 条
```

这些 tool 结果在 provider 层是**孤儿**（没有对应的 tool_call），发请求前
就被丢掉（`dropping orphan tool_results before LLM request`）。

**所以**：
- 探针的 `messages=`（~180K~240K 字符）**高估了真实载荷**；
- 真实载荷 = system + tools + **本轮**（turn 内累积）的消息；
- 「有界历史窗口 60K」裁的绝大部分是**即将被丢掉的孤儿** → 它对成本的
  影响远小于原以为（它真正的作用是让「孤儿丢弃」这件事便宜，不是省 token）；
- **成本的主项回到「每轮调用次数」**：每轮 ~67 次调用，每次都重发本轮
  累积的上下文 → 每轮计费 ~30~56 万 token，摊到每次调用 ~8.4K。

### 事实 14（2026-10-22 补）：调用次数的头号来源是「等视频」

把一轮的真实调用序列打出来（`.git/vtest/calls.py`），一眼看到：

```
212861 webview_eval  (async()=>{await new Promise(r=>setTimeout(r,27000)); …   ← 轮询 1
212864 webview_eval  (async()=>{await new Promise(r=>setTimeout(r,27000)); …   ← 轮询 2
212866 … 27000 … 212868 … 27000 … 212871 … 27000 …                              ← 连着 6 次
212882~212898  8 次调用在反复探测目录图标的 class（roundpointStudent 的背景色）
```

- **一条 831 秒的视频**：2 倍速也要 ~415 秒墙钟；agent 每 27 秒查一次
  `v.ended` → **单节 15~30 次调用**，而每次都带完整上下文。
- **8 次调用在重新推导「目录图标怎么读」** —— 因为会话级 `MEMORY.md`
  写不进去（事实 11），agent 每轮都得重新摸一遍。

**根因是物理约束，不是 agent 懒**：`webview_eval` 的 CDP 读超时只有 30 秒，
**物理上等不完一个 7 分钟的视频**，skill 里写的「同一个 eval 里 await 结束」
根本做不到 → agent 只能退化成轮询。

### 事实 15（2026-10-22 补）：M22 对自动化工作负载是空操作（诚实记录）

M22「丢陈旧工具组的存根」在**自动化**场景下**什么也没做**：
`load_session` 载回来的历史里 assistant 消息数 = 0 → 组数 = 0 → 没有陈旧组
可丢（`.git/vtest/sim-window.py` 复现：`总组数=0`）。

它对**普通对话**（assistant 消息正常入库）仍然有意义（老工具结果不必每轮
重发），但**不是自动化的成本杠杆**。真正的杠杆是事实 14 的「等视频」。

### 事实 16（2026-10-22 补）：agent 自建的 `auto` skill 撑爆技能索引，并会打断前缀缓存

换新 sidecar 后，系统提示从 **50,068 → 69,596 字符**（+19.5K），工具数组从
**26,272 → 53,654 字符**（+27K）。查下来不是新代码引入的，是两件事：

1. **`~/.hermix/skills/auto/` 下堆了 16 个 agent 自己生成的 skill**，
   名字是 `probe-01d635152c9a79d3`、`execute-code-list-tools-search-files-tool-call-tool-search-hermi`
   这类。它们把「技能索引」（预算 20,000 字符）顶满 → 系统提示 +19.5K。
   **更要命的是缓存**：系统提示在载荷的最前面，它一变 → **后面全部变成新鲜
   token**（事实 10 的第 2 条：位置决定代价）。agent 每建一个新 auto skill，
   就等于把这一轮整个上下文重新计费一次。
2. **工具数组 +27K**：查看器 MCP 的 30 个工具这次是**直接可见**的（之前是
   藏在桥接后面）。30 个工具 × ~900 字符 ≈ 27K ✓ 对上。工具数组在轮内是
   稳定的 → 命中缓存后边际成本 ≈ 0；**但它在轮间变（桥接激活与否取决于 MCP
   连上没连上）→ 同样会打断前缀缓存**。

**结论两条**：
- 「工具集合稳定化」这条 P0（迟滞）当初实测「工具指纹跨 3 轮一次没变」就
  标了 ⛔ 不需要 —— **那个实测是在 MCP 稳定连接的前提下做的**。连接/断开
  会让数组在「30 个直接可见」与「桥接三件套」之间跳变，**这是一个真实的
  缓存断点**。
- 技能索引应该**按任务相关性裁剪**，而不是把 agent 自己生成的垃圾 skill
  也算进去（`auto` 分类应当排除，或只保留与当前任务相关的）。

## Decision（按复核后的重心重排）

> **2026-10-22 更正**：本节原写「绝对量的 99% 在会话历史里 → 先把历史管住」。
> 事实 13 推翻了它 —— 自动化会话从 DB 载回的历史里**一条 assistant 消息都没有**
> （存成 `role='automation'`，`load_session` 明确排除），剩下的 tool 结果在
> provider 层是**孤儿**，发请求前就被丢掉。**历史不是成本主项，调用次数才是。**
> 下面保留历史决策，但重心的读法按事实 13/14 修正。

**重心（修正后）：先做「让字节稳定」，再压「每轮的调用次数」，最后才是 prompt 层瘦身。**

核心判断（provider 级对照实验，见下节）：**缓存是块级的，只有变了的字节重新计费。
所以提命中率靠「让字节别变」，不靠「把 prompt 变小」；变小是为了省绝对量。**

**成本的主项是「每轮调用次数」**：每轮 ~67 次调用，每次都重发本轮累积的上下文
→ 每轮计费 ~30~56 万 token。而调用次数的头号来源是**等视频**（事实 14：
一条 831 秒的视频被拆成 15~30 次轮询）—— 已由 M23（长等待）解决。

### P0-新（已实施）：自动化每轮的有界历史窗口

- 新增 `AgentOverrides::history_token_budget`（`hermix-core`）+ `history_window` 模块
  （`hermix-agent`）：按**估算 token**（CJK 感知口径，不是 `chars/4`）从尾部保留，
  切点不落在 tool 结果上、末尾悬空的 tool_call 会被丢掉（两者都会让上游拒收）。
- 两个自动化引擎（JSON 引擎 `dashboard/automation.rs`、SQLite 引擎
  `automation_trigger.rs`）都设 `60,000` token 预算 ≈ 最近 3~4 轮。
- 磁盘上的会话**照旧完整**（UI 时间线 / 归档 / 检索不受影响），只有「送进模型
  的那一份」有界。
- 预期：单次请求 ~1M → **≤100K token**（~10x），每轮 ~7M → **≤700K**。
- **修正（事实 13）**：它裁掉的大部分是**随后就会被丢掉的孤儿 tool 结果**，
  所以它省下的远小于预期；它真正的价值是**让「孤儿丢弃」这件事便宜**
  （不裁的话，每次请求都要先把几万条孤儿消息读进内存再逐条判孤儿）。
  预算值本身对成本影响不大 —— 因此改成**运行时可调**（M20），便于实测。

### P0：让字节稳定（命中率 → 98%+）


对 `https://api.kilo.ai/api/gateway`（`minimax/minimax-m3.1-flash:free`）直接发请求，
唯一变量是「请求体里哪一段的字节变了」：

| 实验 | 命中率 | 相对基线损失 |
|---|---|---|
| 完全相同的请求 | 100.0% | — |
| system 尾部时间戳变（~12 token） | 99.7% | **仅 12 token** |
| 剥离**靠前**那条 assistant 的 `reasoning_content` | **97.5%** | **833 token** |
| 剥离**最后**那条 assistant 的 `reasoning_content` | 99.9% | 297 token |

**结论三条**：

1. **provider 的前缀缓存是块级的**：只有「变了的字节」重新计费，尾部改 12 token 就只损失
   12 token 命中 —— **不是**整个前缀作废。
2. **从某条消息开始改字节 → 从那里往后全部变成新鲜 token**。位置决定代价。
3. 因此优化方向不是「把 prompt 变小」，而是 **「让字节别变」**；把 prompt 变小是为了省
   绝对量，不是为了提命中率。

### 新增档：按成本公式反推的三个动作（2026-10-22）

事实 10 给出公式 `每轮计费 ≈ 窗口 × 未命中占比 × 调用次数` 之后，剩下的手段就只剩
这三个方向，且**互不冲突**：

| 措施 | 做法 | 省在哪一项 | 状态 |
|---|---|---|---|
| **M20 历史预算运行时可调** | `AUTOMATION_HISTORY_TOKEN_BUDGET` 改为可用环境变量 `HERMIX_AUTOMATION_HISTORY_TOKEN_BUDGET` 覆盖（默认仍是 60,000） | 调参不必每次重编 sidecar，把「重编」从实验回路里拿掉 | ✅ 已实施 |
| **M21 会话路径统一** | `session_stem` 提升为 `pub`，归档索引 / rollup 证据档 / 会话级记忆 / 删会话清理四处统一改用它 | 不直接省 token，但**让会话记忆落盘** → agent 每轮少重新摸状态（降调用次数） | ✅ 已实施 |
| **M22 窗口存根治理** | 限制「已 rollup 的工具结果存根」在窗口里的条数上限 | 窗口里 56% 是 1,118 条无信息量存根 | ⚠️ **已实施，但对自动化是空操作**（事实 15：DB 里 assistant 消息为 0 → 组数为 0）。对普通对话仍有效 |

**M22 为什么值得试**：rollup 现在的语义是「把 30K 字符的 DOM 换成一行摘要」——
省了**单条**的体积，但没省**条数**。1,223 条存根 × 81 字符 = 90,870 字符，占了
窗口的 38%。丢掉陈旧存根等于把窗口还给「真正有信息量的最近几轮」。

**M22 的风险**：存根带 `[ALREADY EXECUTED]` 前缀，作用是让模型知道「这个工具已经
调过了」→ 防止重复调用。直接丢存根可能让模型重新调同一个工具。稳妥做法是
**按条数设上限**（比如只留最近 200 条存根），而不是全丢 —— 先量收益再决定。

| 措施 | 做法 | 省在哪一项 | 状态 |
|---|---|---|---|
| **M23 `webview_eval` 长等待** | 查看器 CDP 读超时 30s → 可按 `timeout_ms` 抬到 300s；MCP HTTP 传输 120s → 300s；`per_tool_budget` 给 `webview_eval` 与桥接 `tool_call` 各 300s | **单节 15~30 次轮询 → 1~2 次**（事实 14） | ✅ 已实施 |
| **M24 skill 与任务提示词同步** | 两处都写「一次 eval 等到播完」（skill 说一套、任务 prompt 说另一套 = 白改） | 同 M23 | ✅ 已实施 |

**M23 为什么必须三道闸一起改**：任何一道最矮的闸先掐掉请求，长等待就退化成
轮询（症状是 `os error 10060`）。三道分别是：查看器 CDP 读超时、MCP HTTP
传输总超时、dispatch 的每工具预算 —— 都在上面那张表里。

**只改 CDP 不够**：底层 socket 的读超时是**连接时**定下的（30s），光改命令
的 deadline 不够 —— socket 会先一步超时返回 `os error 10060`。所以
`call_with_timeout` 里要把 socket 的读超时一起调宽。

#### M18：实测一轮里有 5 次调用在「摸工具」

统计最近 300 条助手消息的工具调用：

| | 次数 | 占比 |
|---|---|---|
| `list_tools` | 73 | 8% |
| `tool_describe` | 49 | 5% |
| `search_files` | 45 | 5% |
| `terminal` | 27 | 3% |
| `tool_search` | 42 | 5% |
| **摸工具合计** | **236** | **25%** |
| 真正干活的（`tool_call` → 查看器工具） | 644 | 70% |

**根因**：两个 skill 都假设 `hermix-viewer__webview_eval` 能**直接**调，但这些工具是
**延迟加载**的（不在 `DEFAULT_RESIDENT_TOOLS` 里），必须走桥接工具：

```
tool_call(name="hermix-viewer__webview_eval", arguments={"expression": "..."})
```

模型照着 skill 点名调会被校验器拒 → 就去摸工具 → 每轮 5 次。
**而每次调用的请求都带着整个上下文** —— 5 次摸工具 ≈ 白烧 5 个完整请求。
这是长跑任务最大的单项浪费（比系统提示的冗余大一个数量级）。

|---|---|---|---|
| **单次请求真实 token** | ~1M | **~101K** | **~10x ↓** |
| 每轮 prompt（provider 口径） | 13,078,433 | **2,728,089** | 4.8x ↓ |
| 每调用新鲜 token | ~120K | **~16.5K** | 7.3x ↓ |
| **缓存命中率** | 88.0% | **83.6%** | **↓ 4.4 点** |

单次请求 101K = 窗口 60K + 系统提示 30K + 工具 10K —— **与设计完全吻合**。

**命中率为什么反而降了**（这是诚实要说清楚的）：请求小了 10 倍，「每轮新追加的消息」
这个**变量部分**在总请求里的占比就变大 —— 绝对消耗降了 10 倍，比率却被稀释。
这是「变小」与「变稳」两条路的此消彼长：**要回到 98%，得靠 P0 的字节稳定那一档**
（reasoning 剥离单调化 / 工具顺序确定化 / 工具集合稳定化 / 时间戳冻结），
那些改动在请求变小之后**相对更重要**。

### 实测结果（2026-10-22，字节稳定四件套 + 注入块去重之后）

| 指标 | 修复前 | 修复后 | 变化 |
|---|---|---|---|
| **单次请求真实 token** | ~1M | **~101K** | **~10x ↓** |
| 每调用追加字符（探针分项） | 21.5K | **5.4K** | **4x ↓** |
| 每轮 prompt（provider 口径） | 2,872,829 | **1,462,114** | **2x ↓** |
| system / tools 指纹跨轮 | 每轮变 | **全程不变** | ✓ |
| 缓存命中率 | 70.9% ~ 88.0%（轮间波动大） | 72.5% | 见下 |

### 命中率的天花板是 provider 给的，不是产品能定的（2026-10-22 实测）

直接对 `api.kilo.ai` 做对照实验：

| 实验 | 结果 |
|---|---|
| 同一请求连发 12 次 | **11/12 命中 99.98%**（TTL ≥ 60s） |
| 增长型请求（messages 每轮加一条）14 次 | **8/14 整份命中（命中时 97~98.5%）**，6 次**整份作废**（0.4%） |
| 962 token 的小请求 | 只命中 20% → **provider 有最小可缓存前缀（约 1K token）** |

**结论**：这个免费网关的缓存是**「全命中或全废」**，不是连续前缀缓存。
命中时就是 **97~98.5%**（98% 目标在「命中」这件事上是达到了的），
但增长型请求约 **43%** 的概率整份作废 —— 特征像**多上游/共享 LRU 被别的租户挤掉**，
产品侧改不动。

所以「平均命中率 98%」在这个网关上**做不到**，除非：

1. **换 provider**（带真前缀缓存、缓存 TTL 更长、不共享 LRU 的）—— 这是唯一的真解；
2. 或者**把增长型请求变成固定请求**（每轮固定大小的上下文 → 但那样就丢了对话），
   产品侧的近似做法是**减少调用次数**（每章 7.4 → 5 次），让「抽签」的次数变少；
3. 以及**让每次作废的代价变小**（已经做了：请求小 10 倍）。

**产品侧还能做的**：P2 减少调用次数（每章 7.4 → 5 次）能把平均命中率往上抬
（少 1/3 的抽签次数），绝对消耗也会同步降。

## Alternatives considered

- **只调小 prompt 体积来提命中率**：否决。实验证明缓存是块级的，命中与否取决于**哪些字节变了**，
  不取决于 prompt 多大。把 prompt 砍小但保持每轮都变，命中率不会涨。
- **把 volatile 段挪到请求末尾**：可行但收益小（实测只值 12 token/次），且要改 provider 的
  system/messages 组装方式。**先做 M4（冻结），不够再考虑挪位置。**
- **把 `reasoning_content` 全清空（连本轮内的也不留）**：最省缓存，但会让模型在工具循环里
  看不到自己上一轮的思考 → 连续性下降。**M1 只清「本轮起点之前」的**，保留轮内连续性。
- **给每个 MCP 工具单独开缓存断点**：Anthropic 式缓存支持多断点，但本项目走的是 OpenAI 兼容
  路径，provider 侧是自动块级缓存，**前端加断点无效**。
- **把工具暴露从 109 个砍到路由子集**：P1-6/M13 的方向对，但会改变模型可见的能力面（可能
  够不到某些工具）→ **必须做成可配置开关**，默认保持现状，先在自动化任务这类窄场景开。

## Consequences

- **实施面**：M1/M4/M5 改 `crates/hermix-agent/src/{prompt_assembly.rs,agent_helpers.rs,local_agent_service.rs}`；
  M2/M13 改 `crates/hermix-tools/src/registry.rs`；M3 改 `crates/hermix-agent/src/agent_loop/`；
  M7~M12 改 `crates/hermix-agent/src/prompt_assembly.rs` + `crates/hermix-server/src/dashboard/skills.rs`。
  **这些 crate 此刻由并行线在改**（`crates/hermix-agent/*` 23 个文件、`crates/hermix-tools/*` 13 个文件
  未提交）→ 实施前需要等并行线落地或明确分工，否则会在同一批文件上打架。
- **风险 M3**：工具集合稳定化会降低「模型临时够到某个工具」的概率（路由不再每轮重算）。
  缓解：给路由加显式「换话题」触发条件，而不是纯按分数漂移。
- **风险 M8**：skill 正文按需后，模型可能不主动去取全文 → 站点知识缺失。缓解：索引里给
  「命中即自动注入该 skill 的哪一节」的白名单。
- **观测地基**：M1~M6 的验证都依赖「哪一段在变」可观测。在加哈希 span 字段之前，所有
  命中率改动都只能靠端到端对比验证，迭代成本高 —— **建议先做这一条**。
- **成本现实**：当前模型是 free 档，`estimated_cost` 全为 NULL，**省钱不是当下动机**；
  动机是①命中率高 → 延迟低 → 长任务跑得快；②若将来换付费模型，同样的请求体成本会按
  43K/次 计价，320K/章 × 630 节 = 200M token/门课 —— 那时这轮优化直接决定盈亏。
