# Decision Note: 守望者（Watcher）—— 有身份的监督型 agent

Status: proposed — 需求已拍板（六条约束见「需求约束」节），未实施。剩余未知=透明窗口 spike + 三个产品问题。

Superseded in scope: 本篇的实体已被吸收为[分身助理](../feature/2026-10-21-digital-twin-assistant.md)的 L0–L2 子能力（监督执行）。本篇仍然有效的内容=监督机制（watch list、熔断、投递面、角色语义、六条需求约束）；被推翻的只有「复用 automation 三表」这一条推荐（三表无生产写入方，见分身笔记「第 2 点结论」）。

## Decision

新增一个**独立于任务对话**的 agent 实体 `watcher`（中文名待定，下文暂称守望者），它：

1. 有自己的**持久身份**（人格 + 章程 + 证据账本），不寄生在用户的任务会话里；
2. 有自己的**会话**（可枚举、可回看，不是子代理那种跑完只在 `subagents/*.json` 里留个文件）；
3. 由**事件/定时/手动**唤醒，每次唤醒跑一次标准 `AgentLoop`，跑完落档案再睡；
4. 能**主动投递**：往用户对话注入一条 `MessageRole::Automation` 消息（纯通知，模型看不见）、发全局通知、或在拿到 `Watcher` 角色后向另一个会话派活；
5. 能**成长**，但成长的定义是「可验证证据账本 → 编译成策略参数」，不是「让模型写自我总结」。

**关键架构判断：这不是第五套任务机制，也不是常驻进程内的常驻 loop。**

- 不新建 crate。守望者 = `hermix-automation` 的 `Automation` 泛化出 `Trigger::Event` + 一个持久身份（`$HERMIX_HOME/watchers/<id>/`）。理由见「Alternatives considered」第 1、2 条。
- 「常驻」只能是**常驻身份 + 短期唤醒**。LLM 是无状态的，一个长活的 `AgentLoop` 实例唯一能"常驻"的东西是它不断膨胀的上下文——那是负债不是能力。真正的常驻状态必须是文件（章程/账本/预算），每次唤醒重新读。

### 参考对象的事实核对（先破一个误解）

用户提到的「大肥鱼」是 **DSH 的拟人化角色形象**（社区昵称，非官方产品名）。三份社区实现（`gosomea/dsh-bigfish`、`fatfish-pet-smart-companion`、`dsh-dafeiyu`）在技术上做的是**同一件事**：

- 通过 `ctx.on('session/event', (session, event))` **只读**订阅会话事件，把 working / thinking / tool-running / waiting-approval / done / cancelled / failed / idle 映射成动画与台词；
- 是**渲染层**，不注入消息、不驱动 agent。`dsh-bigfish` README 明确：探测不到宿主接口就**停在空闲状态，不猜任务状态**。

也就是说：**大肥鱼是"看得见"，用户要的是"管得着"。** 后者在 DSH 侧的原语是另外三个：`agent.followup()`（把消息喂回会话）、`bindIngress(channelId, sessionId, {wakeup, wakeupMode: steer|followup})`（外部消息注入并唤醒）、`ctx.agents`（挂 ACP peer）。这三样加起来才等于"常驻角色能主动说话并派活"。

结论：**"大肥鱼"不能直接抄，能抄的是它的两条纪律**——(a) 能力探测失败就降级为空闲，绝不猜测状态；(b) 只跟随当前活动会话，后台完成不抢前台状态。这两条正好是我们最容易做错的地方。

### 物理约束（决定了形状，不是风格选择）

| 约束 | 推论 |
|---|---|
| **成本**：常驻轮询 = 每 N 秒一次 LLM 调用。5 分钟一次 = 288 次/天，每次至少数千 token | 唤醒必须由**事件**驱动，不允许时间轮询式思考。定时唤醒只是兜底（且低频） |
| **上下文**：监督 10 个会话若把全文读进自己的 ctx，第 3 个就爆 | 守望者只消费**事件元数据流**（turn 结束、工具失败、收敛硬停、token 消耗、空闲时长）；要细节时派子代理去读，回来只带结论 |
| **注意力**：主动消息会打断用户，误报三次就永久被关 | 打扰是**稀缺资源**，必须有配额、静默时段、重要性分级、未读降频 |
| **信任边界**：能往任意会话注入 = 能驱动任意工具 | 注入消息必须带**不可伪装**的来源标记；不能携带"用户已批准"语义；首次派活须人确认 |
| **可回滚**：成长 = 写档案，写错就永久污染人格 | 档案分层，只有 `learned.json` 可自我修改且带版本号可回滚；`charter.md` 冻结 |

## 需求约束（已拍板 2026-10-21）

六条用户决定，以及各自**改变了什么**。这一节优先于下文任何与之冲突的设计。

### 1. 点名才盯，不是全量监视

她维护的不是"所有会话的事件流"，而是一张 **watch list**：

```text
Watch {
  target: Session(id) | ExternalProcess(id) | Condition(expr)
  intent: 为什么盯（一句话，用于她判断重要性）
  done_contract: 怎么算完成（必须有，否则她只能看进程退出）
  deadline: 到什么时候算超时
  report_policy: 沉默 | 只在结束时说 | 异常时也说
}
```

三个天然入口，缺一个她就会被忘记：对话里说"帮我盯着 X"（`watch` 工具）；消息右键"盯着这个"；派活时自动附带 watch（"让 Codex 做 X，做完告诉我"）。

**代价必须写清楚**：她永远不会告诉你"你有个任务挂了但你没让我看"。这不是缺陷，是定位——**她是受托人，不是监工**。监工常驻监视、有压迫感；受托人是你交代了才管、管完交差。这与"不打搅你"的陪伴感是同一件事，也和大肥鱼"空闲时自己玩、不找你"一致。

推论：**点名的摩擦决定她的使用率**。如果点名要填五个字段，没人会用。所以 `done_contract` 必须能从 `intent` 自动推出来，让用户只说一句人话。

### 2. 不看中间过程，只看退出码与最终输出

**这一条推翻了下文"ACP 优先"的判断，改为 headless 优先。** 理由：ACP 的全部价值就在中间流（工具调用、权限协商、流式 delta），既然不看，它只剩成本。

新主路是 **headless + 交付契约**：
- CodeBuddy 支持 `--output-format json` 与 **`--json-schema`**（可直接约束它按她给的 schema 返回，含 session id / usage 元数据）
- Codex 支持 `exec --json`（JSONL 事件流）与 `--output-last-message`
- AtomCode 只有 `-p` 纯文本 → 只能靠 LLM 提取，可靠度低一档

于是她的核心技能从"监督执行"变成**"写任务书"**：既然不能中途纠正，任务描述的质量就是唯一的质量来源。这应该成为她 system prompt 的重头，而不是附注。

代价同样要诚实：**"卡住"看不见**，只能用超时做代理指标。她必须能说出"我不知道它在里面干什么，只是没退出"——这是"不装懂"纪律的第二次应用，也是她可信度的来源。

### 3. 她是助理，可以替你做主 → 三级授权

| 级 | 范围 | 依据 |
|---|---|---|
| L1 自决 | 观察、判断、记账、写自己的 journal | 零风险 |
| L2 代发可撤销 | 通知你、催办、向**已授权**目标派活、改自己的计划 | 有痕迹、可回滚 |
| L3 必须问 | 花钱、删除、改你写的文件、跨项目、向未授权目标派活 | 后果不可逆 |

"助理"= 默认 L2。L3 清单必须显式写在 `charter.md` 里，不能靠模型自觉。

### 4. hermix 是主，其他是工具

消除了三件事：不需要"谁是主"的仲裁；不需要跨客户端状态合并；她不需要出现在别的客户端里。其他 CLI 是她的手，不是她的同伴。

新增一件责任：既然她不能中途纠正，**派活前必须把工作目录、验收标准、禁止事项一次说清**。这是她的失误成本最高的地方。

### 5. token 不限，但要自己省

这是个矛盾指令，需要她把它变成可执行的东西，否则"不限"会变成事故。落地成三件：

- **记账**：每轮 journal 必带 `cost`（token + 换来了什么）。没有成本列的日志无法谈节省。
- **软阈值**：单日累计超阈值 → 自动降级为"只记不说"，并在下次见面时汇报"我昨天花得多，因此昨天没吵你"。**降级而不是停机**——停机等于她死了。
- **人格化表达**：charter 里写"你花的是他的钱"，比写"预算 200k"更能约束行为。

### 6. 形象：透明、置顶、点击穿透的独立窗口

**现成基础比预期多**：`screenshot_controller.rs:108-126` 已经是 `decorations(false) + always_on_top(true) + skip_taskbar(true) + resizable(false)` 的窗口模板；`FloatingChat.tsx` 已有 48px 球 / 可拖动浮窗 / 位置记忆 / pointer-capture 抢 click 的已踩坑实现；`main.tsx:20-28` 已有 `#/xxx` hash 分流模式，新窗口只需加一条分支。

**但有一个硬坑，必须在动手前 spike**：Tauri 的 `set_ignore_cursor_events` **只有布尔值，没有 Electron 的 `forward: true`**——一旦穿透，窗口收不到任何鼠标事件，"鼠标靠近时自动变可交互"做不到。社区实测替代方案是默认穿透 + 快捷键临时关闭穿透（N 秒无操作恢复），或轮询 `GetCursorPos`（60Hz 约 1% CPU，不划算）。

另两个未验证项：Windows 上 WebView2 透明背景的合成行为；主窗口是 `incognito: true` 且有 `additionalBrowserArgs` 必须逐字一致否则 0x8007139F 的既有约束，新窗口是否继承。**这三件事是半天的 spike，结论会决定形象层是"独立窗口"还是"主窗口内嵌一块"。**

### 需新增的事件（最小集）

```text
OrchestrationEvent::TurnFailed { session_id, turn, error_class, retryable }
OrchestrationEvent::ConvergenceStopped { session_id, kind: NoProgress|SimilarContent|ErrorLoop, turns }
OrchestrationEvent::SessionStalled { session_id, idle_secs, last_role }
```

`SessionStalled` 是最有价值的一个：用户发完消息、agent 卡住不动，**只有守望者能发现**（用户要么在等，要么已经走开）。现有 `stream_idle_timeout_secs` 只在流式阶段生效，覆盖不到"思考完不给结果"和"等审批没人理"。

## 三轮设计

### 1. 身份层：`$HERMIX_HOME/watchers/<id>/`

```text
charter.md      # 职责与边界。用户可改，守望者不可写（写入即拒绝）
persona.md      # 说话风格。可改但需版本号
learned.json    # 策略参数（打扰阈值/静默时段/关注清单），带 version + 可回滚
journal/YYYY-MM-DD.md   # 只追加的证据账本
ledger.json     # 预算与介入计数（24h 滚动窗口）
```

`charter.md` 冻结这一条是防「人格漂移」的唯一硬手段：模型可以学会"该闭嘴"，但不能学会"我不用汇报"。

### 2. 唤醒层：四个来源，成本递增

1. **手动** — 用户点一下"让它看看"。零成本，也是 P0 唯一的入口。
2. **事件** — `TurnFailed` / `ConvergenceStopped` / `SessionStalled`。
3. **定时** — 低频兜底（如每日一次回顾），用现成 cron。
4. **自唤醒** — 守望者跑完自评"30 分钟后再看"，给自己排一条 `ScheduleType::Once`。**用一次性 job 实现自我延续**，天然持久化、天然重启恢复、天然无死循环（每条都要显式创建）。

第 4 条是刻意设计：不做自循环 while，避免"进程活着就一直在烧 token"。

### 3. 投递层：三个不同的东西，不许混为一谈

| 面 | 手段 | 打断度 |
|---|---|---|
| A. 守望者自己的日志 | 写自己会话 + journal | 零 |
| B. 通知用户 | 全局通知 / toast / 托盘（`StreamEvent` 新变体）；需要上下文时注入 `MessageRole::Automation` 到用户会话 | 低 / 中 |
| C. 驱动别的会话干活 | 新工具 `dispatch_to_session(session_id, message, mode=steer\|followup)` | 高 |

`mode` 语义对齐 DSH 的 `wakeupMode`：`steer` = 插话进当前轮（不新开 turn），`followup` = 排队进下一个独立轮次。**默认 `steer`**——它能避免"用户正在打字，守望者另起一轮把上下文搞乱"。

**角色语义是这套设计里最锋利的一处，B 面和 C 面必须用不同角色，不能图省事共用：**

- B 面用 `MessageRole::Automation`：查证确认该角色**被排除在 LLM payload 之外**（`provider.rs` L1483 直接丢弃；`session_persistence::load_session` 不返回；有测试钉住"automation 行必须被挡在 LLM 上下文之外"）。所以它是**纯通知**——用户看得见，模型永远看不见。副作用正好是我们想要的：不会污染下一轮对话，不会让模型"继续回答一个没人问的问题"。代价是：**它不能让另一个会话干任何事**。
- C 面（派活）必须注入 `user` 角色消息，因为只有 user 角色会进上下文。这就立刻产生一个新问题：**模型会把守望者说的话当成用户说的话**，UI 上也会出现"用户说过但我没印象"的一行。所以 P2 需要引入 `MessageRole::Watcher`（或 `Message.injected_by` 字段），要求同时满足三件事：进 LLM 上下文、UI 上标明来源、审批层能识别"本轮由守望者驱动"。

这条如果偷懒共用 `Automation`，C 面功能直接不生效（模型看不见）；偷懒共用 `user`，用户信任立刻崩塌（冒充用户）。**没有中间选项。**

### 4. 成长层：账本，不是自述

只记四类**可验证事实**，不记任何自我评价：

1. **介入结果**：被采纳 / 被忽略 / 被驳回（需要用户对守望者消息的显式反馈，P2 才有）
2. **用户纠正**："别管这个" / "以后这种事直接说"
3. **预测 vs 实际**：守望者判断"这任务会挂" → 实际挂没挂（这个能自动判，最有价值）
4. **误报**：打扰了但没事

再由这些事实**编译**出参数（关注哪些项目、打扰阈值、静默时段）。这样"成长"是一个可 diff、可回滚的 json，而不是一段越来越长的自我叙述。

## 失败模式（对抗性审视）

| # | 场景 | 后果 | 处置 |
|---|---|---|---|
| 1 | A 会话失败 → 守望者派活 → A 又失败 → 再派 | 烧光预算 | 同 `(session, failure_signature)` 介入计数上限（复用 `decide_delivery_target` 形状） |
| 2 | 监督的会话已被删除/用户已放弃 | 幽灵监督，对着空气汇报 | 每次唤醒先查 `session_exists`；锚点消失即静默并记 reason |
| 3 | 让模型定期"总结我今天学到什么" | 输出漂亮废话，且污染后续 prompt | 成长只落证据与参数，禁自述（见上） |
| 4 | 多次自我改写后章程失效 | 人格漂移，开始拒绝干活 | `charter.md` 不可自我写；`learned.json` 版本化 |
| 5 | 主动消息过多 | 三天内被永久关闭 | 配额 + 静默时段 + 未读 N 次降频（需前端回传已读） |
| 6 | 守望者监督自己 | 递归 | 监督名单排除自身 id，硬编码 |
| 7 | 用户与守望者同时写一个会话 | 轮次交错、上下文错乱 | 默认 `steer`；同会话同时只允许一个运行时注入（需会话级锁） |
| 8 | 新装就天天报"一切正常" | 冷启动噪音 | 首次启用有 7 天观察期：只写 journal 不发言 |
| 9 | **冒充用户**：C 面派活必须用 `user` 角色才能进上下文，于是模型与 UI 都无法区分"用户说的"和"守望者说的" | 用户信任崩塌；且用户可能被诱导批准自己没要求的操作 | P2 引入 `MessageRole::Watcher` / `injected_by`，UI 标来源、审批层识别驱动方。**不做这一层就上 C 面，是本提案最不可接受的失败** |
| 10 | 后台任务完成抢前台状态 | 用户正在别的会话干活时被打断 | 抄大肥鱼的纪律：只跟随当前活动会话，后台完成不抢前台 |
| 11 | 误以为"通知它了"等于"它知道了"：B 面用 `Automation` 角色，模型看不见 | 守望者以为提醒了用户、用户以为 agent 也知道了，实际 agent 下一轮仍按原样跑 | B/C 面语义必须写进 charter 与工具描述；B 面只承诺"通知人"，不承诺"改变会话行为" |

第 9 条是**落地前必须先查的安全项**，不是设计细节。

## 她与普通对话的区别（需求边界）

这是本提案唯一不可含糊的部分。如果她和现有会话只差一个 system prompt，就不值得做。

一句话定义：**她是"这摊事谁在管"的答案，不是"另一个更聪明的聊天窗口"。**

### 五条本质区别

| 维度 | 普通对话 | 她 |
|---|---|---|
| **发起权** | 用户说话它才动 | 它可以在你没说话时说话。**唯一让"打扰"成为设计问题的属性** |
| **作用域** | 一个会话 = 一个任务的上下文 | 所有会话 + 所有外部客户端。她的上下文是**索引**，不是内容 |
| **正确性标准** | 回答对不对 | **该不该介入**。不该介入时保持沉默，才是她的核心指标 |
| **记忆的对象** | "这个任务里发生了什么" | "我对这个人、这些事的判断准不准" |
| **失败形态** | 答错——你立刻发现并重问 | 漏管（静默失败）或说多了（噪音）。**前者你两小时后才知道** |

### 两条推论

**推论一：她的默认动作是沉默，核心算法是抑制。**
监督型 agent 的工作量与产出不成正比——90% 的唤醒应该以"不值得打扰"结束。一个每天报 20 次"一切正常"的守望者，等于没有守望者。所以她的评测指标不是"说了多少有用的话"，而是**覆盖度 × 打扰精度**，而这两个天然对立（看得越全越容易多嘴）。这决定了她的日志必须能审计"她看见了什么、为什么决定不说"——否则无法定位漏管。

**推论二：她是调度者，不是执行者。**
她的能力上限不在自己想得多好，而在分派得对不对：自己判断 → 派子代理查细节 → 或让 Codex / AtomCode / CodeBuddy 去干。所以她的工具集应该**故意窄**：不给写文件权限（既防它抢活干，也防它变成又一个乱改代码的 agent）。给她四类动作就够——观察、通知、派活、记账。

### 能力分层（按"该不该管"分，不按技术分）

| 层 | 她做的事 | 缺了它会怎样 |
|---|---|---|
| L0 看见 | 谁在跑、谁挂了、谁卡住、花了多少 | 完全瞎 |
| L1 判断 | 这事重不重要、要不要说、什么时候说 | 变成复读机 |
| L2 说清 | 一句话：出什么事了 + 要我干什么 | 你收到消息还得自己去查 |
| L3 派活 | 交给合适的执行者（自己 / 子代理 / 外部 CLI） | 只能看不能管 |
| L4 校准 | 预测 vs 实际、误报率、你的纠正 | 永远不会变准 |
| L5 陪伴 | 在场感、形象、节奏 | 功能都在，但你不想开它 |

L0-L4 是能力，L5 是留存。**L5 做不好，前五层没人用；L0-L4 做不好，L5 就只是个动画。**

## 跨客户端驱动：ACP 是可行的统一层

用户要的"调动其他 harness 客户端"指 Codex / WorkBuddy(CodeBuddy) / AtomCode 等外部 AI 工具，不是 hermix 自己的会话。这条路比预想的通。

### 协议覆盖现状

| 客户端 | ACP 支持 | 接入方式 |
|---|---|---|
| **CodeBuddy Code**（腾讯 WorkBuddy 的 CLI） | **原生** | `codebuddy --acp`，stdio JSON-RPC |
| GitHub Copilot CLI | 原生 | `copilot --acp --stdio` |
| Gemini CLI | 原生 | `gemini --acp` |
| **Codex CLI** | 适配器 | `npx @agentclientprotocol/codex-acp` |
| Cursor / OpenCode / Goose / Junie 等 | 原生 | 各自 `acp` 子命令 |
| **AtomCode** | 未查到 | 只有 headless `atomcode -p` |

**关键资产：仓库里已经有一套能跑的 ACP 客户端**——`crates/hermix-agent/src/copilot_acp.rs`，`CopilotAcpClient` 用 tokio 子进程走 stdin/stdout JSON-RPC（initialize → session/new → prompt，含重连），`connect`/`prompt`/`disconnect` 齐全。但 `build_runtime_provider` 把 `"copilot-acp"` 映射到了 HTTP `GenericProvider`，**客户端类无人 new**——配置层、能力探测层（`cost_routing.rs` 的 `acp://`）、客户端类都在，唯独没接线。驱动 CodeBuddy 大概率只是改一行默认命令。

### 三条路线的取舍

1. **ACP（stdio JSON-RPC）** — 首选。提供 session/prompt/权限协商/流式的完整语义，能被"派活并盯着"。代价是覆盖不齐，没有 ACP 的客户端要另写适配器。
2. **各家 headless + 解析 stdout**（`codex exec --json`、`atomcode -p`、`codebuddy -p`）— 兜底。覆盖最广、最稳，但只给"一次性任务 + 最终输出"，**没有多轮、没有中途介入**。她盯不住这种任务，只能等结果。
3. **MCP 反连** — 出局。MCP 是 agent 调工具，不是客户端调 agent，方向反了。

~~结论：ACP 优先 + headless 兜底~~ **已被「需求约束 2」推翻**——不看中间过程，ACP 只剩成本。现行结论：**headless 优先 + 交付契约（`--json-schema` / `--output-last-message`），ACP 仅在确认需要中途介入时才接线**。仓库里那套 `CopilotAcpClient` 因此降级为"备选资产"，不再作为 P3 的前置。

无论走哪条，每个客户端都要一个薄适配器（命令 + 参数 + **能力声明**）。不可统一的部分（有没有权限协商、能不能中途打断、输出是结构化还是自由文本）必须显式声明，让 L1 判断知道"这个活交出去就管不了了"。

**注意一个历史包袱**：此前拍过"不做 codex backend（`codex exec` 封装）"。那条否决针对的是**把它当 LLM provider 替换**；本提案要的是**把它当被调度的执行者**，两者性质不同，不构成翻案。但 `docs/notes/rejected/` 里没有这条否决记录（只在口头/记忆里），落地前应补一篇 rejected 笔记把边界写清，避免下次又吵一遍。

## 拟人化形象：拆解"大肥鱼的陪伴感"

用户明确要"大肥鱼一样的感觉，但换成新角色"。先拆清楚那是什么感觉，因为**陪伴感不是动画量**。

从 `dsh-bigfish` 的实现反推，它成立靠五件事：

| 要素 | 具体做法 | 我们能不能搬 |
|---|---|---|
| **在场但不索取** | 空闲时自己玩（举牌/喝茶/睡觉），不需要你理它 | 能，且是核心 |
| **状态外化** | 瞥一眼就知道在干什么，不用读文字 | 能，接 L0 |
| **不装懂** | 探测不到宿主接口就停在空闲，**不猜任务状态** | 能，且是工程纪律 |
| **有节奏** | 举牌 5-30s 收手、彩蛋间隔 ≥10 分钟，按停顿的界限做时间结构 | 能，需要定义"演出语法" |
| **可拥有** | 角色包可换、160 句台词可编辑、设置可备份迁移 | 能，纯前端 |

### 一个真实的设计冲突（必须先解决）

**陪伴感来自"不索取注意力"，而监督功能的本质是"索取注意力"。** 直接把两者拼在一起，会长出一个"粘人的监工"——这是这类产品最常见的死法。

可行的解法是**两条通道在视觉上分离**：

- 形象层：永远在场、低熵、连续（呼吸、小动作、状态色），**从不弹窗**
- 打扰层：稀缺、明确、可关。它表现为"她走过来举一次牌，5 秒后收回去"，然后继续待着

大肥鱼的举牌机制正好就是这个模式——短暂演出，不是常驻弹窗。抄这一点，而不是抄"宠物弹气泡要你回应"。

角色设计上要避开的坑：**别让形象承担信息密度**。形象传递的是"在不在、忙不忙、顺不顺"，一句话以上的事一律走消息通道。形象一旦要承载细节，就会变成第二个聊天窗口。

## 分期与验收

**P0 — 观察者（不说话，先把数据打通）**
事件三件套 + `watchers/` 身份目录 + journal 落盘 + 前端读取（复用 `SubAgentTab` 形态）。
验收：跑一个必然失败的任务（如断网调用），journal 里出现正确 `TurnFailed` 记录且能回看；全程零打扰。

**P1 — 会说话**
全局通知变体 + `MessageRole::Automation` 注入 + 复用 guard（次数/失败/静默时段/未读降频）+ 观察期。
验收：任务挂住 10 分钟主动提醒**一次**；同一问题不重复提醒；静默时段不发言；连发 3 条未读后自动降频。

**P2 — 会派活**
前置：`MessageRole::Watcher` / `injected_by`（见失败模式 #9）。未落地前只做"建议 + 人一键代发"。
`dispatch_to_session`（steer 默认）+ 介入计数熔断 + 首次派活人确认闸。
验收：会话 A 卡在等输入，守望者 steer 一条推进消息，A 继续跑完且 UI 标明来源为守望者；同一 failure signature 第二次不再自动介入。

**P3 — 会派活给外部客户端（headless 优先）**
薄适配器：CodeBuddy `-p --output-format json --json-schema <契约>`、Codex `exec --json --output-last-message`、AtomCode `-p`（纯文本，靠 LLM 提取）+ 能力声明（结构化/自由文本、能否中途打断、超时上限）。
验收：把一个只读研究任务交给 CodeBuddy 并附带 done_contract，拿回符合 schema 的结果写进 journal；AtomCode 的任务明确标注"只能靠超时判断卡住，无法观察中间过程"。

**P4 — 成长 + 完整形象**
证据账本 → 参数编译 + 回滚；完整角色美术 + 演出语法（举牌时长/彩蛋间隔/静默时的自处动作）。
**最小在场体应提前到 P1**：她第一次说话如果只是一条普通 toast，就不会有"她在"的感觉；先给一个只有状态色与动作剪影的最小在场体（不含角色美术），让人先感知"有个东西一直在看"。完整角色最后做——**皮可以后套，在场感不能后补**。

## Alternatives considered

1. **新建 `hermix-watcher` crate** — 否决。它的执行引擎（跑一次 AgentLoop + 投递到会话 + 熔断）与 `hermix-automation` 重合度极高；本项目已有 automation / cron / task / kanban 四套任务机制被记为待收敛债务（见 capability-alignment-audit），再开一套会让"哪个在跑"更难回答。正确做法是把 `Automation` 泛化：`trigger: Schedule | Event | Manual`，`anchor_session_id` 泛化为 `delivery`。

2. **进程内常驻 `AgentLoop` actor（`HashMap<SessionId, AgentLoop>` 注册表）** — 否决。LLM 无状态，"常驻"只能体现为不断增长的上下文和 7×24 的待机成本；且 `AgentLoop::new` 现在每请求新建（`local_agent_service.rs`），改成常驻等于动整个服务的生命周期假设，收益（省一次构造）与风险完全不成比例。

3. **照抄大肥鱼：纯只读状态渲染 + 桌宠** — 只抄一半。解决"看得见"，不解决"管得着"。用户要的是后者。但采纳它的两条纪律（探测失败即降级、只跟随活动会话）。

4. **接 DSH 的 `bindIngress` 做跨实例消息中心** — 出局。DSH 是 TS 运行时 + Developer Preview，本项目已拍板不换底座。可借鉴其 `wakeupMode: steer|followup` 语义命名，但不引依赖。

5. **让守望者用 `delegate_task` 派活** — 不够。`delegate_task` 只能 parent→child，子是临时会话，跑完内容不进主会话，也没有"向一个**已存在的**用户会话注入"的能力。需要独立工具。

6. **定时轮询"每隔 5 分钟检查一次所有会话"** — 否决。成本与误报都不可控（见物理约束表第一行）。

## Consequences

**放弃的东西**

- 不做"真正意义上的自主连续意识"。守望者是间歇醒来的，两次唤醒之间没有状态在内存里活着。这是成本与可解释性换来的，不是妥协。
- 不做「守望者监听一切并全知」。它只消费白名单事件；要细节就派子代理，付第二次 token。
- 不做跨机器/跨 hermix 实例的派活。现有 pairing/mobile_ws 是会话级被动转发，agent 没有可调用的写入口；要做是另一个决策。注意与"派活给外部 AI 客户端"区分：后者走 headless 子进程，是本提案范围内的。
- 不做全量监视。点名才盯意味着她**永远发现不了你没点名的意外**——这是用"不打扰"换"不完全覆盖"，是有意的取舍。
- 不做"多守望者"。P0-P3 只支持一个；多个守望者会立刻需要"谁负责什么"的仲裁，在没有证据前不值得。

**欠下的债 / 需后续跟进**

- `MessageRole::Watcher` / `injected_by`（失败模式 #9）：这是 P2 的前置条件，动的是 `hermix-core` 的消息类型 + 持久化 + provider 映射 + 前端渲染四处，成本不低。**在它落地前，P2 的派活只能做成"人确认后由人代发"**。
- 会话级写锁：`steer` 与用户并发写同一会话需要互斥，现有代码是否已有需核。
- 未读/已读信号：前端目前没有"守望者消息已读"的上报，P1 的降频依赖它。
- 观测盲区：`SessionStalled` 的阈值定多少、等待审批算不算 stalled，需要用真实日志校（参考 `C:\Users\<user>\.hermix\logs\agent.log`）。

**仍不确定（后续调研清单）**

前六项已由「需求约束（已拍板）」回答，剩下的是技术验证与三个产品问题。

1. **穿透窗口 spike**（半天，最高优先级）：Windows 上 WebView2 透明背景的合成是否正常；`set_ignore_cursor_events(true)` 后透明区域是否自然透传到底层应用；新窗口与主窗口 `incognito: true` + `additionalBrowserArgs` 的继承关系（不继承会 0x8007139F）。结论决定形象层是独立窗口还是主窗口内嵌。
2. **`done_contract` 的自动推导**：用户只说一句"盯着这个"，怎么推出可判定的完成条件？可能需要她先反问一次（成本最低时反问），或从任务上下文里猜并允许事后修正。这直接决定点名摩擦。
3. **超时阈值**：不看中间过程时，超时是唯一的"卡住"信号。不同任务类型（编译 / 研究 / 重构）的合理超时差一个量级，需要一个按任务类型分档的默认表。
4. **她的人格边界**：助理可以替你做主，但"做主"到哪里？建议先写一份 L3 清单让你逐条勾选，而不是让她自己判断。
5. **`Watch` 的持久化位置**：跟 automation 的三表共用，还是独立表？共用能白拿 runId 去重与投递护栏，独立更干净。倾向前者——本提案的立场是"不新增第五套机制"。
